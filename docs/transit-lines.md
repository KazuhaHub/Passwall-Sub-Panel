# 托管中转：PN 服务器之间的中转线路

> 状态：第 1 期（透传）已实现于开发分支（2026-11-16）。只针对 Passwall Node（`PanelKind = psp`）作为入口。

## 1. 目标

`用户 → A → B → 目标`，A 是 PN 服务器，转发由 PSP 下发和管理。一台服务器可以只做中转、只做落地或两者都做，**不设角色字段**，由线路的引用关系推出来。

## 2. 模型：中转线路的“入口”

沿用现有的中转线路（`domain.RelayLine`），新增一个属性 `EntryPanelID`：

| 入口 | 谁配转发 | 行为 |
|---|---|---|
| 外部（`0`，旧数据的默认值） | 管理员在面板外配（realm/gost/iptables、CDN） | 与以前完全相同 |
| PN 服务器（非 `0`） | PSP 下发给该服务器 | 中转服务器确认生效后才发布 |

这和同行的模型一致：V2Board/Xboard 把中转当成落地节点的子节点，只是转发要手动配。我们把同一个概念的“转发”这一步交给 PN。线路的其他能力原样可用，不用另写：订阅生成、线路 Region/Tags、分组可见性、“按线路选择”、健康探测。

线路本身仍存在 `nodes.relays`（管理员拥有）。托管才需要的运行状态单独放在 `transit_forwards` 表里，每条托管线路一行，只由同步服务写：

- 下发给节点的转发键 `fwd_<id>`；
- 中转服务器最近确认的转发（入口、端口、目标、目标端口）；
- 转发流量。

这样同步服务永远不改写管理员的列，两台中转服务器同时确认同一落地的不同线路也不会互相覆盖。

## 3. 两种方式

| | 透传（第 1 期，已实现） | 隧道（第 2 期，已实现） |
|---|---|---|
| 链路 | A 原样转发到 B 的用户入站 | A 解开用户协议，经 A—B 隧道从 B 出口 |
| 身份、计费、审计在 | B | A（按 B 的规则，见 §5） |
| A 持有用户凭据 | 否 | 是 |
| 隧道协议 | 无 | 每条链路可选：SS-2022（不过墙）／VLESS+REALITY（过墙） |

## 4. 场景

| A 的位置 | A→B | 推荐 |
|---|---|---|
| 境外 | 境外互通 | A 可信时用隧道（SS-2022），否则用透传 |
| 境内 | 专线 | 透传 |
| 境内 | 公网过墙 | 透传（B 自己的协议负责抗封锁）；要用隧道必须选 VLESS+REALITY |

入口端口由管理员填写，适配只开放部分端口的 NAT 机。

## 5. 访问策略跟着出口走

一条连接适用它出口服务器的规则。

- B 禁止 X：直连 B、经 A 透传、经 A 隧道，都禁止。
- A 禁止 X，B 不禁止：直连 A 禁止；经 A 到 B 的连接不禁止。

透传时执法本来就在 B。节点上，转发的流量**不进入**中转服务器自己的策略路由：路由的第一条规则就把转发直接交给 `direct`。否则落地是专线内网地址时，会被中转服务器上的“禁止私网”规则拦下。真实内核测试和变异测试覆盖了这一点。

隧道时执法在 A：A 编译策略时，按服务器划定范围的规则对走隧道的入站改看出口服务器，并用 `DestinationRule.Inbounds` 限定入站，不需要改协议。例如范围只含 A 的规则不再作用于从 B 出口的入站，范围只含 B 的规则只作用于它们；范围同时含 A、B 的规则照旧作用于全部入站。没有隧道的服务器，策略和编译缓存键都与以前相同。B 上隧道的入站同样直接交给 `direct`，不再经过 B 的策略。

## 6. 第 1 期实现

**Protocol**
- 能力 `transit.forward.v1`。
- `ConfigBody.Transit.Forwards`：`omitempty`，没有线路时配置字节不变。
- `ForwardKey`（`fwd_<id>`）是独立类型，不会被解析成监听器键。
- 转发作为 config 流对象上报四态；`ForwardCounters` 只出现在全量报告。

**Node**
- Xray 编译为 `dokodemo-door`，sing-box 编译为带 override 的 `direct` 入站。
- 与监听器同端口时，只拒绝该转发对象本身。
- Xray 统计转发流量；sing-box 本期只跳过转发连接、不计量（第 3 期起 sing-box 也计量，见第 7 节「第 3 期补充」）。

**PSP**
- 只向声明了能力的中转服务器下发。
- 端口已被该服务器自己的入站占用、或两条线路争同一端口时，在下发前就撤下，不让节点因此拒绝整份配置。
- 中转服务器持有当前配置并报告 `applied` 时记为确认，`rejected` 等其他状态撤销确认。
- 线路的 `Publishable()` 要求确认内容与当前期望完全一致：改端口、改落地地址或端口后，旧的确认不再算数。读取不到状态时同样不发布，即“失败即关闭”。
- 流量只接受发给该中转服务器的转发键，并按计数器 epoch 处理重置。转发流量不计入任何用户。

**保存时校验**
- 入口必须是 PN 服务器，且不是落地自己所在的服务器。
- 必须填写入口端口，不能覆盖 SNI 或 Host。
- 入口端口不能与该服务器的入站或其他托管线路冲突，停用的入站和线路也算。

## 7. 第 2 期实现

**模型**：节点增加“出口服务器”（`egress_panel_id`，0 为本服务器）。每对有序服务器（入口 A，出口 B）一条隧道，A 上所有出口为 B 的节点共用。

**Protocol**
- 能力 `transit.link.v1`。
- `Transit.LinksIn`（出口持有）、`LinksOut`（入口持有）、`Egress`（入站 → 隧道），都是 `omitempty`。
- `LinkKey`（`lnk_<id>`）独立类型；隧道作为 config 流对象上报四态；`LinkCounters` 只出现在全量报告。
- 隧道协议：`ss2022`（2022-blake3-aes-128/256-gcm）或 `vless_reality`（指纹 chrome 等）。

**Node**
- 出口：SS-2022 或 VLESS+REALITY 入站，直接交给 `direct`。REALITY 走与普通入站相同的客户端兼容检查。
- 入口：每条隧道一个出站。允许类规则按出口拆分：本机组保留原规则，每条隧道组得到一份副本（规则标签加 `~lnk_N` 后缀）指向隧道出站；拦截规则不拆分（第 3 期带 `AuditEgress` 时例外，见「第 3 期补充」）；每个隧道组最后有兜底规则。隧道断开时连接失败，不回退从 A 直出。
- 审计按 `~` 前去掉后缀找回原规则。
- 计数：隧道的出入口各自计数；Xray 提供，sing-box 在第 3 期补上（见下面的「第 3 期补充」）。
- 真实内核矩阵（入口 × 出口内核 × 协议，共 8 种）覆盖 TCP、UDP、入口拦截规则，以及出口停止后不回退。

**PSP**
- 隧道在第一次需要时创建，同时生成两种协议的全部凭据（SS 密钥、X25519 密钥对、UUID、short id），切换协议无需新凭据。REALITY 伪装站点从默认列表随机选取，管理员可以修改。
- 出口端口在 20000–59999 中随机分配，避开出口服务器的入站、进入它的托管线路和其他隧道。
- 入口拨号的地址：管理员填写的出口地址；留空时用 PSP 最近一次看到出口服务器同步的来源地址。新建节点时连接地址同样默认取服务器地址，可修改。
- 只向声明了 `transit.link.v1` 的服务器下发。出口端口被入站占用、或没有可用地址时，在下发前撤下该半边。
- 两侧各自记录“已下发”和“已确认”的摘要；入口一侧的摘要包含绑定的入站。节点只在两侧都确认当前内容、且该节点在入口已下发的绑定里时才发布（`EgressReady`），否则从订阅中撤下，不回退直出。
- 隧道流量取入口的计数，入口没有时取出口的；不计入任何用户。

**保存时校验**
- 节点和出口都必须是 PN 服务器，且出口不是节点自己的服务器。
- 隧道设置：协议必须是两者之一；出口地址必须是合法主机；REALITY 伪装站点必须合法。

### 第 3 期补充：命中记录出口与 sing-box 计量

- **sing-box 计量**：sing-box 服务器也统计转发与隧道的流量（转发、隧道的入口与出口各自计数），按计数器 epoch 处理重置；没有 Xray 时的“只跳过、不计量”不再成立。
- **命中记录出口**：PSP 只在四个条件同时成立时给策略置 `AuditEgress`——该 agent 声明了能力 `audit.hits.egress.v1`、编译引擎是 Xray、该服务器有出口绑定（编译输入的 `Egress` 非空）、记录没有关闭（协议校验拒绝“记录关闭却带出口标志”）。没有隧道的服务器和 sing-box 服务器收到的策略与摘要和以前逐字节相同；能力进入编译缓存键，能力变化会重新编译；回退到最近已知良好策略时标志只降不升。策略带该标志时：策略带 `AuditEgress` 标志时，入口给每条命中附上它经过的隧道（`AuditHit.Egress`，空表示从本服务器直出）。标志只在 Xray 上生效；拦截规则也只在这个标志下按隧道拆分（每条隧道一份副本），不带标志时拦截规则不拆分，与以前字节相同。
- 入库（`destaudit`）按链路号一次查出 `{入口, 出口}`：链路不存在、入口不是上报的服务器、或 agent 没声明 `audit.hits.egress.v1` 却带了出口，这条命中丢弃并计入丢弃类型 `egress_unknown`（指标 `hits_egress_unknown`，计入命中记录的 `dropped_in_range`）；查询失败按其他数据库错误处理，整批作废。链路从不删除、入口出口永不改变，所以结果可信。
- `dest_hits` 增加 `egress_panel_id`（0 = 从本服务器直出，也是已有行的值），列入主键，并有索引 `(egress_panel_id, hour_ms)`。升级时由 4.2 迁移重建表（见 `schema_upgrade_v4_2.go`）。管理接口 `GET /dest/hits` 接受 `exit_panel_id`（0 合法，不带表示不筛选）和 `group_by=exit`。`exit_panel_id` 只出现在未分组的行和 `group_by=exit` 的行上，`site`、`user`、`policy` 分组的行不带它（0 会被误读成“直出”）。

## 8. 规则（不变量）

1. 用户流量只在身份终结的那一跳计配额，另一跳记为链路流量。
2. 托管线路只在中转服务器确认当前转发后发布；隧道节点只在两侧都确认当前隧道后发布。失效时撤下，不回退直连或直出。
3. 转发和隧道入站不进入策略路由，只去固定去向。
4. 没有托管线路和隧道的服务器，配置字节、策略和编译产物与以前相同。

## 9. 来源 IP

透传时 B 只看到 A，基于 IP 的限制对经此线路的连接不生效，界面已标明。

**保留来源推迟到后续阶段（原定第 3 期）。** 现在基于 IP 的限制只观察、不执行（`IPShadow`），保留来源也不会让任何限制真正生效，所以先不做。

可选的“保留来源”（后续阶段）：仅两端都是 Xray 时可用，默认关闭，B 为该线路单独开影子端口接收 PROXY 头。依据是以下实测结论：

- sing-box 已移除 PROXY 协议，而且 `check` 能通过、启动才失败；
- 开启后同一端口上的直连会断；
- PROXY 头可被持有凭据的人伪造。

## 10. 多跳（预留）

`境内入口 → 境外中转 → 落地` 暂不支持，第 2 期的隧道结构为它预留位置，启用时需要成环检测和跳数上限。

## 11. 分期

1. **透传**（已实现）。
2. **隧道**（已实现）：两种隧道协议，加按出口的策略编译。
3. **审计出口维度 + sing-box 计量**（已实现）：命中记录出口服务器（`AuditEgress`，仅 Xray）；sing-box 转发与隧道也计量。
4. 透传保留来源（原第 3 期，推迟：IP 限制目前只观察、不执行）。
5. 链路质量自测、按目标分流、多跳、按线路设流量倍率。

发布顺序：Protocol 打标签 → Node 换正式依赖并发布 → PSP 换正式依赖。

## 12. 链路质量自测与压缩同步（4.3，开发分支）

**自测（`transit.probe.v1`）**

- 只向声明了该能力、且持有出口链路（`LinksOut`）或转发的服务器下发 `Transit.Probe`；没有声明的 agent 收到的配置与以前逐字节相同。
- 设置（管理员，`GET/PUT /api/admin/transit/probe-settings`）：开关（默认开）、间隔（60 秒，30–3600）、超时（5000 毫秒，500–10000）、探测地址（默认 `https://www.gstatic.com/generate_204`，http/https，端口 1–65535；**留空表示只测传输**：不经隧道抓取，不下发 `link_url`，没有 e2e 结果，芯片显示传输的数字）、撤下开关（默认关）、连续失败 N 次撤下（3）、连续正常 N 次恢复（3）。越界一律拒绝，不静默修正。
- 转发探测方法：默认 `tcp`；落地监听是纯 UDP（Hysteria2、TUIC）时用 `quic`；转发是 SNI 共用端口的路由目标时用 `tls`（见第 13 节；协议规定这种转发不能用 `tcp`，决定在 `linkprobe.Method`，由同步服务在发出前套用）。
- 入库只收下发配置里的对象，且只收对的一侧：`LinksOut` 的 `e2e`／`transport`、转发的 `forward`；其余丢弃。状态表 `transit_probe_state`。
- 一个窗口：全部失败（且至少 3 次尝试）为 `down`，失败率不低于 20% 为 `degraded`，其余 `ok`；没有尝试或结果过期（超过 3 个上报间隔，取探测间隔与全量上报周期中较大者）为 `unknown`。
- 撤下：只在撤下开关打开时，连续 N 个 `down` 窗口置位、连续 M 个 `ok` 窗口清除。只数**新**窗口：内容（尝试、失败、RTT、最近成功、最近错误）变了算新窗口；内容不变（一直中断的链路每次都一样）则隔一个探测间隔才算一个。重复上报（同一 agent 时间戳且内容相同）整条忽略，agent 时钟回拨或跳到未来不会卡住状态。结果过期后整段历史作废，从新窗口重新判断；`unknown` 永不撤下并清除标记。关掉探测或撤下开关会立即清除所有撤下标记，读取时也只在开关打开时才认标记。被撤下的托管线路（`RelayLine.Publishable()`）或隧道节点（默认出口的链路，`withoutUnreadyEgress`）从订阅中去掉，永不回退直连。`health.go` 不变。
- 用户页 `relay_statuses` 只带粗略质量（ok／degraded／down）和中位 RTT。

**压缩同步（`sync.gzip.v1`）**

- `/v1/node/sync` 只接受声明过该能力的 agent 的 gzip 请求（其余带 `Content-Encoding` 的请求为 415）；线上 16 MiB、解压后 64 MiB，先读完线上字节（受 16 MiB 限制），再取解压槽，只在解压时占用；解压并发由信号量限制为 4，同一 agent 同时只解一份；等不到槽返回 503（带 `Retry-After`，agent 保持状态、下次轮询重发）。对声明了该能力的 agent，所有响应带 `Vary: Accept-Encoding`。 agent 同时接受 gzip 时，面板可发送解压后超过 16 MiB 的名单；响应仍受 16 MiB 线上和 64 MiB 解压上限约束。大响应优先发送配置和名单，任务留到后续轮询。指标：`psp_node_sync_gzip_refused_total`（415）、`psp_node_sync_decode_busy_total`（503）、`psp_node_sync_gzip_bytes_total`。
- 对声明了该能力的 agent，每个 2xx 响应带 `Accept-Encoding: gzip`；请求带 `Accept-Encoding: gzip` 时响应也压缩。没有该能力的 agent 行为不变。

## 13. SNI 共用端口（`transit.sni.v1`，4.3，开发分支）

一个 TCP 端口按 TLS 握手里的 SNI 分给多个用途：Node 读取每个连接的 ClientHello（不解密），把连接交给对应的监听器、中转线路或外部伪装站点。只有 Xray 能做到。

**规则（不变量）**

1. **设置只作用于它所设在的那一项**：共用端口、每个监听器的回环端口、每条路由的 SNI、默认站点，都是管理员保存的值。自动值只是编辑器里的预填（按钮“随机生成”），发送时不会改写任何一项。
2. **任意 TCP 端口都能共用**（默认 443）；一台服务器可以有多个共用端口，最多 16 个（协议上限），每个端口至多一个前置。
3. **只有 Node 能承载的监听器能放在后面**，规则与 Node 的 `frontUnfit` 一致：传输为空／`tcp`／`raw`，安全层为 tls 或 reality，且自己不接收 PROXY 头（`sockopt`、`rawSettings`、`tcpSettings` 的 `acceptProxyProtocol`，因为前置会再写一个）。PSP 比 Node 更严的一点：只接受 VLESS／VMess／Trojan（这些协议的客户端才会发订阅渲染出来的服务器名）；没有服务器名（REALITY 的 `serverNames` 为空、TLS 的 `serverName` 为空）的监听器不能前置，因为没有可匹配的 SNI。监听器 JSON 按精确键名读取（与 Node／Xray 一致），大小写不同的重复键不会让面板比 Node 更宽松。WebSocket／gRPC／XHTTP、SS-2022、Hysteria2、TUIC 等保持自己的端口，保存时拒绝并说明原因。
4. **只发给 Xray，且是真的在跑 Xray**：agent 声明了 `transit.sni.v1`、期望引擎是 Xray、并且本次报告的引擎是 Xray 才下发 `Transit.Fronts`；其他服务器的配置字节与以前相同，界面显示“SNI 共用端口需要 Xray”并禁用，已保存的前置显示为“未生效”并写出原因。声明缺失会让节点把已移到回环端口的监听器丢掉，所以这是必须的门。
5. **没有前置时配置字节不变**：`Fronts` 为 `omitempty`，同步服务在没有任何前置时一字不改（测试逐字节对比整份配置）。
6. **冲突阻止保存并指名**：同一 SNI 在一个前置里出现两次、端口已被监听器／转发／隧道端口／另一个前置或回环端口占用、回环端口落在 Node 内部探测范围 `127.0.0.1:31000-31999` 或 Node 自留的 `127.0.0.1:10085`（核心 API），保存被拒绝，信息里写出冲突的那个对象。端口占用视图也列出这些。 支持上报端口的 Node 还会列出最近一次上报的实际探测监听器及其链路；观测过期后移除该条目。
7. **路由名必须是客户端真会发的名字**：去往监听器的路由，名称必须是该监听器自己的 REALITY `serverNames`／TLS `serverName`，并且到它的路由合起来必须**包含订阅给它的客户端的那个名字**（REALITY 的第一个 `serverNames`，按写入顺序；TLS 的 `serverName`），其余名字可以多；去往中转线路的路由同理：名称是落地节点的 SNI（托管线路本来就不能覆盖 SNI，订阅里渲染的就是落地的第一个名称），必须包含它，且落地必须是 TCP 上的 TLS／REALITY 监听器，UDP 或无 TLS 的落地不能走共用端口，也绝不会被静默改成只 TCP。节点保存也受此约束：改掉被路由引用的名称（包括调换第一个名称使订阅渲染的名字不在路由里）、传输、协议，会被拒绝并指出前置和路由。
8. **默认去向是外部站点**（`FrontTarget.External`）：选定、随机生成或手填。PSP 拒绝等于本服务器自己公网地址（或解析到它）且端口等于前置端口的默认站点，因为连接会绕回前置；手填的名称与服务器自己的任一地址（观察到的地址、节点地址）逐字相同（不分大小写、忽略结尾的点）也拒绝，即使 DNS 解析失败。保存时的 DNS 并行解析，总预算 3 秒。
9. **会移动或停用东西的改动，是需要确认的单独动作**（409 `confirm_required`，写出受影响的对象）：把已占用该端口的监听器放到前置后面（用户重连一次）；监听器在节点保存时落到共用端口上（响应写出前置、它将用的 SNI 和回环端口，确认后在同一次保存里加入前置并审计 `transit_front_listener_joined`，绝不静默）；**监听器离开前置**——把前置后面的监听器改到别的端口，或删除它：先确认，确认后同一次操作把它和它的路由从前置里去掉（审计 `transit_front_listener_left`；前置后面只剩它时拒绝，请先删前置）；停用共用端口后面的监听器（它的 SNI 改去默认站点，允许，但先确认）；删除前置、改端口、去掉中转线路路由；把服务器的引擎切离 Xray（前置保留但不再下发）。在前置编辑器里直接去掉一个仍监听共用端口的监听器会被拒绝，请先改它自己的端口。
10. **前置不发时，后面的监听器不能撞同一个端口**：Node 不允许两个监听器绑同一个端口，整份配置会被拒绝。所以删除前置、改前置端口、把服务器切离 Xray——只要有两个及以上监听器共用这个端口——是**拒绝**而不是确认，信息点名这些监听器，要先把它们分别改到不同端口；只剩一个监听器时才允许（它回到自己的公网端口）。同步时对称处理（与 Node 的 `WithoutFront` 一致）：一个没有发出的前置（被撤下、没有能力、不是 Xray、协议拒绝……），如果它的监听器加上端口上其他启用的监听器多于一个，这些监听器这次就不下发，并为每个记一条问题（`front_withheld`，详情 `listener_unserved`，写明与谁同端口）；只有一个时回退到公网端口。被省掉的监听器同时不进名册，没有悬空引用。
11. **删除服务器会同时删除它的前置**（逐条审计）；孤儿前置（服务器已不存在）不再阻止任何中转线路或节点的编辑。
12. **同一台服务器上读后写的保存串行化**（按服务器 ID 的互斥锁，前置保存和会碰前置的节点保存共用一个服务实例），回环端口不会被并发保存分配两次。

**数据模型**

表 `transit_fronts`（`ID`、`PanelID`、`Port`、`Spec` JSON、时间戳），`(panel_id, port)` 唯一；前置的线上键是 `fnt_<id>`。`Spec` 是 `domain.FrontSpec`：

- `Listeners`：`{node_id, loopback_port}`——监听器保留它公网端口的配置，节点把它绑到 `127.0.0.1:loopback_port`；
- `Routes`：`{server_names, target}`，名称小写、精确匹配、排序；目标是 `listener`（`node_id`）或 `forward`（落地节点 `node_id` + 中转线路 `line_id`）；
- `Default`：`external`（`host`、`port`）。

升级：只多一张表，由 `autoMigrateCurrentSchema` 创建，没有数据要搬，所以 `schema_upgrade_v4_3.go` 里只记了一条说明；升级测试在 `transit_front_repo_test.go`（SQLite／MySQL／PostgreSQL 都跑）。

**编译（`service/front`）与下发**

- `PlanFor` 在 agent 没有能力或引擎不是 Xray 时返回空计划。否则把每个前置编成 `nodeprotocol.Front`：路由按首个名称排序，目标是中转线路的，用该线路的转发（`transit_forwards` 行 id）并把它的网络改成只 TCP。
- 不可达的目标（落地停用、线路已不在这个端口）只丢掉那条路由，不影响其余；监听器不在这台服务器的配置里、或没有路由再指向它，就把它留在公网端口；一个前置没有任何路由，整个不发。
- 同步服务把共用端口和回环端口当作已占用：不属于前置的转发或隧道在这些端口上照旧被撤下；属于前置的转发在前置端口上发出。最后整体过一遍 `ValidateTransit`，被协议拒绝就撤下全部前置和它们的转发（监听器留在公网端口），并记录日志。
- 前置后面的转发用 `tls` 探测（协议拒绝对它用 `tcp`）。
- 被停用的监听器不作为前置监听器下发（Node 会拒绝点名未服务监听器的前置），指向它的路由一并去掉，其余监听器照常；端口上有启用的监听器不在前置后面、或前置后面的监听器已不能被承载时，整个前置不发（否则 Node 拒绝整份配置）。
- 每个前置各自过协议校验（单独、再放进除前置外的其余配置里），所以只撤下有错的那个，别的对象（如隧道）的错误不会连累前置；通过的几个再一起校验一次，互相冲突才全部撤下；撤下前置时，为该服务器记一条问题 `front_withheld`（键为 `fnt_<id>`，详情写原因，出现在“节点问题”里），计数 `psp_fronts_withheld_total{reason}`，共用端口对话框和服务器行都会显示“未生效”。
- 保存时的协议校验是干跑，不写任何行（不为转发生成行 ID）。

**保存时校验（`service/front`、`service/node`）**

- 前置：服务器是 Node、引擎 Xray、已声明能力；端口 1–65535 且不在 Node 内部探测范围 `127.0.0.1:31000-31999`；监听器可前置、监听在这个端口、回环端口不与任何已用端口相同；每个被移动的监听器至少有一条路由；路由目标是已选的监听器，或在这个端口入口的托管中转线路；默认站点是外部站点；最后用协议的校验兜底。VLESS REALITY 链路的出口也可以作为路由目标，路由必须使用隧道已配置的服务器名。绑定后入口拨共享端口，独立端口仍保留供解除共享时使用。
- 节点保存：被前置使用的监听器不能改端口、不能改成 Node 承载不了的传输或协议、不能丢掉被路由引用的名称、不能删除；落在共用端口上的监听器会被提议加入前置（见规则 9）；也不能占用某个前置的回环端口；被路由引用的中转线路不能改端口、改入口或删除；中转线路可以进入共用端口（多条线路共享一个端口，靠 SNI 区分）。

**接口（adminGroup）**

`GET/POST /servers/:id/fronts`（GET 同时给出 `support`、`withheld`）、`PUT/DELETE /servers/:id/fronts/:fid`（`DELETE ?confirm=true`）、`GET /servers/:id/fronts/options`（候选监听器及不能前置的原因、候选中转线路）、`GET /servers/:id/fronts/suggest?what=loopback|camouflage`（只读的预填）、`GET /servers/:id/ports`（端口占用）。拒绝返回 `code` 和 `params`，界面按 `code` 写自己的文案。写入审计为 `transit_front_created／updated／deleted`（带前后内容），外加通用的请求审计。

**端口占用视图**（服务器页的“共用端口（SNI）”→“端口占用”）：只读，列出这台服务器用到的每个端口——监听器、中转线路（未被路由选中的标出）、隧道端口、每个共用端口及其后面的 `SNI → 去向` 与默认站点、前置的回环端口、Node 内部探测范围 `127.0.0.1:31000-31999`。

**界面说明（ⓘ）**：什么是 SNI 共用、客户端不能把 ClientHello 拆到多个 TLS 记录里、纯 HTTP 探测要等约 1 秒才到默认站点、监听器会被移到回环端口且用户重连一次。

**其他保存路径**：新建时不会把会加入前置的创建放进重试队列（失败就返回错误，由管理员重试，否则排队的创建会在没有加入的情况下落在共用端口上）；加入前置时不再对已保存的默认站点做第二次 DNS 校验；加入失败（竞态或故障）时节点已保存，同步会按上面的规则撤下会撞端口的监听器并记问题。同一台服务器的锁在新建、导入、编辑、停用、删除、分离时都先于任何读取取得，键按升序取，不会交叉死锁。

**监听器在两个共用端口之间换位**（A 的端口改到 B 的端口）：一次确认同时写出离开 A（路由改去 A 的默认站点）和加入 B（SNI、回环端口），确认后同一次保存里先离开再加入，两条都审计；任一步成功后即使后面失败也会写审计。只缩小前置的操作（监听器离开、删除或分离节点、只删路由的编辑、删除前置）不受“服务器必须能跑前置”的门限制，所以服务器切到 sing-box 或丢了能力之后，有多个监听器的前置仍能被清空；任何新增或改动仍需要门。启用前置后面的一个已停用监听器，而该前置没有下发、端口上还有别的启用监听器时，先 409 确认（它们都会保持停止，写出前置未下发的原因）。

**已接受的限制**：加入／离开和节点保存不在同一个事务里，中途失败靠同步时的安全网（撤下会撞端口的监听器并记问题）兜底；排队执行的旧式创建和采纳（Adopt）同样靠这个安全网；被撤下的监听器仍会出现在订阅里（订阅渲染不看下发状态），由可见的问题提示。

**未做／已知限制**

- 前置自身的收敛状态（`fnt_<id>` 的 config 对象）暂不存、不在界面显示；其目标转发的确认照旧决定线路是否发布。
- 默认站点的域名只在保存时解析一次；以后它改成解析到本机，不会重新检查。

## 14. 按目标分流（`transit.route.v1`，4.3，开发分支）

一个节点（入口服务器上的一个监听器）原本只有一个出口：本机，或它的 `EgressPanelID` 指定的那条隧道（**默认出口**）。按目标分流让管理员给节点写一串**有序的规则**：目标命中某条规则，就改从那条规则指定的出口出去（另一台 PN 服务器，或 `local`），都不命中仍走默认出口。例如“流媒体走东京、其余走本机”。

**规则（不变量）**

1. **设置只作用于它所设在的那一项**：每条规则的位置、匹配、出口都是管理员保存的值；目录列表（含 geosite 类列表）在发送时才展开成字面条目，保存的规则从不被改写。
2. **默认出口不变**：没有规则时，配置和策略与以前**逐字节相同**（`Transit.Routes` 为 `omitempty`，同步服务在没有任何规则时一字不改；策略编译只在有分流的监听器上改变，且保存的 digest、编译缓存键都有固定值的测试）。
3. **`local` 的意思**：从这个节点自己的服务器出去，**不看**默认出口。它不是“没有规则”。
4. **只发给声明了 `transit.route.v1` 和 `transit.link.v1` 的 agent，而且绝不在没有规则的情况下发监听器**：不声明的 agent 会忽略这个字段，监听器照常运行，所有目标都送进默认出口且没有任何报错。所以对这样的服务器，**有规则的节点这次不下发（监听器不进配置），同时不出现在订阅里**（`transit_routes.withheld = no_capability`，`Node.RoutesWithheld`，`EgressPublishable` 为假），并记问题 `routes_not_sent`（详情 `no_capability: …`）；服务器升级后下一次同步恢复，或清空规则后恢复。保存时对这样的服务器拒绝，并写出原因；清空规则永远允许。节点不能换服务器（没有移动操作），所以不存在“把有规则的节点挪到不支持的服务器”这条路径。界面在不支持时整段禁用并写出原因。
5. **每个出口都需要一条隧道**：保存规则时为每台出口服务器建立入口服务器 → 出口服务器的隧道（`transit.Service.EnsureLink`，与默认出口的隧道同一套分配：端口、REALITY 伪装站点、两种协议的凭据），管理员能在服务器的隧道列表里看到、改地址和协议。同一对服务器只有一条隧道：默认出口和规则共用它。入口只在声明了 `transit.route.v1` 时才拿到规则用的出站一半；出口那一半不看入口声明什么（隧道在入口能用时就已就绪）。被停用的节点和指向本机的规则不建隧道。
6. **就绪只看默认出口的隧道**（owner 决定 2）：规则出口的隧道断了只告警（规则里的链路状态、探测质量），**不会**让节点从订阅里消失，也**绝不**回退到默认出口（目标连不上就是连不上，不会泄漏到本机）。节点是否发布仍只由 `EgressPublishable` / `EgressWithheld`（默认出口）决定。
7. **规则发不出去时，整个监听器这次不下发**，而不是丢掉这条规则：规则点名的隧道出站半边这次没有发出（出口没有地址、隧道被拒），或服务器已被删除、规则过不了协议校验、整台服务器的规则超过线上上限，若只把规则丢掉，这些目标就会走默认出口。记问题 `route_listener_withheld`（详情 `no_link`／`target_gone`／`contract_refused`／`too_many_entries`）。保存时能预见的情形（出口从未上报因而没有地址）在保存时就拒绝。这与前置的 `listener_unserved` 同一机制，并且**在规划共用端口和隧道之前先决定**（`route.Service.Early`，用已存的隧道和“能否拨通”判断；同步里随后的 `PlanFor` 用真实隧道再把关）：被撤下的监听器就像不存在，会连同它的路由从所在的前置里掉出来，其余监听器仍留在前置后面，不会因为前置点名了一个不在配置里的监听器而被 Node 整个拒绝（测试 `TestARouteWithheldListenerDropsOutOfItsFront`）。被撤下的节点同样不进订阅（`routes` 表的 `withheld` 记原因，状态变化时刷新订阅缓存）；规则恢复可发送后下一次同步解除。
8. **正则**：规则里手写 `regexp:` 保存被拒绝（`regexp_in_route`，写出规则和条目）；列表里的 `regexp:` 条目不进规则，保存时警告、状态里列出条数、同步时记问题 `route_regexp_skipped`。原因：正则无法与按出口分段后的访问策略相交（`protocol.IntersectDestinations`）。
9. **列表没就绪**（没下载、国家库缺失）或展开后为空：该列表那一部分被跳过并说明（`route_skipped`／警告）；规则**只剩端口或网络**而本应有地址的，整条规则不发送，端口不会代替缺失的地址（与访问策略同一规则）。被路由使用的列表不能删除（409 `dest_list_in_use`，`used_by` 里 `kind=route`），列表页的“被谁使用”也列出它；这个检查在删除列表的事务里做（`DeleteUnused` 读 `transit_routes`，与路由写入用同一把状态锁，保存路由时也在锁内确认所点名的列表还在），不会有“检查后被抢先”的空隙。**编辑**被路由使用的列表，若会让它对路由什么都不剩（空、只剩 regexp、引用的 geosite／GeoIP 数据不可用），先 409 `dest_list_route_impact`（写出节点，并说明这些目标之后会走各节点的默认出口），加 `?confirm_routes=true` 才执行（与 `ErrListNotReady` 同一风格；编辑器会弹确认）。**自动刷新（geosite／GeoIP 版本、远程列表拉取）不能弹确认，也不能把这些目标改走默认出口**：列表给不出路由能用的东西（空、只剩 regexp、没就绪、数据不可用）时，路由继续用该列表**最近一次有内容的展开**（表 `transit_route_lists`，每个列表一行，条目按行存成字节，列表有内容的同步里写入、内容变了才写；规则仍在，只是用“上一次好的”），并记问题 `route_skipped`（详情写“仍在使用上一次的列表”）和编辑器里的 `list_last_good` 提示；只有管理员确认的编辑（`?confirm_routes=true`）才会让路由真的丢掉这些目标（确认时 `RouteUses.Forget` 清掉上一次好的内容）。从没有过好内容的列表仍按原样跳过。展开列表时出现的其它错误（读库、解码失败，既不是空也不是数据缺失）同样不会让整台服务器的同步失败，也不会不带规则地发节点：有上一次好的内容就用它，没有就撤下该监听器（`list_error`，并记问题）。上一次好的内容只由**同步**写入（预览、保存干跑、状态页都不写），在没有任何路由再点名某个列表时（保存路由、删除节点、删除列表）一并清掉，避免过期内容在列表以后又被点名时冒出来；管理员确认的编辑只在编辑已经落库**之后**才让路由忘掉它，被拒绝或失败的编辑不改变路由。
10. **隧道的生命周期**：规则先存，再建隧道（存不下去就不留隧道），建隧道时取出口服务器的锁（与前置同一把，端口在出口上挑）；规则不再用某个出口、且入口服务器上没有节点把它当默认出口、也没有别的节点的规则用它，就删除这条隧道并释放出口上的端口。`LinksFor` 绝不为已删除的服务器建隧道。**删除被规则点名为出口的服务器被拒绝**（409 `server_used_by_routes`，写出节点和规则）；删除节点同样先判断：它的路由独占的隧道（没有别的节点默认出口或路由在用）随节点一起删除，用的是同一条规则、同一对服务器锁。取锁时先取入口和出口两台服务器的前置锁（编号小的在前，与节点保存同序，不会互相等待），**在锁里**才读节点列表判断“还有没有人用”，所以并发的默认出口绑定不会被删掉隧道。保存路由和删除节点还互相错开：`Replace` 在状态行锁里确认节点行仍然存在（否则 `ErrNotFound`，保存返回 404，不再建隧道；清空永远允许），不会留下没人删的孤儿行；删除和分离节点在读它的路由到清理完隧道这一段取路由服务的服务器锁（锁顺序：agent 锁 → 路由锁 → 服务器前置锁 → 状态行锁），所以清理不会漏掉并发保存刚加上的出口。这些锁不可重入，所以删除节点之后的隧道清理在调用者**放掉**自己的服务器锁之后才执行（分离节点 `DetachAndSync` 先在锁内删节点、解锁后才清理；测试用真实的前置服务和路由服务驱动分离和删除，带超时，死锁会让测试失败）；同步里为一对服务器**新建**隧道时同样取这两把锁，并在锁里重新读节点确认这对服务器还有人用，所以同步刚读完节点、保存恰好删掉最后一条规则和它的隧道时，隧道不会被同步重新建出来。数据库里写路由的几条路径（保存路由、上一次好的列表内容的写入与清除、删除节点）都先取状态行锁（`lockDestState`，顺序写在 `dest_state_repo.go` 的锁顺序说明里），再动 `transit_routes` 和 `transit_route_lists`；写入上一次好的列表内容只在仍有路由点名该列表时才写。隧道删除后，仍在缓冲里、点名这条已删隧道的命中记录会作为 `egress_unknown` 丢弃并计数（不会算错出口）。万一服务器行已不在（直接改库），该节点的监听器和订阅按 `target_gone` 撤下并记问题。隧道设置（协议、地址、REALITY）在规则编辑器里每个出口服务器一块，改协议或影响默认出口的节点前要确认（会重新握手，那些节点在两端重新应用前不进订阅）。

**数据模型**

表 `transit_routes`（`NodeID` 主键、`Body` 字节列里的 JSON、`Sent`／`Applied` 摘要、`Withheld` 原因、时间戳）。`Body` 是字节列而不是 TEXT：一条规则可以有几千个手写条目，超过 MySQL TEXT 的 64 KiB（测试用 5000 条在三种数据库上存取）。4.3 测试版建过 TEXT 列 `spec` 的库，由 `widenRouteSpec`（`schema_upgrade_v4_3.go`）在升级时逐行复制到 `body` 再删掉旧列，可重复执行。不放在 `nodes` 表的列里：节点行会被导入、轮询等多处整行写回，写回会冲掉规则，而发送／确认摘要每次同步都在写。`Body` 是有序的 `[]domain.DestRoute`：`id`（`r<n>`，稳定，重排不变，新规则取最大号加一）、`name`（可选）、`target`（`local` 或 `server` + `panel_id`）、`list_ids`、`domains`（只收 `domain:`／`full:`／`keyword:`）、`cidrs`、`ports`、`network`。保存时规范化：域名小写去重排序、CIDR 取网络地址、端口按协议的写法。线上 `RouteRule` 只有字面条目；`Exit` 是 `lnk_<id>` 或 `local`。

升级：只多一张表，由 `autoMigrateCurrentSchema` 创建，没有数据要搬，所以 `schema_upgrade_v4_3.go` 里只记了一条说明；升级测试在 `transit_route_repo_test.go`。删除节点同事务删除它的规则。

**编译与下发（`service/route`、`nodesync`）**

- `PlanFor`：对服务器配置里每个启用的、有规则的节点：展开列表（带缓存，缓存键是规则、各出口隧道键、各列表的内容摘要和就绪状态、GeoIP／geosite 版本）、排序去重、合并 CIDR；单个监听器单独过 `ValidateTransit`；整台服务器的域名（5 万）、CIDR（2 万）、规则数（1024）上限累计检查。规则按列表顺序下发，`Transit.Routes` 按监听器键排序。
- 前置：被前置移到回环端口的监听器，规则照样有效——路由按监听器键 `lst_<id>`，不看绑定地址；同一次同步里被前置“未服务”而去掉的监听器，它的规则一并去掉。有测试。
- 发送摘要：同步在配置定稿后记下每个节点“这次发出的规则摘要”（没发出记空，同时清掉旧的确认），确认时：配置与服务器所持一致、且该监听器 `lst_<id>` 状态为 `applied`，才把摘要记为已确认；被拒绝或报告里缺失则撤回。**规则运行中 = 已发送摘要非空且等于已确认摘要。** 节点编辑器和 `GET /nodes/:id/routes` 显示“未发送／已发送待应用／运行中”和时间。Node 把规则编译失败记在这个监听器上（`ListenerError`），所以监听器的确认就是规则的确认。
- 隧道状态：每条规则的出口显示入口端、出口端各自是否已应用所发内容（`in_applied` 是出口端、`out_applied` 是入口端）、整条是否就绪、探测质量（`transit_probe_state` 中入口服务器该链路的行）。

**访问策略按出口分开（`DestinationRule.Exits`）**

- 作用域为“服务器”的策略（`panels`）本来就“跟着出口走”。有分流的监听器上，一个监听器有多个出口：每个出口属于哪台服务器就各自判断。该监听器所有出口都在范围内，规则不带 `Exits`；只有部分出口在范围内，生成一份**只对这些出口生效**的拷贝（`Exits` 为排序后的链路键，`Inbounds` 显式列出监听器）；一个出口都不在范围内，这个监听器不受此规则约束。落在同一组出口的监听器共用一份拷贝，拷贝的规则 ID 取该策略下一个空闲的 `x` 后缀，命中记录和风险信号照常归到原策略。
- 没有分流的节点：`assemble` 走原来的路径，策略 digest 和编译缓存键与升级前相同（测试里固定了值，值取自升级前的提交）；只有有分流的监听器才在编译缓存键里多写 `rt…`。
- 上一份已应用的策略（降级回退）按 `covered` 收窄：一条规则只保留在它的作用域仍然通过它所取的每个出口覆盖的监听器上，只会放宽。
- 命中记录带出口（`AuditEgress`）：除了有默认出口隧道的服务器，只要有监听器的某条规则或默认出口走链路也打开（仅 Xray、并且声明 `audit.hits.egress.v1`）。
- Node 的每出口分段、Xray 对正则／关键字×关键字的“失败即闭合”：规则与线路的交集不能精确表示时，放行／只记录的那份拷贝**被丢掉**，拦截的那份**放宽成超集**，并记问题 `route_policy_approximate`（Node 报告）；PSP 保存时用同一个 `IntersectDestinations` 预先算出来并警告，点名监听器、规则和线路（owner 决定 4）。sing-box 用逻辑 AND，交集精确，没有这类警告。

**预算（保存时预先计算，与 Node 同口径）**

Node 对带分流的编译有硬上限：目的条目 `MaxRoutedEntries` = 1,000,000、核心规则 `MaxRoutedRules` = 20,000，超限的监听器被 Node 当成它自己的错误拒绝；编码后的配置另有 32 MiB（`MaxRoutedConfigBytes`）。保存规则时 PSP 先算同一个数（`service/route/budget.go`），对象是保存后的整台服务器（Node 的预算整份编译一个，按路由分组累计）：

- **是 Node 编译器的移植，不是估算**：Xray 对应 `xray/route.go` 的 `segmentRules`，sing-box 对应 `singbox/route.go` 的 `applyRoutes`／`sequence`／`shared`。逐条规则、逐个条目地和 Node 一样记账（`RouteBudget.Add`／`AddEntries`），包括：每个分段里每条适用的策略规则（Xray 拷贝它的匹配并与线路相交，用 `protocol.IntersectDestinations`，并先用 `intersectionBound` 提前拒绝；域名和地址分两条规则时各带一份 inbound、用户、源地址、协议）、豁免用户规则、尾点防护规则（策略里有带域名的拦截规则时每段一条）、`psp-usage` 用量规则（收集等级为 hits_and_usage 时每段一条）、线路的汇总规则、默认出口链路规则；sing-box 里一条规则的匹配达到 16 个条目（`sharedMatcherMinimum`）就整体写成一个共享规则集（按策略规则记一次，各段只记一个引用），有嗅探需求时分“请求域名”和“请求地址”两遍，线路自己的规则集每组各写一次（地址部分另写一份）。分组与 Node 相同（规则和默认出口完全相同的监听器合为一组，一组只算一次，按配置里监听器的顺序累计，超限处点名该组第一个监听器）。Node 开头那个便宜的 `EstimateRoutedEntries` 也同样移植，因为 Node 会在它超限时先拒绝（它常比实际计数大）。
- **与 Node 的数字逐一对照**：`internal/service/route/testdata/routebudget.json` 是 9 组夹具（Xray 的 hits／hits+usage／豁免与按用户的规则／关键字与正则／on_demand 解析、两个分组与默认出口隧道；sing-box 的小匹配、大共享匹配与两个分组、不需要嗅探、豁免加尾点防护加用量），期望值由 Node 自己的编译器跑出来（`passwall-node` 的 `feat/4.3-transit`，提交 `1c030bd`，协议 v0.9.0-rc.1；在 Node 的临时副本里给 `RouteBudget` 加了读数方法，Node 仓库本身没动）。`TestBudgetEqualsTheNodesCountOnTheNodesOwnFixtures` 要求 PSP 在同样的策略、名册、线路上给出同样的条目数和规则数；任何一边改动使数字移动都会失败。改了 Node 的编译器后要重跑夹具更新期望值。
- **超过硬上限：拒绝保存**（`over_budget`，参数带监听器、哪个上限、已用和上限），因为 Node 会拒绝这个监听器。已经超限的监听器若本次保存不是让它变差，不拦截，只警告。**达到上限的一半：警告**（`budget_near_limit`）。
- **32 MiB 的配置字节**：PSP 看不到 Node 编出来的字节，所以估算整台服务器（名册每个客户端 400 字节、每个监听器 4 KiB、策略和路由条目的文本长度加固定开销，偏高估），**达到 75% 起警告**，写出服务器名，**不拒绝**；超限由 Node 拒绝并在节点问题里显示。
- 被计的策略是保存时“会发给这台服务器的那一份”（`destpolicy.PlanPolicy`，只读、不改任何投递状态；做了嗅探限制和 resolve 收敛，没有做超限降级等针对投递状态的处理）。编辑器显示预算条（条目、规则，字节为整服务器估算，写明按哪个引擎算）。

**接口（adminGroup）**

`GET /nodes/:id/routes`（路由、各线路的链路状态和条目数、默认出口、已发送／运行中、警告、预算）、`PUT /nodes/:id/routes`（整体替换，返回保存后的状态和这次保存的警告）、`POST /nodes/:id/routes/check`（干跑：校验、预算、警告，什么都不写，也不建隧道，不审计；登记在 `readOnlyPreviewRoutes`）。拒绝返回 `code` 和 `params`。写入审计 `transit_routes_updated`（前后内容）。

**界面（节点编辑器“按目标分流”）**：有序的规则行（上移／下移、增删）；每行：名称、列表选择、手写条目、CIDR、端口、网络、出口（可搜索的服务器列表 + “本机直出”）；每行显示出口隧道状态（入口端／出口端、质量）、条目数、是否已发送、列表跳过说明；顶部显示默认出口及其隧道、已发送／运行中；保存前干跑（防抖）显示警告和预算；不支持时整段禁用并写出原因。ⓘ 说明：什么是按目标分流、默认出口与规则、`local` 的含义、Xray 的限制和正则处理、出口断了的行为。

**未做／已知限制**

- 策略测试页不知道分流：它用不带出口的匹配，对带 `Exits` 的规则只给出保守结果（协议里的 `MatchRouted` 已就绪，页面还没接）。
- 同步时不再重算预算：保存时通过，之后访问策略变大使该监听器超限，由 Node 拒绝并在节点问题里显示，PSP 不提前撤下。
- 预算里的字节数是整台服务器的偏高估算，只警告。
- “上一次好的列表”只在这台面板里（重启不丢，存在 `transit_route_lists`）；刷新后列表有了不同的、仍可用的内容就按新内容走，不会保留旧的。

## 15. 隧道模式线路（“加密隧道”，4.3，开发分支）

入口服务器 E 上给落地节点 L 的一条线路，有两种承载方式，在节点编辑器的线路区按线路切换（ⓘ 说明）：

| | 直接转发（默认，第 1 期） | 加密隧道 |
|---|---|---|
| E 做什么 | 原样转发用户连接到 L 的监听器 | 用 E 自己的监听器终结用户连接（自己的 REALITY），再经 E→L 所在服务器的隧道送到 L 的服务器，从那里出去 |
| 加密 | 落地自己的加密，端到端 | 用户到 E 一层，E 到 L 的服务器再一层 |
| E 的网络看到 | L 的指纹 | 只看到 E 自己的指纹 |
| 开销 | 最低 | 略多 |

**规则（不变量）**

1. **子监听器是一个普通节点行**，只是带标记：`nodes.parent_node_id`（L）、`nodes.parent_line_id`（线路）。同步、名册、前置、端口、出口隧道及其就绪、探测、按目标分流，对它和对任何监听器完全一样，所以没有第二套机制。它不进节点列表（`ListPaged` 排除，`node.Service.List` 过滤）、不进分组和订阅（`ListEnabled` 排除）；管理员在 L 的线路下看到它，并有指向它设置的链接（节点编辑器按 id 打开，页首说明它属于哪条线路、名称/地址/出口/倍率跟随线路）。
2. **线路**：`RelayLine.Mode = "tunnel"`、`TunnelNodeID`（服务端维护）、`EntryPanelID = E`。`Managed()` 对隧道线路为假，所以转发的一整套（入口端口、`fwd_` 键、确认、转发探测、前置的转发目标）都不碰它；`Gated()` 为真，发布需要 `ManagedReady`。**直接转发的线路一字不变**，已有线路全部保持直接转发，没有迁移。
3. **监听器的设置全部存在监听器上，可见可改**：端口、REALITY 的 SNI／目标／密钥／short id、协议、传输。创建时预填（见下），之后不再由任何东西推导。编辑器里“随机生成”只是预填（端口取 E 上空闲端口，SNI／目标取伪装站点，密钥取新的 X25519 对和 short id），保存时按所填值存。
4. **创建时的协议**：落地是 REALITY 的 VLESS／VMess／Trojan 时复制它（协议、设置、传输、嗅探、flow），**名称和所有密钥都换成新的**（SNI／目标、私钥、公钥、short id、ML-DSA 种子和验证串）；落地不是 REALITY（TLS 的证书属于落地主机，SS-2022、Hysteria2、TUIC 的服务器密钥不应出现在两台服务器上）时建默认的 VLESS + REALITY + Vision 监听器，管理员再改。端口在 20000–59999 里挑 E 上空闲的，冲突阻止保存并点名占用者（监听器、转发线路、进入 E 的隧道、前置的回环端口、Node 的内部端口；落在共用端口上走前置的加入确认）。
5. **默认出口 = L 的服务器**：子监听器的 `EgressPanelID = L.PanelID`，E→L 所在服务器的隧道沿用第 2 期的整套（创建线路时 `EnsureLink`，同步里也会建；协议、地址、REALITY 伪装站点在服务器的隧道列表里改）。L 的服务器终结隧道，用户流量从那里出去，受那台服务器的访问策略约束，与 L 自己的用户一样。**按目标分流按监听器设置，子监听器不隐式继承 L 的任何规则**；界面在线路卡片上这样写，并链到监听器设置里的“按目标分流”。
6. **用户和身份**：用户就是 L 的用户。身份是每条线路一个（ADR 0043）：该用户在 (L, 线路) 上的派生 UUID，行属于 E 的服务器（`PanelID = E`），`NodeID/LineID = (L, 线路)`，挂在子监听器上（`psp_client_inbounds.node_id` = 子监听器）；唯一性在子监听器上检查。身份行的唯一键是 `(user, panel, node, line)`（`uk_psp_client_line_panel`，升级里由 `widenClientLineKey` 替换旧键 `(user, node, line)`，存量数据原样保留）：切换模式时身份从一台服务器搬到另一台，旧服务器上的行先解除挂接、保留计数，等流量轮询记完账后删除，换回时复用这一行，所以不会撞唯一键。`clientplan.TunnelLineCreds` 按服务器列出隧道线路，`clientprov` 在 E 的服务器上建行；移除线路时行与普通被去掉的线路一样先解除挂接、保留计数，由流量轮询在记完账后删除。
7. **订阅里是 L 的一条线路**：和其他中转线路同一个位置，用线路自己的名称／区域／标签，**从不作为独立节点出现**。拨的地址是线路的 `Address`，端口、REALITY 的 SNI／公钥／short id、flow 取子监听器，凭据取该线路的已应用身份（`renderItem.listener()`）。**没有回退**：隧道线路在自己的身份未应用时不渲染（监听器不认直连身份）。
8. **发布条件**（`domain.TunnelRunning`，在读取节点时填 `ManagedReady`）：线路和 L 都启用、监听器启用且已应用（`ConfigSyncState = synced`）、监听器的出口隧道两端都确认当前内容且监听器在入口已下发的绑定里、没有因分流发不出（`RoutesWithheld`）、且探测状态没有撤下（探测撤下标记取该隧道的）。任何一项不满足就不发布，不回退直连。
9. **计费**：线路自己的倍率（`RelayLine.TrafficFactorMilli`），按行入账，与第 3 步多倍率一致：行的 `LineKey` 是 (L, 线路)，记账读线路倍率。E 的服务器的节点集里没有 L，所以子监听器带一份线路倍率的副本（`TrafficFactorMilli`，节点服务在改倍率、保存线路、批量设置倍率时同步），`domain.LineFactors` 让它代表该线路（节点集里有 L 时以 L 的值为准）。额度下发、待入账用量、流量轮询都走这一个函数。隧道的出入口流量仍是链路流量，不计入用户。
10. **冲突、确认、不静默**：
    - 保存时的冲突（端口、前置上的 SNI／回环端口）阻止保存并点名对象；
    - **创建**一条隧道线路（新增线路选“加密隧道”）就是创建监听器的动作，不另问；
    - **切换模式**（直接转发 ↔ 加密隧道）、**删除隧道线路**、**删除落地**都是确认动作（409 `confirm_required`，`params.kind = "tunnel"`，`action`、`creates`、`removes`（节点 id、名称、端口、所在共用端口）、`refresh_needed`），写明会创建和删除什么、订阅者需要刷新订阅；监听器离开共用端口一并列出，同一次确认里办完；
    - 已有线路的模式只能通过 `POST /nodes/:id/lines/:line_id/mode` 改，节点保存里改模式被拒绝；
    - 停用落地停用它的全部子监听器，启用落地只启用线路本身启用的那些（被共用端口挡着需要确认的，先于任何改动检查）；线路的启用开关同步到监听器；
    - 子监听器不能单独停用、删除、分离（指向线路）。
11. **前置**：子监听器是普通的 TLS／REALITY 监听器，可以像任何监听器一样放在 E 上的前置后面（仅 Xray）：加入／离开的确认、端口占用视图、前置路由编辑器都按监听器处理。端口占用视图和前置路由里它读作“<L> 的隧道线路 <线路名>”（`parent_node_id`／`parent_name`／`line_name`）。隧道线路本身通过 `listener` 目标共享入口端口。若要共享两台服务器之间的链路出口端口，则选择对应的 `link` 目标。指向隧道线路的 `forward` 目标被拒绝并说明应指向它的监听器。
12. **引擎**：入口是 Xray 或 sing-box 都行（两者都支持隧道）；SNI 共用仍只有 Xray。

**从落地同步**：`GET /nodes/:id/lines/:line_id/tunnel/sync` 预览差异（协议、flow、设置、传输、嗅探；私钥以 `***` 代替），`POST` 同一路径在 `confirm` 后重新复制落地的协议设置，**保留监听器自己的端口、SNI／目标、密钥、short id、监听地址**；落地不是 REALITY 时拒绝（监听器保持自己的设置）。

**数据模型**

- `nodes.parent_node_id`（默认 0，有索引）、`nodes.parent_line_id`（默认空）；`relays` JSON 里每条线路多 `Mode`、`TunnelNodeID`（`omitempty`）。运行时字段 `RelayLine.TunnelNode`、`ManagedReady`、`Probe`、`ProbeWithheld` 不入库，由 `attachTransitState` 在读取节点时填（监听器与节点一起读，走同样的出口／分流／探测装载）。
- 升级：只多两列和两个 JSON 字段，已有线路都是直接转发，没有数据要搬；`schema_upgrade_v4_3.go` 里只记了一条说明，升级测试在 `transit_tunnel_repo_test.go`（SQLite／MySQL／PostgreSQL 都跑）。

**接口（adminGroup）**

`POST /nodes/:id/lines/:line_id/mode`（`{mode: tunnel|forward, port, confirm}`）、`PUT /nodes/:id/lines/:line_id/tunnel`（端口、`server_name`、`target`、`short_id`、`private_key`、`public_key`、`fingerprint`，空表示不改）、`GET|POST /nodes/:id/lines/:line_id/tunnel/sync`；`PUT /nodes/:id/metadata`、`DELETE /nodes/:id`、`POST /nodes/:id/detach` 接受 `?confirm_tunnels=true`；`GET /servers/:id/fronts/suggest?what=port` 给出 E 上的空闲端口预填。节点详情里每条线路带 `mode`、`tunnel`（监听器的端口、名称、REALITY 设置——私钥只给管理员——、`applied`、`egress_ready`、探测质量、路由数）和 `running`。写入审计 `transit_tunnel_line_created／removed`、`transit_line_mode_switched`、`transit_tunnel_listener_updated／synced`（私钥只记“是否改过”）。

**界面（节点编辑器“线路”）**：每条由 PN 服务器承载的线路有模式开关（直接转发／加密隧道，ⓘ 说明两者区别：前者原样转发、落地加密端到端、最省；后者入口自己终结用户连接、用自己的 REALITY，在加密隧道里送到落地，对入口的网络隐藏落地指纹，略有开销）；切换弹确认并列出创建／删除的对象和“订阅者需要刷新”。隧道线路卡片显示监听器的端口、SNI、目标、short id、公钥／私钥（均可改，“随机生成”预填）、链路状态、探测质量芯片、应用状态，以及“从落地同步”（先显示差异、确认后执行）、指向监听器完整设置的链接和“按目标分流按监听器设置，不继承落地”的说明。

**补充规则（评审后）**

- **确认先于保存**：停用／启用落地或线路时，落在共用端口后面的监听器要的确认（停用会把它的名称送去默认站点，启用可能让同端口的监听器都停着）在写任何东西之前问；取消确认什么都不变（`tunnelEnabledRefusal`）。
- **REALITY 密钥对必须配对**：公钥必须是私钥推出的那个（x25519），否则保存被拒（任何保存监听器入站的路径都查）。编辑器里改私钥会推出并填上公钥（`POST /nodes/reality-public-key`），“随机生成”同时设置两者。
- **确认列出每个要开关的端口**：创建项带入口服务器上监听器的端口，以及落地服务器上隧道的端口（隧道已存在则复用，不新开）；删除项带入口上要关的端口。预览里的端口就是之后创建用的端口：监听器端口按线路记住，隧道端口由 `PlanLink` 预留，确认后的重试用同一个。
- **不会留下没人要的监听器**：删除线路／切回直接转发时先删监听器、再保存线路（保存中断只会留下“监听器不见了”的线路——不发布，再删一次即可）；新建时先建监听器、保存失败就撤销。仍然留下的孤儿监听器（线路已不在）会出现在该服务器的节点问题（`tunnel_listener_orphan`）和端口占用视图（标为孤儿，有“移除”），并且只有这种监听器允许单独删除；删除监听器会按节点的规则清理只有它的分流用到的隧道（锁放掉之后）。
- **删除服务器**：服务器上只剩隐藏监听器时，409 `server_has_nodes` 点名“<落地> 的隧道线路 <线路名>”，并说明去落地节点上移除这些线路。
- **监听地址和协议绑定不继承**：子监听器用默认监听地址（所有地址，可改），不复制落地的 `listen`／`allocate`／REALITY `xver`／`acceptProxyProtocol`；ML-DSA 种子和验证串置空，复制来的设置去掉 `clients`。“从落地同步”同样处理，差异和审计里的每个密钥（私钥、ML-DSA、客户端 id、密码）都以 `***` 代替。
- **来源地址与连接数限制**：隧道线路的连接在入口服务器上看到的是用户真实来源 IP，所以这些行和直连线路一样计入个人的 IP／位置统计、实时连接和风险／地理关注（`tunnelLineRows`：按落地的线路判断，转发线路的行仍不计）。同一个人的所有行是同一组地址、归到同一个用户，限制按人判断；节点收到的来源 IP 限制本来就是按人（`IPShadow` 按 subject，一人一条，不随线路数增加），目前只观察不执行（见第 9 节），所以线路不会把限制乘以线路数。
- **访问来源规则**：落地节点上设的来源规则（国家／IP）也作用于它的隧道监听器（线路属于落地，设置作用于所设的那一项）；分流规则仍按监听器各自设置，不继承。
- **不当作节点出现的地方**：规则集代理组检查器不列隐藏监听器；流量榜把子监听器的流量显示为“<落地> · 隧道线路 <线路名>”，节点数不计它；批量改倍率拒绝给监听器自己设倍率（倍率在线路上），线路倍率没能同步到监听器时返回错误，下一次同步还会记问题 `tunnel_factor_stale`。

- **并发与顺序**：保存线路、切换模式、批量改倍率先取落地服务器和各条隧道线路入口服务器的锁，**再**读存储的节点并以此为准规划（`lockAndLoad`；锁集合与重读结果不一致时用更大的集合重试），所以并发保存不会让监听器没人要。孤儿监听器的删除同样先锁入口和落地服务器、再判断是否孤儿；同步只在连续两次都看到“没有线路”时才报孤儿，不会把正在被保存创建的监听器当孤儿。
- **监听器建不出来就不排队**：隐藏监听器创建失败（服务器不可用、AddInbound 失败）直接返回错误并撤销整次保存，不入队，线路里也不会存下 id 为 0 的监听器。新建时已关闭的线路，其监听器在保存线路前就置为关闭（之后没有可失败的步骤）。保存失败撤销时，这次保存新建的隧道（没有别的监听器或分流在用）一并删掉。
- **确认带回它回答的清单**：每个隧道 409 都有 `params.plan`（列出的端口和种类的摘要）；确认的重发必须把它原样带回（请求体或查询参数 `confirm_plan`）。服务器按现在重新规划的结果比对，不一致就再给一个 409 和新清单，所以跨管理员、跨重启都成立，也不需要服务器记住上一次的预览。切回直接转发不指定端口时，转发沿用监听器自己的端口（清单里可见，可改），同一个请求每次规划出同一个端口。新建线路时隧道预留端口被占用会得到动作 `create_line` 的 409，列出新端口。
- **确认里的端口保持不变**：监听器端口按线路记住，隧道端口由 `PlanLink` 预留 10 分钟、所有其他隧道的分配都避开它，并检查共用端口和回环端口（`WithPortCheck`）；这些预留也出现在端口占用视图（`link_planned`）里，服务器上所有挑端口的地方（监听器、转发、`suggest?what=port`）都避开它；确认后的保存若发现带回的清单已不是现在规划的（被占用或预留过期），重新给出 409 并列出新端口，**绝不在确认背后换端口**（预留的端口在建隧道时被占用则整次保存撤销，错误 `ErrReservedPortTaken`）。切回直接转发的确认还列出在入口服务器上打开的转发端口（可以沿用刚删掉的监听器的端口：被删的监听器不算占用）。共用端口自己的 409 由请求里的 `confirm_front`（查询参数，切换模式和同步另有请求体字段）确认，编辑器按服务器的话问后重发。
- 隧道线路的 IP 统计只认入口服务器上的那一行（模式切换后留在别的服务器上的同线路旧行不算）。

**未做／已知限制**

- 新建节点向导的“入口”步骤可以同时配置隧道线路，见 §17。
- 子监听器的 `Region`／`Tags` 取落地节点的，不是线路的（线路标签只作订阅显示，ADR 0040）。
- 落地不是 REALITY 时子监听器用默认的 VLESS + REALITY + Vision，不复制其协议；“从落地同步”对这样的落地不可用。
- 加入共用端口和节点保存不在同一个事务里（第 13 节“已接受的限制”同样适用）。

## 16. CDN 线路（“CDN（如 Cloudflare）”，4.3，开发分支）

落地节点 L 上的第三种线路：客户端连 CDN，CDN 回源到 L 自己的监听器。没有入口服务器、没有转发、没有隧道。PSP 看不到 CDN，所以线路**随 L 一起发布**（`Publishable()` 只看启用开关，`Managed()`／`Gated()` 为假），**不做转发探测**（没有入口节点；节点健康检查对线路地址做的 TCP 可达检查照旧，只说明边缘能连上）。

**模型**：仍是 `RelayLine`，`Mode = "cdn"`、`EntryPanelID = 0`，新增 `Domain`（CDN 域名）。其余全部是已有字段，**按线路字面生效，管理员看得到、改得了每一个值**：

| 字段 | 含义 | 留空时 |
|---|---|---|
| `Domain` | CDN 代理的域名（必填，小写化；不接受 IP、端口、路径、通配符） | 拒绝保存 |
| `Address` | 客户端拨的地址：优选 IP 或域名 | 保存时填入域名 |
| `Port` | 客户端拨的端口 | 保存时填入 443 |
| `SNI` | 客户端发的 TLS 服务器名（CDN 按它路由） | 保存时填入域名 |
| `Host` | WS／HTTPUpgrade 的 Host，gRPC 的 authority | 保存时填入域名 |
| `ClientTLS` | 客户端到 CDN 是否用 TLS（与落地自己的 TLS 无关） | 保存时按端口填：CDN 的 HTTPS 端口开，HTTP 端口（80、8080、8880、2052、2082、2086、2095）关 |

留空补默认只发生在保存那一刻，补进去的值就是线路自己的值，之后不再由域名推导（改域名不会悄悄改它们；编辑器里改域名时，仍等于旧域名的地址／SNI／Host 会跟着变，一眼可见，改过的不动）。线路的名称、区域、标签、倍率（默认 1000）、身份与其他线路完全一样：身份是 (L, 线路) 的派生 UUID，行在 L 自己的监听器上（`clientplan.LineCredsFromNodes`，没有改动），倍率按行入账。

**落地必须能过 CDN**（`domain.CDNLandingProblem`，保存线路、创建节点、导入节点、**修改落地的入站配置**时都查，拒绝时点名节点和线路）：VLESS／VMess／Trojan + 传输 WS／gRPC／HTTPUpgrade，落地一般需要 TLS；**例外**：VLESS／VMess 的 WS／HTTPUpgrade 可以不带 TLS（Cloudflare 灵活模式，CDN 用明文 HTTP 回源，警告里写明这一跳不加密：VLESS 内容可读，VMess 仍加密载荷）。不带 TLS 的 Trojan 和 gRPC 仍拒绝；Trojan 的 `ClientTLS` 不能关。拒绝：REALITY、裸 TCP、Hysteria2／TUIC／SS／AnyTLS 等非 HTTP 协议、带 `xtls-rprx-vision` 流控的节点；检查按**这次保存之后的节点**判断（包括这次编辑里的流控，导入时在复制入站流控之后），线路详情按界面语言显示诊断原因；拒绝信息建议“在同一台落地服务器上另建一个 TLS + WS/gRPC 节点”。**XHTTP 暂不支持**：订阅渲染目前对任何客户端都不输出 XHTTP（Xray 服务端本身可以，但没有可用的客户端配置），所以不放行。线路的种类保存后不能变（CDN ↔ 转发／隧道都拒绝，删掉重加）；模式切换接口对 CDN 线路本来就拒绝（没有入口服务器）。

**警告而不拒绝**（`domain.CDNWarnings`，随节点详情的每条线路返回 `cdn_issues`，编辑器显示；保存后有“可能不通”的警告时再弹一次提示）：落地内联证书没有覆盖 CDN 域名（读得出证书才判断；证书是文件路径或没设置时只提示“无法检查”，源站 CA 证书另行配置的情况合法）；落地的 TLS serverName 不是该域名；落地端口不在 Cloudflare 的端口表里（落地有 TLS 看 HTTPS 表 443、2053、2083、2087、2096、8443，没有 TLS 看 HTTP 表 80、8080、8880、2052、2082、2086、2095），线路端口同理按 `ClientTLS` 选表；落地没有 TLS（回源明文）、客户端不用 TLS；落地的 Host（`wsSettings.host`／`headers.Host`、HTTPUpgrade 的 host）与线路的 Host 不同；线路端口不等于落地端口（要用源站规则改写）；SNI／Host 不是域名；落地允许不安全 TLS（对 CDN 线路无效）。Cloudflare 的 gRPC 端点要求 443、TLS 和 HTTP/2。gRPC 的 Host 与 SNI 不同时，也会提示 mihomo 和 sing-box 使用 SNI 作为 authority。

**订阅渲染**（`effectiveEndpoint`／`applyCDNStream`，Clash／mihomo、sing-box、URI 列表都走同一处）：拨 `Address:Port`；线路的 Host 是**所有设了 Host 的线路**（不只 CDN）的 WS／HTTPUpgrade Host 和 gRPC authority；路径／serviceName、ALPN 取落地的。客户端侧由线路自己的 `ClientTLS` 决定：开则带线路的 SNI 和落地的 TLS 指纹，**`allowInsecure` 恒为 false**（CDN 出示自己的证书，客户端必须验证），落地没有 TLS 时补一段 TLS 客户端设置；关则不输出 TLS。落地 Xray 的 `wsSettings.host` 也会读（`headers.Host` 优先）。**落地后来不再适合 CDN 时**（在面板外被改成 REALITY 等，或导入时就是），这条线路不渲染，节点同步记问题 `cdn_landing_unfit`（点名线路和原因）；没有本地快照时，渲染器检查实际取到的入站配置。无名称的 CDN 线路用域名作标签，不用优选 IP。随之补了两处原本缺的输出，对所有条目生效：HTTPUpgrade 传输（mihomo 用 `ws` + `v2ray-http-upgrade`，sing-box `httpupgrade`，URI `type=httpupgrade`）；mihomo 的 Trojan 在 ws／grpc 下补上 `network`（原先只有 `ws-opts` 而没有 `network`，客户端会当成裸 TCP）。gRPC 的 authority：VLESS／Trojan URI 用 `authority=`，VMess JSON 放在 `host`（`type` 为落地的 gRPC 模式 gun／multi，VLESS 的 `mode` 同）；mihomo 和 sing-box 的 gRPC 取 TLS SNI。

**接口**：`relays[]` 里 `mode: "cdn"`、`domain`；`address`、`port`、`sni`、`host` 可省略（见上表）。响应里每条 CDN 线路带 `domain`、`cdn_issues: [{code, warn, params}]`。没有新增列或表：线路在 `nodes.relays` 的 JSON 里，只多 `Mode: "cdn"` 和 `Domain`（`omitempty`），升级不需要迁移，旧版本留下的外部线路原样不动。

**界面**：节点编辑器“中转线路”每条线路的“入口”下拉里，在“外部入口”之后多一项“CDN（如 Cloudflare）”（保存后的线路种类不可改）。选中后这条线路显示：CDN 域名、端口（默认 443）、优选 IP／地址、SNI、Host／authority，页首说明“没有入口服务器，随节点发布，不做探测”，ⓘ 说明 Cloudflare 设置（橙色云代理、SSL 完全（严格）、WebSockets／gRPC 开启、允许的端口、证书走“证书”里的 Cloudflare DNS-01）。落地的检查结果按线路列在下面。CDN 域名必填。保存时为留空的字段填入默认值，已保存的地址、SNI、Host 和客户端 TLS 各自独立编辑。

**未做／已知限制**

- XHTTP（见上）；渲染器补上 XHTTP 之后，只需在 `CDNLandingProblem` 放行。
- 警告基于已保存的节点，编辑器里尚未保存的改动不会实时重算（保存后显示）。
- 证书检查只读内联证书（PSP 托管证书部署到节点后就是内联证书，会被检查）；文件路径或未设置时只提示“无法检查”。
- 不检查 Cloudflare 一侧的设置（PSP 没有它的凭据用途），只在 ⓘ 里列出。


## 17. 按来源校验线路身份（`transit.source_guard.v1`，4.3，开发分支）

直接转发（托管或外部）与 CDN 线路终止在落地监听器上，与直连共用它。为了让每个字节只能经过它身份对应的
线路（[ADR 0044](adr/0044-line-source-guard.md)），PSP 给每条这样的线路一组来源地址，落地按来源拒绝不符的连接。

1. **倍率类**：同一个落地监听器上，终止在它上面的线路（直连、托管/外部直接转发、CDN；隧道线路有自己的监听器，不算）
   按有效倍率分组（缺省 1000）。含直连倍率的那一类是**直连类**：其中的中转线路不需要来源。其余每一类是**计价类**，
   来源组 = 该类各线路有效来源的并集。
2. **来源组与约束**：`SourceSet` 的键按（监听器，倍率）确定，形如 `src_<落地节点>_f<倍率千分位>`，放在配置的 transit 段。
   计价类的客户端带 `allow_from` = 本类的键，**总是**带：来源未知或这一类被撤下时仍引用这个键但不下发来源组，
   Node 因此拒绝该客户端的全部连接（失败即关闭）。直连类的客户端（直连线路与同倍率的中转线路）带 `deny_from` = 该监听器上
   已知且非空的各计价类的键；一行挂在多个监听器上的旧行取各监听器的并集（最多 64 个，放不下则该客户端被禁用而不是少写）。
   隧道线路不带。
3. **来源**：托管转发 = 入口服务器的 `interface_addresses`（完整回报）+ PSP 看到的同步来源地址 + 线路的 `source_cidrs`；
   CDN = 线路的 `source_cidrs`，没有则用 Cloudflare 地址段；外部 = 线路的 `source_cidrs`。管理员填写的 CIDR 在所有保存路径
   （元数据、线路、创建向导、导入）统一规范化：拒绝主机位、IPv4 映射、过宽前缀（IPv4 短于 /8、IPv6 短于 /19）。
4. **可执行的监听器**：落地服务器的 agent 声明 `transit.source_guard.v1`，**并且**监听器的来源是连接本身的地址。核心会从
   客户端可控的头里取来源时不可执行：sing-box 任何传输（ws、httpupgrade、http/h2、grpc；只有纯 TCP，含 TLS/REALITY 可以）；
   Xray 的 `sockopt.trustedXForwardedFor` 非空，或流设置/入站设置里任意位置设了 `acceptProxyProtocol`（Passwall 前端加的
   PROXY 头不算）。不可执行的监听器适用“所有线路倍率相同”的规则。CDN 线路通常落在 ws/grpc/httpupgrade 上，所以在
   sing-box 落地上不能与直连定不同的价。
5. **Cloudflare 地址段**：内置快照（`internal/domain/cloudflare_builtin.go`，带日期）；每天从
   `https://www.cloudflare.com/ips-v4`、`/ips-v6` 拉取（普通 GET，不带标识部署的头，限时限大小），校验（规范前缀、
   5..500 条、两个地址族都在）后保存最后一次成功的结果；任何失败都沿用上次结果。系统设置里关闭自动拉取后使用内置快照，
   而不是上次拉取的结果。
6. **只发给声明能力的 Node**；其他 agent 的配置和名册与以前逐字节相同。来源组变化推进配置版本，客户端的约束变化推进名册版本。
7. **保存规则**（所有保存路径，含导入）：不能执行的监听器，所有线路倍率必须相同；能执行的监听器，两类的已知来源不得重叠
   （含 CDN 默认的 Cloudflare 段与直连类中转线路的来源），即“来自相同地址的线路必须使用相同倍率”；计价类最多 64 个，
   一类的来源并集最多 1024 条，不截断；倍率与直连不同的外部中转线路必须填来源地址。已保存的状态后来变成不合规
  （能力消失、Cloudflare 地址段变化造成重叠或超限）时不下发有问题的方案：撤下受影响的计价类线路（`source_guard_withheld`），
   它们的客户端保持失败即关闭。
8. **应用即发布**：计价类线路的身份只有在已应用的名册带着预期的约束、且已应用的配置带着它的来源组之后才记为已应用，
   之后订阅才会渲染它。
9. **渲染**：任何中转线路在自己的身份应用之前都不发布，不再借用直连身份。
10. **被拒绝的来源**：Node 在完整回报里上报，PSP 每个（来源组、监听器、地址）保留最新一条，每台服务器最多 1000 条、30 天；
    线路编辑里按类显示：地址不在任何一类的来源里是“未登记来源”，可一键加入该类某条有自己地址的线路（只改那条线路的来源，
    在节点保存的锁内完成）；CDN 默认线路不提供（加一个地址会替换整个默认）；地址已在某一类的来源里则是“身份用在了错误的线路上”，不提供加入。

## 18. 节点创建向导与线路表

创建步骤为落地、入口、出口和确认。落地默认 VLESS + REALITY + Vision，监听 443，打开时预填密钥和 Short ID。默认名称和地区来自所选服务器，管理员可以修改。服务器的地区和标签可在服务器设置中填写，入口选择器按这些字段分组，也可以搜索服务器名称、地区和标签。

入口支持直连、直接转发、加密隧道、外部入口和 CDN。向导内每台入口服务器可选一条线路。新入口预填地址、名称和端口，管理员可以调整；加密隧道还可以编辑入口监听器的绑定地址和 REALITY 名称。默认出口和按目标分流使用现有路由规则及校验。

确认页按服务器列出监听、转发和隧道端口。SNI 共用端口同时显示路由的服务器名以及监听器的回环端口，修改回环端口后需重新核对。预览会检查已分配端口、共用端口名称以及分流规则。创建时在服务器锁内重算计划并核对确认值，避免分配管理员未确认的端口。如创建过程失败，回滚这次新增的监听与转发路由，并清理未使用的新隧道。

节点页的「线路表」列出直连和每条附加线路的入口地址、出口、发布状态及倍率，可以搜索并跳到对应线路的编辑位置。
