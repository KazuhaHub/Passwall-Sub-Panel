# 连接限制：并发 IP 与设备数

> 状态：**已实现，实机验证（3X-UI 3.7.0 + xray-core 26.7.28）。**
> 关联：[ARCHITECTURE.md](ARCHITECTURE.md)、[inbound-ownership.md](inbound-ownership.md)、[3xui-compat.md](3xui-compat.md)、[data-plane-plan.md](data-plane-plan.md)。

## 1. 设计立场

**PSP 的领域模型是真相源，面板是兼容目标。**

字段按 PSP 想表达的意图命名和定义（`User.IPLimit` / `User.DeviceLimit`），**不跟任何面板的字段名或语义走**。各适配器把它翻译成自己面板能表达的部分，翻译不了的**通过 capability 显式声明缺口**——而不是静默不生效。

这条立场决定了下面几乎每个具体选择。

## 2. 领域模型

```go
User.IPLimit     int  // 并发源 IP 上限，0 = 不限
User.DeviceLimit int  // 绑定设备数上限，0 = 不限
```

**为什么 0 表示不限**：和既有的 `TrafficLimitBytes` 一致，也和面板侧编码一致（面板把 0 读作「无上限」）。于是 GORM AutoMigrate 给存量安装加列时，**零值天然等于「不限」，不需要任何回填**，升级前后行为完全一致。

**~~为什么是 per-user 而不是 per-group~~：这条已经反转，见 §10。** 原文写的是「分组承载的是节点选择与布局，从不承载配额」——写下时就不准确（`Group.Require2FA` 是分组级强制策略，`OverridableScopeKeys` 里还有 15 项按分组覆盖的设置），现在更不成立：三个额度都可以由分组承载并被成员继承。

## 3. 推送契约：`domain.UserLifecycle`

推送链路不再是一串标量参数，而是一个契约类型：

```go
type UserLifecycle struct {
    Enable        bool
    ExpiryTime    int64
    QuotaHeadroom int64  // 本期剩余；不是给面板的数
    IPLimit       int
    DeviceLimit   int
}
```

**它是契约，不是参数打包。** PSP 自己的数据面才是设计目标，3X-UI / S-UI 是兼容目标——所以这个集合由「PSP 想强制什么」定义，各适配器再按能力翻译。往里加字段不应该波及五个函数签名。

### 3.1 `QuotaHeadroom` 始终是本期剩余

面板拿终身累计计数器做比较（见 [traffic-floor-defect.md](traffic-floor-defect.md)），所以必须重基。**重基只在唯一知道「是哪个 client 的计数器」的那一点发生**：

```go
want.PanelQuota(panelLifetime)   // = PanelQuotaCap(QuotaHeadroom, panelLifetime)
```

一个用户的 lifecycle 会扇出到多个 client，每个 client 有各自的计数器——所以这个转换**不能**折进结构体里，它是「per-user 意图」的「per-client 解析」。

## 4. `limitHwid`：从「故意不发」到「PSP 所有」

这个字段的历史值得完整记一笔，因为它是本立场的最佳例证。

**3.7.0 之前**：字段不存在。

**3.7.0 引入后，PSP 故意不发它**。原因不是疏忽：上游 `clients/update/:email` 会把**缺失的 key 绑成 0**，而 `EnforceHwidForSubID` 在 `limit <= 0` 时直接返回 `Allowed = true`——**即 PSP 每次推送都在静默关掉这个安全控制**。

那为什么不回显？因为回显更糟：`setClientLimitHwidByEmail` 把读到的值喂给 `trimClientHwidsForSubID`，后者会**删除超出上限的设备注册记录**。读-改-写窗口内的任何变化（管理员调高上限、一台设备刚注册）都会让陈旧值**永久销毁设备行**。

两害相权，当时选了「清零」——丢一个标量，好过删数据。

**所有权消灭了这个两难。** PSP 现在发的是**自己的意图值**（`User.DeviceLimit`），不是回显，**根本不存在读-改-写窗口**。

> 这正是「领域模型为主、面板为辅」的价值：只要 PSP 拥有该字段，上游那个「缺失 key 绑 0」的缺陷就不再能伤到任何人。

### 4.1 但这个字段在 PSP 架构下**不执行**（2026-09-02 更正）

上面整段分析成立，结论不成立。之前追到 `EnforceHwidForSubID` 就停了，没有再问一句**谁调用它**。

在 3X-UI 全仓里，`limit_hwid` 只有**一处**被拿来做判断：

```
internal/sub/controller.go:623
  → EnforceHwidForSubID(c.Param("subid"), …)
    → effectiveHwidLimitForSubID   (client_hwid.go:70)
       SELECT COALESCE(MAX(limit_hwid), 0)
       FROM clients WHERE sub_id = ? AND enable = true
```

其余每一处引用都只是写入、在 payload 里传递、在列表里回显、或节点同步时合并——没有一处执行。

而那唯一的调用方是**订阅控制器**：设备指纹在客户端 App 去拉**3X-UI 自己的订阅 URL** 时，从请求里注册进 `client_hwids`。

**PSP 自己发订阅**（`internal/transport/http/router.go:162`，走 NoRoute 动态路径）。PSP 的用户拿到的是 PSP 的订阅地址，永远不会请求 3X-UI 的那个端点。于是：

- 那道闸**从不触发**；
- `client_hwids` 对 PSP 管理的客户端**永远是空表**；
- `limitHwid` 被正确地存进 client 记录，然后**什么也不做**——在**任何** 3X-UI 版本上，3.7.0 及以上也一样；
- `trimClientHwidsForSubID` 同理无事可做，因为没有注册记录可裁。

还有一条相关事实：PSP **从不设置 `subId`**（`buildSharedClientSpec` 不填，适配器发 `"subId": ""`）。`EnforceHwidForSubID` 对空 `subId` 直接 `Allowed = true` 短路返回（`client_hwid.go:81-84`），所以**不会**发生「所有 PSP 客户端共用一个设备桶」——`MAX(limit_hwid)` 不会跨用户取。不幸中的万幸，但也说明这条路本来就没接通。

**这不是上游缺陷。** 3X-UI 的设计是自洽的：它自己发订阅，就在自己的订阅端认设备。缺陷在于 PSP 把订阅接管了，却指望执行留在原地。

**因此设备上限的执行点只能在 PSP 的订阅端。** 而且这恰恰是**唯一可能做成「按用户」的位置**——它能看见同一个用户的全部拉取，无论凭据被 `clientplan` 拆成几份、落在几块面板上。对照之下 `limitIp` 是按 client email、按面板各算各的，被双重放大。见 §11 与任务 #45。

## 5. 能力与兼容

**能力（capability）回答的是「面板存不存得下这个字段」，不是「这个值会不会被执行」。** 两者不同，而且下表只说前者：

| 能力 | xui | sui |
|---|---|---|
| `client.iplimit` | ✅ | ❌ |
| `client.devicelimit` | 面板 ≥ 3.7.0 才声明 | ❌ |

**S-UI 两个都不支持**——它的 client 模型既没有并发 IP 上限也没有设备上限，`applySpec` 直接丢弃这两个字段。给 S-UI 面板上的用户设了限制，那里就是不生效。这通过 capability API 呈现，而不是让写入失败。

**xui 的设备上限跟随面板版本**（v3.9.2-beta.14 起）。`limitHwid` 是 3.7.0 才有的列，更低版本收下这个 key 但不保存，读回永远是 0；无条件声明会让 `lifecycleWriteReason` 的收敛守卫失效，每周期发一次全量替换 + 内核重启。`version.XUIAtLeast` 对空值或无法解析的版本判 false，方向是刻意的——误报支持产生上述循环，误报不支持只是让该字段不再单独触发写入。**IP 上限不设版本门**：它在所有受支持版本上都存在，设了门反而会让未探测面板上的上限静默失效。

**存得下 ≠ 会执行。** 两个字段各有一个能力系统看不见的执行前提：

- **`limitIp`** 需要节点上装有可用的 fail2ban（见 §5.1）。缺了它，面板照常存值、照常返回成功，然后不封任何东西。3.7.0 起可以用 `GET /server/fail2banStatus` 探测（任务 #46）。
- **`limitHwid`** 需要客户端去拉**3X-UI 自己的订阅端点**——而 PSP 接管了订阅，所以它在 PSP 架构下**从不执行**，与面板版本无关。详见 §4.1。

换言之：能力为 ✅ 只保证写入不会被丢弃，**不保证限制生效**。这两条前提要各自被观测，否则它们和「面板存不下」对管理员是同一个症状——填了值，毫无作用。

### 5.1 `limitIp` 的执行前提（已实测确认）

3X-UI 的并发 IP 限制走 **core 的 online-stats API**（不需要访问日志，这是好消息）。但它的执行被**两道闸**门控，任一不满足就完全不生效——`resolveEnforce`（`check_client_ip_job.go:89`）：

```go
if hasLimit && runtime.GOOS != "windows" && !f2bInstalled {
    return false            // ← 整个执行路径关闭
}
```

`enforce == false` 时 `updateInboundClientIps` 在第 509 行直接早退：**不封禁、不断连**，只把观察到的 IP 存下来给界面显示。

| 闸 | 条件 | 实测 |
|---|---|---|
| ① 二进制 | `fail2ban-client -h` 能跑通 | 未装 → `enforce=false`；装上 → `enforce=true` |
| ② 环境变量 | `XUI_ENABLE_FAIL2BAN` **未设** 或等于字面量 `"true"` | 设成 `"1"` / `"yes"` / `"false"` **一律关闭** |

**②是个陷阱**：`XUI_ENABLE_FAIL2BAN=1` 看着像「启用」，实际把执行关掉了（`isFail2BanEnabled` 只认 `"true"`）。

### 5.1.1 装了 fail2ban 之后，实际执行的是什么

不是「只写日志」——两件事一起做：

1. **面板自己断连**：通过 xray API `RemoveUser` + 100ms 后重新 `AddUser`，掐掉该客户端**全部**连接。仅支持 `vmess / vless / trojan / shadowsocks / hysteria`，**其他协议只打一行 warning 就返回**。
2. **fail2ban 在防火墙层封 IP**：面板按固定格式写 `[LIMIT_IP] Email = … || Disconnecting OLD IP = … || Timestamp = …`，`x-ui.sh` 建的 `filter.d/3x-ipl.conf` 匹配它。（上游注释明确写着「log format is load-bearing … don't change the wording」。）

所以两者互补：①让超限客户端立刻掉线，②让那个具体 IP 短期内连不回来。

**给运维方的结论**：节点上装 fail2ban，且**不要**设 `XUI_ENABLE_FAIL2BAN`（或只设成 `true`）。PSP 侧推送始终正确，执行前提在节点。

## 6. 漂移愈合

两个上限是 PSP 所有的，所以**被人在面板界面上改动必须被改回来**，而不是被跳过。它们已进入 `SyncLifecycle` 的比较集合（`lifecycleWriteReason`），因此：

- 面板值与 PSP 意图不一致 → 重推，并在 `psp_lifecycle_sync_write_reason_total{reason=ip_limit|device_limit}` 上计数
- 一致 → 仍然命中 no-op skip，不会因为多了两个字段就每周期多一次写

**但比较受能力门控**：面板**存不下**的字段被排除在比较之外。

这不是可选的优化，是必须的。一个默默丢弃该字段的面板，读回来永远是 0——若让它参与比较，skip 就**结构性地永远不可能命中**：每周期都看到差异、每周期发一次整体替换、每周期重启一次内核，**而这个值永远无法收敛**。

排除它不等于「忽略漂移」：一台没地方存这个值的面板上根本不存在漂移可言，而缺口本身已经由 §6.2 计数上报。

## 6.2 缺口是被上报的，不是被吞掉的

声明能力只解决了一半：**S-UI 上的用户设了限制，写入照样成功、就是不生效。** 这正是能力列表本该防住的失败形状，所以 `SyncLifecycle` 在推送前检查：

```
PSP 想强制某个上限  且  目标面板没有对应能力  →  psp_capability_gap_total{capability=…} 计数 + 告警
```

两个设计选择：

- **只在 PSP 真的想强制时才算缺口。** 不限的用户落在不支持的面板上不是问题，把它计进去会让这个指标失去意义。
- **计数器是持久信号，日志每（面板, 能力）只打一次。** 这个状态是稳态的——直到运维方把用户挪走或升级面板才会消失，每周期为每个受影响的客户端打一行会把别的都埋掉。

**缺口是警告，不是拒绝**：同一次写入里的 enable / 到期 / 配额，那台面板执行得好好的。

## 9. UI 上的能力提示

服务端把缺口计进 `psp_capability_gap_total`（§6.2），但**计数器不是设置这个值的人正在看的地方**。写入会成功、就是不生效——这正是能力列表本该防住的失败形状，而它在管理界面上原本是完全不可见的。

新建 / 编辑用户对话框里，两个上限字段各自在下方显示无法执行它的面板名：

```
Concurrent IP limit  [ 3 ]
Not enforceable on: probe-sui — clients placed there ignore this.
```

判定是纯函数 `unenforceablePanels(limit, servers, capability)`（`web-react/src/utils/capabilities.ts`），**规则与服务端 `reportCapabilityGaps` 刻意一致**：

- **只在 PSP 真的想强制时才算缺口** —— `limit <= 0` 一律不提示。不限的用户落在不支持的面板上不是问题，为它告警只会训练运维方忽略真正要紧的那条。
- **两个上限各判各的** —— 一台面板可能支持其中一个而不支持另一个。
- **未声明任何能力的面板算作「不支持」** —— 从未探测过、或较旧的构建都落在这里。宁可多提示：这个提示存在的意义就是拦住静默不生效的设置。

实机验证（真实浏览器驱动真实面板，建了一台 S-UI 面板——它两个能力都不声明）：上限为 0 时不提示；设成 3 之后提示出现、点名了那台面板、无 console 报错；两个字段互不干扰。

**范围上的诚实**：提示列的是**整个机队**里不支持的面板，不是「这个用户的客户端实际落在哪几台」——后者要走 用户 → 分组 → 节点 → 面板 这条链，前端此处没有。文案因此写成「落在其上的客户端不会生效」而不是「这个用户不会生效」。

## 10. 从分组继承（OU 策略）

三个额度——流量配额、并发 IP 上限、设备数上限——**默认从用户所属分组继承**，用户可以逐字段覆盖。改一次分组策略即可作用于全组，不必逐个用户编辑。

### 10.1 第三个状态，以及为什么非要有它

`0` 早就被占用了：它在两端都表示「不限」——PSP 这样编码，面板也这样读。所以一旦分组能承载策略，一个存量的 `0` 就是**歧义**的：是「不限」，还是「听分组的」？读错的后果是**给本来没有配额的用户凭空造出配额**，正是 [`traffic-floor-defect.md`](traffic-floor-defect.md) 那个缺陷换了个位置重演。

于是引入真正的三态：

| 存储值 | 含义 |
|---|---|
| `NULL` | **继承分组** |
| `0` | **明确不限**（即使分组有规定） |
| `N` | 明确为 N |

三个字段各自独立解析：`用户覆盖 → 分组策略 → 不限`。分组被删除的用户解析为不限，而不是报错或卡在旧值上——放行付费用户比误伤他们安全。

### 10.2 存量数据：`0` 迁移为 `NULL`，且只迁一次

存量的 `0` 全部转成 `NULL`（继承）。这个重新解释之所以安全，理由很具体：

> 在此之前 `0` 是表达「不限」的**唯一**方式，而且**没有分组层可供对比**——所以没有任何一个存量 `0` 能携带「不限，且刻意不听分组的」这种意图。它没有丢弃任何曾经存在过的信息。

反过来若保留为明确 `0`，每个存量用户都会静默退出分组策略，运维方设了分组配额会发现**对谁都不生效**——正是这个功能要消除的逐人操作。

**落地瞬间行为不变**：分组的新列都是 `NULL`（不作规定），继承解析为不限，正是 `0` 原本的含义。非零值原样保留为显式覆盖。

这类迁移**只正确一次**，重跑会把运维方后来刻意填的 `0` 又变回继承，所以它由 `schema_migrations` 表里的标记门控，且标记与数据改动在**同一个事务**里写入——中途崩溃不会留下「数据改了、标记没写」的可重跑状态。（`EnsureSchema` 里既有的那些回填是幂等的：它们把 NULL 归并成本来就该是的 0，重跑无副作用，因此不需要标记。）

### 10.3 生效值与存储值分开放

`domain.User` 上的 `TrafficLimitBytes` / `IPLimit` / `DeviceLimit` 是**解析后的生效值**，由仓储在加载时填好；**存储的覆盖值**在旁边的 `u.Limits` 里（`nil` = 继承）。

这么切是因为约有 100 个消费点只想要那个数字——计量循环问「这个用户的配额是多少」不该被迫先拿到分组。而它之所以**安全**，取决于一个前提：写路径是稀疏指针 DTO，**请求里没提到的字段就不写**。因此一次普通编辑（比如只改显示名）不会把继承中的用户悄悄钉死在他分组当时的值上。`TestSaveDoesNotPinAnInheritingUser` 钉住这一点，并已用变异验证——把映射改成回写生效值，该测试立刻失败。

「恢复继承」需要独立信号（`nil` 已经表示「别动」），所以用户侧有 `inherit_*` 标志、分组侧有 `clear_*` 标志，形状与既有的 `ClearExpire` 一致。

创建路径携带的是标量，**没有办法表达「继承」**，因此那里的 `0` 读作「没有意见」→ 继承。这与迁移的判断同源，理由也相同。

### 10.4 解析发生在哪

在用户仓储里，配一个分组限额缓存（TTL 30s），分组仓储每次写入都会让它失效。

每个已鉴权的请求都会加载用户，所以按次查库不可接受；而 30s 的陈旧度是可接受的，因为分组策略是**长期决定**，作用于它的东西都更慢（多分钟的轮询、每小时的邮件）。运维方编辑分组仍然**立即生效**——两个仓储共用同一个缓存实例，写入即失效，与作用域设置缓存同一套纪律。

**读不到时向「不限」失败**：因为一次数据库抖动而切断付费用户是更糟的错误，何况 PSP 自己仍在计量并停用，面板侧上限只是兜底。

### 10.5 界面

- **分组 → 策略**：三个输入框。**留空 = 本组不作规定**（解析为不限），**填 0 = 明确不限**。
- **用户编辑**：每个额度下方一个「跟随分组」勾选框。勾上时输入框置灰，但**仍显示继承到的数值**——让运维方看见自己继承的是什么，而不是一个空框。

### 10.6 已验证

对着真实数据库与真实面板跑通的完整生命周期：继承 → 改分组策略立即到达成员 → 单字段覆盖 → **无关编辑不钉死其余字段** → 分组再变、继承字段跟随而覆盖保持 → 交还给分组 → 清空分组策略回到不限。迁移双向覆盖（转换，以及第二次运行不动刻意填的 `0`），标记与「不钉死」两处均已变异验证。

> **这句话曾经越界。** 上面验证的是「改分组策略立即到达成员的**解析值**」——即 API 读出来是对的。但**推送到面板**是另一回事，而当时并没有：只有标签过滤变更会触发成员重推，闲置成员因此会无限期保留旧的上限（轮询只碰有流量的用户）。已修，额度变更现在触发同一条后台重推，且判定把 `nil` 与任何值区别对待（清空策略同样让成员停止执行，和设置一样是变更）。

### 10.7 两个容易忽略的耦合

- **抬高配额必须解除流量停用**。`UpdateProfile` 写的是 `u.Limits`，而旁边的解析值仍是编辑前的——`TrafficExceeded()` 会拿旧配额判断，于是用户仍被停用、管理员的编辑看起来毫无作用。解析因此必须发生在**保存之后、第一个读取者之前**，而不是在推送前。
- **分组策略要和用户端受同样的校验**。创建分组时漏掉校验的话，一个负数上限会被全组继承、原样推给面板，而且**连能力缺口告警都不会触发**（那个告警只在上限为正时才算缺口）。

## 11. 谁决定用户在哪个 OU：IdP 分流

§10 让 OU 承载额度之后，「这个人属于哪个 OU」就不再只是节点分配问题，而是**他拿到多少配额**的问题。原先这件事只有一个答案：`DefaultGroupSlug`，一个静态的桶，所有 SSO 用户都进去。IdP 送来的组和属性早就解析好放在 `EnsureSSOInput` 里，却只喂给角色匹配器，从没参与过 OU。

现在有一组 `group_rules`：有序、首条命中者胜、精确比对，命不中则落 `DefaultGroupSlug`。

### 11.1 为什么是独立的一组规则，不是 `SSORoleRule` 上加个字段

「谁是管理员」和「谁属于哪个 OU」很少是同一个条件。塞进同一个 first-match 列表会强迫这两个决定共享一套优先级顺序，而 `SSORoleRule.Keep` 的语义也只对角色成立。

但**匹配本身共用一份代码**（`attributeMatches` / `lookupRuleValues`）。两种规则声称「匹配方式一样」却各持一份实现，一定会漂移，而第一次分歧是静默的——一条规则对角色生效、对分组不生效，或者反过来。

### 11.2 每次登录都重新判定，不是只在建号时

这是本节最重要的一条，也是初版设计里做错、被指出后改掉的一条。

初版是「只在建号时定 OU」，理由是爆炸半径（OU 决定节点、订阅内容，现在还决定额度）。这个理由站不住：

- **角色一直是每次登录同步的**，`Keep=false` 时还会主动降级。同一套 IdP 信号在两件事上两套规则，没有依据。
- **不同步的错误方向是「权限过大」**。IdP 把某人移出支撑高级 OU 的那个组、而 PSP 永不复查，那份高配额和高级节点就是永久的。这比「被误搬」严重。

那条「升级不该悄悄搬动线上用户」的顾虑是真的，但它**不需要开关**——`ResolveGroupForSSO` 沿用了角色引擎现成的 carve-out：

| 情形 | 结果 |
|---|---|
| 没配任何 group 规则 | 规则集什么都不主张 → **谁都不动**（升级后所有存量部署正是此状态） |
| 命中，且等于当前 OU | 不变 |
| 命中，但当前 OU 被某条 `Keep=true` 的规则主张 | 保留当前（手工授予优先） |
| 命中，其余情况 | 采用命中的 OU |
| 未命中，当前 OU **无人主张** | 不动（管理员手工放的，IdP 不知道也不该管） |
| 未命中，当前 OU 被主张且无 `Keep` | 落回默认组 —— **这一条才是补上口子的那条** |

### 11.3 两条方向相反的失败策略

规则指向一个不存在的分组时：

- **建号时 → 拒绝建号。** 静默回落可能把一个本该被**限制**的人放进更宽松的默认组；而且建号是失败代价最小的时刻，还没有服务可打断。
- **登录时 → 记日志、保持原样、不阻断登录。** 存量用户因为某条规则的目标后来被删掉就登不进来，比一个陈旧的 OU 糟糕得多。这也是主流 IdP 的做法：provisioning 映射错误不阻断 sign-in。

真正该拦住这件事的是**保存时校验**：`validateSSOGroupRules` 在 PUT 落库前解析每个 slug，并点名出错的行号与 slug。不然运维方的拼写错误要由别人的登录失败来告诉他。

### 11.4 改了 OU 必须推到面板

存储行本身改不动节点上的任何东西。OU 决定入站归属，§10 之后还决定继承来的额度，所以变更走 `ResyncMembershipOrEnqueue`——和管理员手工换组同一条路。这和 §10.6 记的是同一个缺陷，只是高一层。

反过来也要成立：**没有发生迁移的登录不推送任何东西**。每次 SSO 登录都会走这条路径，逐次重推等于把 `UpdateClient` 和 Xray 重启扇出到整个机队，而什么都没变。

### 11.5 界面与文案

规则编辑器在 设置 → SSO，SAML 与 OIDC 各一份，紧挨着角色规则，同样支持拖拽排序。**目标是真实分组的下拉选择器，不是自由文本**：角色可以合法地填一个后端还不认识的字符串（角色编辑器正因如此是 freeSolo），但一个解析不了的分组 slug 有两个坏结局，且都在别人的登录时才发作。

顺带修正了三处已经不准确的文案。`0` 在 §10 之后不再表示「不限」，而是「没有意见，跟随分组」——而分组可能有配额，所以填 `0` 恰恰可能**不是**不限：

| 位置 | 之前 | 现在 |
|---|---|---|
| 自助注册默认流量 | `0=不限` | `0=跟随分组` |
| SAML 新用户默认流量 | `0=无限` | `0=跟随分组` |
| OIDC 新用户默认流量 | `0=无限` | `0=跟随分组` |

这三个默认值都在**数据库**里、由设置页管理，不在 `config.yaml`——后者自 v3.x 起只保留启动所需的监听地址、密钥与数据库连接。

### 11.6 降级前必须成立的两个条件（对抗性 review 查出）

功能第一版发布后跑 `/code-review`，查出**降级这条分支本身**有两个缺陷。两个都把「撤销权限」变成了别的东西，而且都是本轮引入的。

**一、没有配默认分组时，降级 = 发放无限额度。**

3c 分支无条件返回 `DefaultGroupSlug`。该值为空时（全新安装的状态）解析成 `GroupID=0`，而**不属于任何分组的用户什么都继承不到**——`ResolveLimits` 给出 0/0/0，也就是**流量不限、连接上限不限**。于是被 IdP 撤销的人拿到的比撤销前**更多**，正好是这条分支存在意义的反面。

后续重推还会静默成功：`ResyncMembership` 对 `GetByID(ctx, 0)` 拿到 `ErrNotFound`，而 `runUserTask` 的 `SyncTaskUserResync` 分支把 `ErrNotFound` 当作「用户已删除」并把任务标记为**成功**，旧 OU 的入站因此永远不会被摘掉。

两处修：**保存时拒绝**——有分组规则却没有默认分组的配置存不进去，因为一套能降级的规则必须有降级的去处；**运行时兜底**——`defaultSlug` 为空时不降级，保持原样。

**二、IdP 压根没发声明，被当成「明确撤销」。**

`attributeMatches` 分不清「IdP 说你不在那个组里」和「IdP 什么都没说」，而 3c 对两者一视同仁地降级。第二种情况和这个人毫无关系：Entra 在用户加入约 150 个组以上时**停止下发 `groups`、改发 `hasgroups`**；声明映射可以被改坏；新建的应用注册可能根本没配这个声明。

任何一种都会变成**机队级的权限变更**——每个 SSO 用户在下次登录时离开自己的 OU、失去它的配额与节点集——起因是一次目录侧的编辑，而做那次编辑的人根本没把它和 PSP 联系起来。

修法是把「沉默」和「否认」分开：`idpSpokeAboutGroups` 检查规则集引用的属性是否**真的出现在断言里**，没有出现就视为 SSO 没有意见，存储的分组保持不变。声明**存在但不含该组**仍然照常降级——否则这个修复就等于把功能关掉了。

**角色规则有完全相同的形状，同一轮一并修掉了。** 最初只改了分组侧，理由是角色降级掉到 `RoleUser`、代价远小于失去一个 OU 的额度与节点集。那个理由只站得住一半：代价确实小，但缺陷同源、修法现成，而「Entra 一次 group overage 就让所有靠规则拿到 admin/operator 的人在下次登录被降成普通用户」并不是小事——面板可能因为一次目录侧编辑失去全部特权用户。

判断「IdP 是否发过声」的核心因此只有**一份实现**（`idpSpokeAbout`），两种规则各自把自己引用的属性名传进去。两套规则对「什么算 IdP 说过话」如果理解不一致，会在同一个断言上朝相反方向出错，而且这种分歧是静默的——所以有一条测试专门钉住它们的一致性。

### 11.7 已验证

真实面板 + 真实浏览器：三条拒绝路径各自返回 400 并点名行号与 slug（未知 slug、空值、空分组），且**被拒绝的保存不会覆盖已存的规则**；SAML 与 OIDC 走的是同一个校验。浏览器里两条已存规则正确渲染成分组**名称**（存的是 slug），下拉里是真实分组目录 `Default / VIP / Staff`，改选后保存并回读确认落库、`keep` 未丢失，全程无 console 报错。

§11.6 的两条守卫各有解析层与服务层测试，并变异验证：删掉沉默守卫、删掉空默认组守卫、把「IdP 是否发声」恒为假（那会等于关闭降级），三者各自都让测试挂掉。

解析矩阵每个分支单测覆盖并变异验证；服务层另有测试断言 `EnsureSSO` 确实调用了它、以及面板确实被通知——两者都是能静默失效的一环。有一处变异**存活**：删掉 `len(rules)==0` 的提前返回不影响任何测试，因为「当前 OU 无人主张」那条分支会给出同样答案。该性质由两条独立路径保证，测试钉的是性质而非某一行，这一点写在测试注释里。

### 11.8 安全审查：SSO 触及的两处权限判定

对 §11 这批改动做专门的安全审查（视角与通用 review 不同：谁能控制输入、能否借此提权或阻止撤销），查出两条。第一条比这个功能本身老得多。

**一、SSO 的角色降级绕过「最后一个管理员」保护。**

管理 API 在**三条**路径上都拦着这件事——降级（`UpdateProfile`）、删除、停用——理由写在代码里：否则面板会没有人能管理。而 `reconcileSSOUser` 写的是同一个 `role` 列，却一条都没经过：它直接赋值再走 `updateUser`，那只是 `users.Update`。

后果不是理论上的。实测：唯一一个启用的管理员，IdP 那边把他移出管理员组，一次登录之后 `CountEnabledAdmins` **归零**。全新安装总会有一个带本地密码的 bootstrap 管理员兜底，但把它删掉、或者全部管理员都只靠 SSO 的部署，就是一次目录侧编辑换来一个无人可管的面板。

现在同一条件也在 SSO 路径上执行，但**拒绝的方式不同**：管理 API 返回错误即可，这里不能——让登录失败等于把人整个挡在外面，比一个过期的角色更糟。所以是**拒绝这次降级、打警告、登录照常继续**，其余角色变更不受影响。计数读取失败时**向安全侧失败**（当作「可能是最后一个」而拒绝）：判断错了的代价是一个管理员多留到下次登录，反过来的代价是数据库抖一下就没人能管面板了。

**二、沉默守卫是一个撤销绕过，而且它原本完全不可见。**

§11.6 加的守卫刻意 fail-open：IdP 没发声明时保留已存的角色与分组。这挡住了「一次目录侧意外把整个机队降级」，但代价必须说清楚——**能让声明消失的人，就能保住目录已经收回的授权**。Entra 的 group overage 由用户自己所在的组数触发，而不少组织允许自助加组。

这个取舍保留，但不能是隐形的：新增 `psp_sso_claim_silent_total{kind=role|group}`，在「配了规则、但 IdP 一个相关属性都没发」时计数。**长期高于零意味着两件事之一**：IdP 停发了 PSP 依赖的声明，或者有人正握着目录已经收回的授权。有测试同时钉住「沉默要计数」和「说了话不能计数」——后者同样重要，一个会误报的指标运维方很快就学会忽略。

> **顺带修正一处我自己的方法缺陷。** 这轮的变异验证一度报告两条变异「存活」。其中一条是假的：变异后代码**编译不过**，而我用 `grep -c '^--- FAIL'` 统计失败数，于是「没有任何测试结果行」被读成了「0 个失败 = 变异存活」——恰好反了。变异验证必须先确认变异体能编译，否则它会在最该报警的时候保持沉默。另一条是真的：计数失败那条 fail-safe 分支当时确实没有测试，已补。
