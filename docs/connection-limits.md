# 连接限制：并发 IP 与设备数

> 状态：**已实现，实机验证（3X-UI 3.7.0 + xray-core 26.7.28）。**
> 关联：[ARCHITECTURE.md](ARCHITECTURE.md)、[inbound-ownership.md](inbound-ownership.md)、[3xui-compat.md](3xui-compat.md)、[data-plane-plan.md](data-plane-plan.md)。

## 1. 设计立场

**PSP 的领域模型是真相源，面板是兼容目标。**

字段按 PSP 想表达的意图命名和定义（`User.IPLimit` / `User.DeviceLimit`），**不跟任何面板的字段名或语义走**。各适配器把它翻译成自己面板能表达的部分，翻译不了的**通过 capability 显式声明缺口**——而不是静默不生效。

这条立场决定了下面几乎每个具体选择。

## 2. 领域模型

```go
User.IPLimit     int  // 并发源 IP 上限，0 = 不限
User.DeviceLimit int  // 绑定设备数上限，0 = 不限
```

**为什么 0 表示不限**：和既有的 `TrafficLimitBytes` 一致，也和面板侧编码一致（面板把 0 读作「无上限」）。于是 GORM AutoMigrate 给存量安装加列时，**零值天然等于「不限」，不需要任何回填**，升级前后行为完全一致。

**~~为什么是 per-user 而不是 per-group~~：这条已经反转，见 §10。** 原文写的是「分组承载的是节点选择与布局，从不承载配额」——写下时就不准确（`Group.Require2FA` 是分组级强制策略，`OverridableScopeKeys` 里还有 15 项按分组覆盖的设置），现在更不成立：三个额度都可以由分组承载并被成员继承。

## 3. 推送契约：`domain.UserLifecycle`

推送链路不再是一串标量参数，而是一个契约类型：

```go
type UserLifecycle struct {
    Enable        bool
    ExpiryTime    int64
    QuotaHeadroom int64  // 本期剩余；不是给面板的数
    IPLimit       int
    DeviceLimit   int
}
```

**它是契约，不是参数打包。** PSP 自己的数据面才是设计目标，3X-UI / S-UI 是兼容目标——所以这个集合由「PSP 想强制什么」定义，各适配器再按能力翻译。往里加字段不应该波及五个函数签名。

### 3.1 `QuotaHeadroom` 始终是本期剩余

面板拿终身累计计数器做比较（见 [traffic-floor-defect.md](traffic-floor-defect.md)），所以必须重基。**重基只在唯一知道「是哪个 client 的计数器」的那一点发生**：

```go
want.PanelQuota(panelLifetime)   // = PanelQuotaCap(QuotaHeadroom, panelLifetime)
```

一个用户的 lifecycle 会扇出到多个 client，每个 client 有各自的计数器——所以这个转换**不能**折进结构体里，它是「per-user 意图」的「per-client 解析」。

## 4. `limitHwid`：从「故意不发」到「PSP 所有」

这个字段的历史值得完整记一笔，因为它是本立场的最佳例证。

**3.7.0 之前**：字段不存在。

**3.7.0 引入后，PSP 故意不发它**。原因不是疏忽：上游 `clients/update/:email` 会把**缺失的 key 绑成 0**，而 `EnforceHwidForSubID` 在 `limit <= 0` 时直接返回 `Allowed = true`——**即 PSP 每次推送都在静默关掉这个安全控制**。

那为什么不回显？因为回显更糟：`setClientLimitHwidByEmail` 把读到的值喂给 `trimClientHwidsForSubID`，后者会**删除超出上限的设备注册记录**。读-改-写窗口内的任何变化（管理员调高上限、一台设备刚注册）都会让陈旧值**永久销毁设备行**。

两害相权，当时选了「清零」——丢一个标量，好过删数据。

**所有权消灭了这个两难。** PSP 现在发的是**自己的意图值**（`User.DeviceLimit`），不是回显，**根本不存在读-改-写窗口**。

> 这正是「领域模型为主、面板为辅」的价值：只要 PSP 拥有该字段，上游那个「缺失 key 绑 0」的缺陷就不再能伤到任何人。

### 4.1 但这个字段在 PSP 架构下**不执行**（2026-09-02 更正）

上面整段分析成立，结论不成立。之前追到 `EnforceHwidForSubID` 就停了，没有再问一句**谁调用它**。

在 3X-UI 全仓里，`limit_hwid` 只有**一处**被拿来做判断：

```
internal/sub/controller.go:623
  → EnforceHwidForSubID(c.Param("subid"), …)
    → effectiveHwidLimitForSubID   (client_hwid.go:70)
       SELECT COALESCE(MAX(limit_hwid), 0)
       FROM clients WHERE sub_id = ? AND enable = true
```

其余每一处引用都只是写入、在 payload 里传递、在列表里回显、或节点同步时合并——没有一处执行。

而那唯一的调用方是**订阅控制器**：设备指纹在客户端 App 去拉**3X-UI 自己的订阅 URL** 时，从请求里注册进 `client_hwids`。

**PSP 自己发订阅**（`internal/transport/http/router.go:162`，走 NoRoute 动态路径）。PSP 的用户拿到的是 PSP 的订阅地址，永远不会请求 3X-UI 的那个端点。于是：

- 那道闸**从不触发**；
- `client_hwids` 对 PSP 管理的客户端**永远是空表**；
- `limitHwid` 被正确地存进 client 记录，然后**什么也不做**——在**任何** 3X-UI 版本上，3.7.0 及以上也一样；
- `trimClientHwidsForSubID` 同理无事可做，因为没有注册记录可裁。

还有一条相关事实：PSP **从不设置 `subId`**（`buildSharedClientSpec` 不填，适配器发 `"subId": ""`）。`EnforceHwidForSubID` 对空 `subId` 直接 `Allowed = true` 短路返回（`client_hwid.go:81-84`），所以**不会**发生「所有 PSP 客户端共用一个设备桶」——`MAX(limit_hwid)` 不会跨用户取。不幸中的万幸，但也说明这条路本来就没接通。

**这不是上游缺陷。** 3X-UI 的设计是自洽的：它自己发订阅，就在自己的订阅端认设备。缺陷在于 PSP 把订阅接管了，却指望执行留在原地。

**因此设备上限的执行点只能在 PSP 的订阅端。** 而且这恰恰是**唯一可能做成「按用户」的位置**——它能看见同一个用户的全部拉取，无论凭据被 `clientplan` 拆成几份、落在几块面板上。对照之下 `limitIp` 是按 client email、按面板各算各的，被双重放大。见 §13.4（设备标识只观测、不执行）。

## 5. 能力与兼容

**能力（capability）回答的是「面板存不存得下这个字段」，不是「这个值会不会被执行」。** 两者不同，而且下表只说前者：

| 能力 | xui | sui |
|---|---|---|
| `client.iplimit` | ✅ | ❌ |
| `client.devicelimit` | 面板 ≥ 3.7.0 才声明 | ❌ |

**S-UI 两个都不支持**——它的 client 模型既没有并发 IP 上限也没有设备上限，`applySpec` 直接丢弃这两个字段。给 S-UI 面板上的用户设了限制，那里就是不生效。这通过 capability API 呈现，而不是让写入失败。

**xui 的设备上限跟随面板版本**（v3.9.2-beta.14 起）。`limitHwid` 是 3.7.0 才有的列，更低版本收下这个 key 但不保存，读回永远是 0；无条件声明会让 `lifecycleWriteReason` 的收敛守卫失效，每周期发一次全量替换 + 内核重启。`version.XUIAtLeast` 对空值或无法解析的版本判 false，方向是刻意的——误报支持产生上述循环，误报不支持只是让该字段不再单独触发写入。**IP 上限不设版本门**：它在所有受支持版本上都存在，设了门反而会让未探测面板上的上限静默失效。

**存得下 ≠ 会执行。** 两个字段各有一个能力系统看不见的执行前提：

- **`limitIp`** 需要节点上装有可用的 fail2ban（见 §5.1）。缺了它，面板照常存值、照常返回成功，然后不封任何东西。**PSP 会主动探测这一条并把结论显示出来**（§5.2）。
- **`limitHwid`** 需要客户端去拉**3X-UI 自己的订阅端点**——而 PSP 接管了订阅，所以它在 PSP 架构下**从不执行**，与面板版本无关。详见 §4.1。

换言之：能力为 ✅ 只保证写入不会被丢弃，**不保证限制生效**。这两条前提要各自被观测，否则它们和「面板存不下」对管理员是同一个症状——填了值，毫无作用。

### 5.1 `limitIp` 的执行前提（已实测确认）

3X-UI 的并发 IP 限制走 **core 的 online-stats API**（不需要访问日志，这是好消息）。但它的执行被**两道闸**门控，任一不满足就完全不生效——`resolveEnforce`（`check_client_ip_job.go:89`）：

```go
if hasLimit && runtime.GOOS != "windows" && !f2bInstalled {
    return false            // ← 整个执行路径关闭
}
```

`enforce == false` 时 `updateInboundClientIps` 在第 509 行直接早退：**不封禁、不断连**，只把观察到的 IP 存下来给界面显示。

| 闸 | 条件 | 实测 |
|---|---|---|
| ① 二进制 | `fail2ban-client -h` 能跑通 | 未装 → `enforce=false`；装上 → `enforce=true` |
| ② 环境变量 | `XUI_ENABLE_FAIL2BAN` **未设** 或等于字面量 `"true"` | 设成 `"1"` / `"yes"` / `"false"` **一律关闭** |

**②是个陷阱**：`XUI_ENABLE_FAIL2BAN=1` 看着像「启用」，实际把执行关掉了（`isFail2BanEnabled` 只认 `"true"`）。

### 5.1.1 装了 fail2ban 之后，实际执行的是什么

不是「只写日志」——两件事一起做：

1. **面板自己断连**：通过 xray API `RemoveUser` + 100ms 后重新 `AddUser`，掐掉该客户端**全部**连接。仅支持 `vmess / vless / trojan / shadowsocks / hysteria`，**其他协议只打一行 warning 就返回**。
2. **fail2ban 在防火墙层封 IP**：面板按固定格式写 `[LIMIT_IP] Email = … || Disconnecting OLD IP = … || Timestamp = …`，`x-ui.sh` 建的 `filter.d/3x-ipl.conf` 匹配它。（上游注释明确写着「log format is load-bearing … don't change the wording」。）

所以两者互补：①让超限客户端立刻掉线，②让那个具体 IP 短期内连不回来。

**给运维方的结论**：节点上装 fail2ban，且**不要**设 `XUI_ENABLE_FAIL2BAN`（或只设成 `true`）。PSP 侧推送始终正确，执行前提在节点。

### 5.2 PSP 对这条前提的探测

上面那两道闸是**节点上的事实**——一个二进制文件和一个环境变量——PSP 已有的任何一次读取都看不见它们。写入成功、读回一致、界面显示正常，然后什么也没封。所以只能主动去问。

3X-UI 3.7.0 起提供 `GET /server/fail2banStatus`，返回 `enabled / installed / usable / windows` 四个布尔量。PSP 在**已有的版本探测那一跳里顺带发一次 GET**（同一个面板、同一个已登录的会话）。该探测挂在**流量轮询**上，周期即 `cron_traffic_pull_minutes`（默认 **5 分钟**，管理员可调），而不是一个独立的定时器，把结论落在 `xui_panels.ip_limit_enforcement` 上。管理员点「测试连接」也会立刻重探一次，不用等下一个周期。

**六种状态，判定顺序是刻意的：**

| 状态 | 含义 | 判定 |
|---|---|---|
| `enforced` | 断连 + 防火墙封 IP，完整生效 | `usable` |
| `disconnect_only` | Windows：会断连，但不封 IP，对方可以立刻重连 | `windows` 且非 `usable` |
| `disabled` | `XUI_ENABLE_FAIL2BAN` 被设成了 `true` 以外的值 | `!enabled` |
| `not_installed` | 闸开着，但节点上没有 fail2ban | 其余 |
| `unknown` | 本该能回答的面板没给出答复（探测失败，或还没跑过） | — |
| `unsupported` | 面板低于 3.7.0，没有这条路由 | 404 |

三条容易被「简化」掉的规则：

1. **`!enabled` 排在 `windows` 前面。** 上游 `Run()` 在看平台之前就检查环境变量，所以一台设了 `XUI_ENABLE_FAIL2BAN=1` 的 Windows 节点同样什么都不执行。先看平台会把它报成正常。
2. **`usable` 直接采信上游，不在 PSP 侧用 `enabled && installed` 重算。** 今天两者等价，但这是上游的复合判断：以后它多加一道闸，采信它会让 PSP 跟着降级，重算则会永远宣称「生效」。
3. **`unknown` 不是好消息也不是坏消息。** 探测失败时**保留上一次的结论**，不覆盖成 `unknown`——一次网络抖动把 `enforced` 变成 `unknown`，会把运维引向一个不存在的故障。`ip_limit_probed_at` 记的是**这个结论是什么时候得出的**，不是最后一次尝试的时间，所以陈旧本身是看得见的。

**呈现在两处**：服务器列表里该节点状态下方的徽标（`enforced` 和 `unsupported` 不画徽标，理由见下），以及用户表单里填并发 IP 上限的地方——会点名那些「存得下但不会执行」的面板。指标是 `psp_ip_limit_enforcement_total{state}`，按状态计数，`unknown` 与其余并列上报：只看 `enforced` 一条线的话，一个探测已经坏掉的机群和一个健康机群长得一模一样。

**两个刻意留下的盲区**：

- **`unsupported` 不画徽标。** 低于 3.7.0 的面板没法回答，画出来就是一个永久且无从下手的告警——而运维学会忽略的那些告警，会连带着让别处真正要紧的那个也被忽略。版本一栏就在旁边，已经说明这块面板旧了。
- **`unknown` 会画，灰色。** 它的含义是「本该能回答的面板没回答」，即探测自身坏了。一个坏掉的探测器如果长得像干净机群，正是这套东西存在的理由被反过来实现了一遍。

**这里不做任何处置。** 探测只写状态、只画徽标，不改用户、不改推送、不改能力声明。能力（capability）回答的仍然是「存不存得下」——把两者合并，要么会让一块存得下的面板停止漂移愈合，要么会宣称一份看不见的执行力。

## 6. 漂移愈合

两个上限是 PSP 所有的，所以**被人在面板界面上改动必须被改回来**，而不是被跳过。它们已进入 `SyncLifecycle` 的比较集合（`lifecycleWriteReason`），因此：

- 面板值与 PSP 意图不一致 → 重推，并在 `psp_lifecycle_sync_write_reason_total{reason=ip_limit|device_limit}` 上计数
- 一致 → 仍然命中 no-op skip，不会因为多了两个字段就每周期多一次写

**但比较受能力门控**：面板**存不下**的字段被排除在比较之外。

这不是可选的优化，是必须的。一个默默丢弃该字段的面板，读回来永远是 0——若让它参与比较，skip 就**结构性地永远不可能命中**：每周期都看到差异、每周期发一次整体替换、每周期重启一次内核，**而这个值永远无法收敛**。

排除它不等于「忽略漂移」：一台没地方存这个值的面板上根本不存在漂移可言，而缺口本身已经由 §6.2 计数上报。

## 6.2 缺口是被上报的，不是被吞掉的

声明能力只解决了一半：**S-UI 上的用户设了限制，写入照样成功、就是不生效。** 这正是能力列表本该防住的失败形状，所以 `SyncLifecycle` 在推送前检查：

```
PSP 想强制某个上限  且  目标面板没有对应能力  →  psp_capability_gap_total{capability=…} 计数 + 告警
```

两个设计选择：

- **只在 PSP 真的想强制时才算缺口。** 不限的用户落在不支持的面板上不是问题，把它计进去会让这个指标失去意义。
- **计数器是持久信号，日志每（面板, 能力）只打一次。** 这个状态是稳态的——直到运维方把用户挪走或升级面板才会消失，每周期为每个受影响的客户端打一行会把别的都埋掉。

**缺口是警告，不是拒绝**：同一次写入里的 enable / 到期 / 配额，那台面板执行得好好的。

## 9. UI 上的能力提示

服务端把缺口计进 `psp_capability_gap_total`（§6.2），但**计数器不是设置这个值的人正在看的地方**。写入会成功、就是不生效——这正是能力列表本该防住的失败形状，而它在管理界面上原本是完全不可见的。

新建 / 编辑用户对话框里，两个上限字段各自在下方显示无法执行它的面板名：

```
Concurrent IP limit  [ 3 ]
Not enforceable on: probe-sui — clients placed there ignore this.
```

判定是纯函数 `unenforceablePanels(limit, servers, capability)`（`web-react/src/utils/capabilities.ts`），**规则与服务端 `reportCapabilityGaps` 刻意一致**：

- **只在 PSP 真的想强制时才算缺口** —— `limit <= 0` 一律不提示。不限的用户落在不支持的面板上不是问题，为它告警只会训练运维方忽略真正要紧的那条。
- **两个上限各判各的** —— 一台面板可能支持其中一个而不支持另一个。
- **未声明任何能力的面板算作「不支持」** —— 从未探测过、或较旧的构建都落在这里。宁可多提示：这个提示存在的意义就是拦住静默不生效的设置。

实机验证（真实浏览器驱动真实面板，建了一台 S-UI 面板——它两个能力都不声明）：上限为 0 时不提示；设成 3 之后提示出现、点名了那台面板、无 console 报错；两个字段互不干扰。

**范围上的诚实**：提示列的是**整个机队**里不支持的面板，不是「这个用户的客户端实际落在哪几台」——后者要走 用户 → 分组 → 节点 → 面板 这条链，前端此处没有。文案因此写成「落在其上的客户端不会生效」而不是「这个用户不会生效」。

## 10. 从分组继承（OU 策略）

三个额度——流量配额、并发 IP 上限、设备数上限——**默认从用户所属分组继承**，用户可以逐字段覆盖。改一次分组策略即可作用于全组，不必逐个用户编辑。

### 10.1 第三个状态，以及为什么非要有它

`0` 早就被占用了：它在两端都表示「不限」——PSP 这样编码，面板也这样读。所以一旦分组能承载策略，一个存量的 `0` 就是**歧义**的：是「不限」，还是「听分组的」？读错的后果是**给本来没有配额的用户凭空造出配额**，正是 [`traffic-floor-defect.md`](traffic-floor-defect.md) 那个缺陷换了个位置重演。

于是引入真正的三态：

| 存储值 | 含义 |
|---|---|
| `NULL` | **继承分组** |
| `0` | **明确不限**（即使分组有规定） |
| `N` | 明确为 N |

三个字段各自独立解析：`用户覆盖 → 分组策略 → 不限`。分组被删除的用户解析为不限，而不是报错或卡在旧值上——放行付费用户比误伤他们安全。

### 10.2 存量数据：`0` 迁移为 `NULL`，且只迁一次

存量的 `0` 全部转成 `NULL`（继承）。这个重新解释之所以安全，理由很具体：

> 在此之前 `0` 是表达「不限」的**唯一**方式，而且**没有分组层可供对比**——所以没有任何一个存量 `0` 能携带「不限，且刻意不听分组的」这种意图。它没有丢弃任何曾经存在过的信息。

反过来若保留为明确 `0`，每个存量用户都会静默退出分组策略，运维方设了分组配额会发现**对谁都不生效**——正是这个功能要消除的逐人操作。

**落地瞬间行为不变**：分组的新列都是 `NULL`（不作规定），继承解析为不限，正是 `0` 原本的含义。非零值原样保留为显式覆盖。

这类迁移**只正确一次**，重跑会把运维方后来刻意填的 `0` 又变回继承，所以它由 `schema_migrations` 表里的标记门控，且标记与数据改动在**同一个事务**里写入——中途崩溃不会留下「数据改了、标记没写」的可重跑状态。（`EnsureSchema` 里既有的那些回填是幂等的：它们把 NULL 归并成本来就该是的 0，重跑无副作用，因此不需要标记。）

### 10.3 生效值与存储值分开放

`domain.User` 上的 `TrafficLimitBytes` / `IPLimit` / `DeviceLimit` 是**解析后的生效值**，由仓储在加载时填好；**存储的覆盖值**在旁边的 `u.Limits` 里（`nil` = 继承）。

这么切是因为约有 100 个消费点只想要那个数字——计量循环问「这个用户的配额是多少」不该被迫先拿到分组。而它之所以**安全**，取决于一个前提：写路径是稀疏指针 DTO，**请求里没提到的字段就不写**。因此一次普通编辑（比如只改显示名）不会把继承中的用户悄悄钉死在他分组当时的值上。`TestSaveDoesNotPinAnInheritingUser` 钉住这一点，并已用变异验证——把映射改成回写生效值，该测试立刻失败。

「恢复继承」需要独立信号（`nil` 已经表示「别动」），所以用户侧有 `inherit_*` 标志、分组侧有 `clear_*` 标志，形状与既有的 `ClearExpire` 一致。

创建路径携带的是标量，**没有办法表达「继承」**，因此那里的 `0` 读作「没有意见」→ 继承。这与迁移的判断同源，理由也相同。

### 10.4 解析发生在哪

在用户仓储里，配一个分组限额缓存（TTL 30s），分组仓储每次写入都会让它失效。

每个已鉴权的请求都会加载用户，所以按次查库不可接受；而 30s 的陈旧度是可接受的，因为分组策略是**长期决定**，作用于它的东西都更慢（多分钟的轮询、每小时的邮件）。运维方编辑分组仍然**立即生效**——两个仓储共用同一个缓存实例，写入即失效，与作用域设置缓存同一套纪律。

**读不到时向「不限」失败**：因为一次数据库抖动而切断付费用户是更糟的错误，何况 PSP 自己仍在计量并停用，面板侧上限只是兜底。

### 10.5 界面

- **分组 → 策略**：三个输入框。**留空 = 本组不作规定**（解析为不限），**填 0 = 明确不限**。
- **用户编辑**：每个额度下方一个「跟随分组」勾选框。勾上时输入框置灰，但**仍显示继承到的数值**——让运维方看见自己继承的是什么，而不是一个空框。

#### 10.5.1 输入框里的数字，不是被执行的数字

表单**按用户**收一个数，两个连接上限却**按 (面板, 客户端 email) 各自独立执行**。这两个量不相等，而在此之前界面从不说明这件事——运维方读到的「并发 IP 上限 2」是一个系统并不作出的承诺。

编辑框现在按**这个用户自己的**面板给出结论（`GET /api/admin/users/:id/limit-enforcement`）。判定规则只有两条，且**不对称**：

1. **漏洞压倒倍数。** 只要有一个面板执行不了，用户走那个面板就行了——全局上限不是「更高」，是**没有**。所以有漏洞时报「整体不生效」，而不是报一个倍数；把这种情况显示成「×2」是错的，不是保守的。
2. **未知不等于正常。** 探测没有答案的面板单独归入「无法确认」，绝不与在执行的面板合并计数。让未读到的前提渲染成正常的前提，正是「静默失效的上限」得以长期隐形的原因——与 `IPLimitEnforcement.Enforcing()` 对 `unknown` / `unsupported` 的处理同一条纪律。

都不适用时才报倍数：**全局可达 = 输入值 × 该用户的面板侧客户端行数**。

**取代了原先那条全局提示**，因为旧的按整个部署的面板列表判断：部署里只要存在一台 S-UI，**每个**用户的编辑框都会警告，哪怕他在那台上根本没有客户端。创建表单仍用旧的全局提示——那时用户还不存在，没有客户端可数。

**呈现方式**：字段下方只留一个短结论（「实际可达 4」「整体不生效」「无法确认是否生效」…）加一个信息图标，**点开**才是完整原因和面板名。理由两头都成立——原因必须能拿到，否则运维方读到「整体不生效」却查不出是哪台，只能盲信或无视；但整句铺在字段下会随着输入实时改变表单高度，把布局推来推去，那是警告失效的另一种方式。用点击而不是悬停，因为触屏上没有悬停，而带面板名的正是这一半。

短标签与详情共用一个键根（`<key>` 是详情，`<key>_short` 是短标签），所以不可能只写一半；测试同时钉住两半存在、以及短标签**确实短**（≤32 字符，防的是「有人把详情粘进来了」）。颜色由 `isMisleading(verdict)` 推出，不是第二处手工判断：只有在「填的数不是生效的数」时才用警告色，`multiplied` 算在内。

**设备上限的结论是恒定的**：`device_limit_enforced_anywhere` 由服务端给出，今天在任何面板、任何版本上都是 `false`。它做成字段而不是让前端假定，是为了让它变成 `true` 的那天是一次服务端改动，而不是一场在界面代码里的搜寻。

两半事实**来源不同，且必须不同**：能力（能不能存下这个字段）问的是 pool 里的适配器；fail2ban 判定读的是**面板行**。`UpdateIPLimitEnforcement` 只写行、从不回写 pool，所以 pool 里那份是面板注册时的快照——从那里读会把「探测早就不同意了」显示成「在执行」，正是这个端点要暴露的失效。

### 10.6 已验证

对着真实数据库与真实面板跑通的完整生命周期：继承 → 改分组策略立即到达成员 → 单字段覆盖 → **无关编辑不钉死其余字段** → 分组再变、继承字段跟随而覆盖保持 → 交还给分组 → 清空分组策略回到不限。迁移双向覆盖（转换，以及第二次运行不动刻意填的 `0`），标记与「不钉死」两处均已变异验证。

> **这句话曾经越界。** 上面验证的是「改分组策略立即到达成员的**解析值**」——即 API 读出来是对的。但**推送到面板**是另一回事，而当时并没有：只有标签过滤变更会触发成员重推，闲置成员因此会无限期保留旧的上限（轮询只碰有流量的用户）。已修，额度变更现在触发同一条后台重推，且判定把 `nil` 与任何值区别对待（清空策略同样让成员停止执行，和设置一样是变更）。

### 10.7 两个容易忽略的耦合

- **抬高配额必须解除流量停用**。`UpdateProfile` 写的是 `u.Limits`，而旁边的解析值仍是编辑前的——`TrafficExceeded()` 会拿旧配额判断，于是用户仍被停用、管理员的编辑看起来毫无作用。解析因此必须发生在**保存之后、第一个读取者之前**，而不是在推送前。
- **分组策略要和用户端受同样的校验**。创建分组时漏掉校验的话，一个负数上限会被全组继承、原样推给面板，而且**连能力缺口告警都不会触发**（那个告警只在上限为正时才算缺口）。

## 11. 谁决定用户在哪个 OU：IdP 分流

§10 让 OU 承载额度之后，「这个人属于哪个 OU」就不再只是节点分配问题，而是**他拿到多少配额**的问题。原先这件事只有一个答案：`DefaultGroupSlug`，一个静态的桶，所有 SSO 用户都进去。IdP 送来的组和属性早就解析好放在 `EnsureSSOInput` 里，却只喂给角色匹配器，从没参与过 OU。

现在有一组 `group_rules`：有序、首条命中者胜、精确比对，命不中则落 `DefaultGroupSlug`。

### 11.1 为什么是独立的一组规则，不是 `SSORoleRule` 上加个字段

「谁是管理员」和「谁属于哪个 OU」很少是同一个条件。塞进同一个 first-match 列表会强迫这两个决定共享一套优先级顺序，而 `SSORoleRule.Keep` 的语义也只对角色成立。

但**匹配本身共用一份代码**（`attributeMatches` / `lookupRuleValues`）。两种规则声称「匹配方式一样」却各持一份实现，一定会漂移，而第一次分歧是静默的——一条规则对角色生效、对分组不生效，或者反过来。

### 11.2 每次登录都重新判定，不是只在建号时

这是本节最重要的一条，也是初版设计里做错、被指出后改掉的一条。

初版是「只在建号时定 OU」，理由是爆炸半径（OU 决定节点、订阅内容，现在还决定额度）。这个理由站不住：

- **角色一直是每次登录同步的**，`Keep=false` 时还会主动降级。同一套 IdP 信号在两件事上两套规则，没有依据。
- **不同步的错误方向是「权限过大」**。IdP 把某人移出支撑高级 OU 的那个组、而 PSP 永不复查，那份高配额和高级节点就是永久的。这比「被误搬」严重。

那条「升级不该悄悄搬动线上用户」的顾虑是真的，但它**不需要开关**——`ResolveGroupForSSO` 沿用了角色引擎现成的 carve-out：

| 情形 | 结果 |
|---|---|
| 没配任何 group 规则 | 规则集什么都不主张 → **谁都不动**（升级后所有存量部署正是此状态） |
| 命中，且等于当前 OU | 不变 |
| 命中，但当前 OU 被某条 `Keep=true` 的规则主张 | 保留当前（手工授予优先） |
| 命中，其余情况 | 采用命中的 OU |
| 未命中，当前 OU **无人主张** | 不动（管理员手工放的，IdP 不知道也不该管） |
| 未命中，当前 OU 被主张且无 `Keep` | 落回默认组 —— **这一条才是补上口子的那条** |

### 11.3 两条方向相反的失败策略

规则指向一个不存在的分组时：

- **建号时 → 拒绝建号。** 静默回落可能把一个本该被**限制**的人放进更宽松的默认组；而且建号是失败代价最小的时刻，还没有服务可打断。
- **登录时 → 记日志、保持原样、不阻断登录。** 存量用户因为某条规则的目标后来被删掉就登不进来，比一个陈旧的 OU 糟糕得多。这也是主流 IdP 的做法：provisioning 映射错误不阻断 sign-in。

真正该拦住这件事的是**保存时校验**：`validateSSOGroupRules` 在 PUT 落库前解析每个 slug，并点名出错的行号与 slug。不然运维方的拼写错误要由别人的登录失败来告诉他。

### 11.4 改了 OU 必须推到面板

存储行本身改不动节点上的任何东西。OU 决定入站归属，§10 之后还决定继承来的额度，所以变更走 `ResyncMembershipOrEnqueue`——和管理员手工换组同一条路。这和 §10.6 记的是同一个缺陷，只是高一层。

反过来也要成立：**没有发生迁移的登录不推送任何东西**。每次 SSO 登录都会走这条路径，逐次重推等于把 `UpdateClient` 和 Xray 重启扇出到整个机队，而什么都没变。

### 11.5 界面与文案

规则编辑器在 设置 → SSO，SAML 与 OIDC 各一份，紧挨着角色规则，同样支持拖拽排序。**目标是真实分组的下拉选择器，不是自由文本**：角色可以合法地填一个后端还不认识的字符串（角色编辑器正因如此是 freeSolo），但一个解析不了的分组 slug 有两个坏结局，且都在别人的登录时才发作。

顺带修正了三处已经不准确的文案。`0` 在 §10 之后不再表示「不限」，而是「没有意见，跟随分组」——而分组可能有配额，所以填 `0` 恰恰可能**不是**不限：

| 位置 | 之前 | 现在 |
|---|---|---|
| 自助注册默认流量 | `0=不限` | `0=跟随分组` |
| SAML 新用户默认流量 | `0=无限` | `0=跟随分组` |
| OIDC 新用户默认流量 | `0=无限` | `0=跟随分组` |

这三个默认值都在**数据库**里、由设置页管理，不在 `config.yaml`——后者自 v3.x 起只保留启动所需的监听地址、密钥与数据库连接。

### 11.6 降级前必须成立的两个条件（对抗性 review 查出）

功能第一版发布后跑 `/code-review`，查出**降级这条分支本身**有两个缺陷。两个都把「撤销权限」变成了别的东西，而且都是本轮引入的。

**一、没有配默认分组时，降级 = 发放无限额度。**

3c 分支无条件返回 `DefaultGroupSlug`。该值为空时（全新安装的状态）解析成 `GroupID=0`，而**不属于任何分组的用户什么都继承不到**——`ResolveLimits` 给出 0/0/0，也就是**流量不限、连接上限不限**。于是被 IdP 撤销的人拿到的比撤销前**更多**，正好是这条分支存在意义的反面。

后续重推还会静默成功：`ResyncMembership` 对 `GetByID(ctx, 0)` 拿到 `ErrNotFound`，而 `runUserTask` 的 `SyncTaskUserResync` 分支把 `ErrNotFound` 当作「用户已删除」并把任务标记为**成功**，旧 OU 的入站因此永远不会被摘掉。

两处修：**保存时拒绝**——有分组规则却没有默认分组的配置存不进去，因为一套能降级的规则必须有降级的去处；**运行时兜底**——`defaultSlug` 为空时不降级，保持原样。

**二、IdP 压根没发声明，被当成「明确撤销」。**

`attributeMatches` 分不清「IdP 说你不在那个组里」和「IdP 什么都没说」，而 3c 对两者一视同仁地降级。第二种情况和这个人毫无关系：Entra 在用户加入约 150 个组以上时**停止下发 `groups`、改发 `hasgroups`**；声明映射可以被改坏；新建的应用注册可能根本没配这个声明。

任何一种都会变成**机队级的权限变更**——每个 SSO 用户在下次登录时离开自己的 OU、失去它的配额与节点集——起因是一次目录侧的编辑，而做那次编辑的人根本没把它和 PSP 联系起来。

修法是把「沉默」和「否认」分开：`idpSpokeAboutGroups` 检查规则集引用的属性是否**真的出现在断言里**，没有出现就视为 SSO 没有意见，存储的分组保持不变。声明**存在但不含该组**仍然照常降级——否则这个修复就等于把功能关掉了。

**角色规则有完全相同的形状，同一轮一并修掉了。** 最初只改了分组侧，理由是角色降级掉到 `RoleUser`、代价远小于失去一个 OU 的额度与节点集。那个理由只站得住一半：代价确实小，但缺陷同源、修法现成，而「Entra 一次 group overage 就让所有靠规则拿到 admin/operator 的人在下次登录被降成普通用户」并不是小事——面板可能因为一次目录侧编辑失去全部特权用户。

判断「IdP 是否发过声」的核心因此只有**一份实现**（`idpSpokeAbout`），两种规则各自把自己引用的属性名传进去。两套规则对「什么算 IdP 说过话」如果理解不一致，会在同一个断言上朝相反方向出错，而且这种分歧是静默的——所以有一条测试专门钉住它们的一致性。

### 11.7 已验证

真实面板 + 真实浏览器：三条拒绝路径各自返回 400 并点名行号与 slug（未知 slug、空值、空分组），且**被拒绝的保存不会覆盖已存的规则**；SAML 与 OIDC 走的是同一个校验。浏览器里两条已存规则正确渲染成分组**名称**（存的是 slug），下拉里是真实分组目录 `Default / VIP / Staff`，改选后保存并回读确认落库、`keep` 未丢失，全程无 console 报错。

§11.6 的两条守卫各有解析层与服务层测试，并变异验证：删掉沉默守卫、删掉空默认组守卫、把「IdP 是否发声」恒为假（那会等于关闭降级），三者各自都让测试挂掉。

解析矩阵每个分支单测覆盖并变异验证；服务层另有测试断言 `EnsureSSO` 确实调用了它、以及面板确实被通知——两者都是能静默失效的一环。有一处变异**存活**：删掉 `len(rules)==0` 的提前返回不影响任何测试，因为「当前 OU 无人主张」那条分支会给出同样答案。该性质由两条独立路径保证，测试钉的是性质而非某一行，这一点写在测试注释里。

### 11.8 安全审查：SSO 触及的两处权限判定

对 §11 这批改动做专门的安全审查（视角与通用 review 不同：谁能控制输入、能否借此提权或阻止撤销），查出两条。第一条比这个功能本身老得多。

**一、SSO 的角色降级绕过「最后一个管理员」保护。**

管理 API 在**三条**路径上都拦着这件事——降级（`UpdateProfile`）、删除、停用——理由写在代码里：否则面板会没有人能管理。而 `reconcileSSOUser` 写的是同一个 `role` 列，却一条都没经过：它直接赋值再走 `updateUser`，那只是 `users.Update`。

后果不是理论上的。实测：唯一一个启用的管理员，IdP 那边把他移出管理员组，一次登录之后 `CountEnabledAdmins` **归零**。全新安装总会有一个带本地密码的 bootstrap 管理员兜底，但把它删掉、或者全部管理员都只靠 SSO 的部署，就是一次目录侧编辑换来一个无人可管的面板。

现在同一条件也在 SSO 路径上执行，但**拒绝的方式不同**：管理 API 返回错误即可，这里不能——让登录失败等于把人整个挡在外面，比一个过期的角色更糟。所以是**拒绝这次降级、打警告、登录照常继续**，其余角色变更不受影响。计数读取失败时**向安全侧失败**（当作「可能是最后一个」而拒绝）：判断错了的代价是一个管理员多留到下次登录，反过来的代价是数据库抖一下就没人能管面板了。

**二、沉默守卫是一个撤销绕过，而且它原本完全不可见。**

§11.6 加的守卫刻意 fail-open：IdP 没发声明时保留已存的角色与分组。这挡住了「一次目录侧意外把整个机队降级」，但代价必须说清楚——**能让声明消失的人，就能保住目录已经收回的授权**。Entra 的 group overage 由用户自己所在的组数触发，而不少组织允许自助加组。

这个取舍保留，但不能是隐形的：新增 `psp_sso_claim_silent_total{kind=role|group}`，在「配了规则、但 IdP 一个相关属性都没发」时计数。**长期高于零意味着两件事之一**：IdP 停发了 PSP 依赖的声明，或者有人正握着目录已经收回的授权。有测试同时钉住「沉默要计数」和「说了话不能计数」——后者同样重要，一个会误报的指标运维方很快就学会忽略。

> **顺带修正一处我自己的方法缺陷。** 这轮的变异验证一度报告两条变异「存活」。其中一条是假的：变异后代码**编译不过**，而我用 `grep -c '^--- FAIL'` 统计失败数，于是「没有任何测试结果行」被读成了「0 个失败 = 变异存活」——恰好反了。变异验证必须先确认变异体能编译，否则它会在最该报警的时候保持沉默。另一条是真的：计数失败那条 fail-safe 分支当时确实没有测试，已补。

## 12. 按用户的实时并发观测（2026-09-02；分级判定与可选自动暂停 2026-09-25）

> 2026-09-25 这一轮改了四件事：只判**此刻仍在连接**的地址（§12.4.3）；先排除不说明人在哪的地址（§12.4.4）；按国家 / 省 / 城市**分级**判定（§12.3）；以及一个默认关闭、按分组开启的**限时自动暂停** `geo_auto`（§12.5）。新行为由单元测试覆盖；3X-UI 时间戳的语义是按源码核对的，尚无实机记录。

### 12.1 为什么必须由 PSP 做

管理员填的上限意在约束**一个人**。下面每一个执行点约束的都是别的东西：3X-UI 的 `limitIp` 按 client **email** 计，而 PSP 会把一个用户在同一面板上按凭据分区拆成多个 email、再乘以面板数。每块面板只看得见自己那份，所以**「这个人现在用了几个地址」这个数在系统里任何地方都不存在**。

`domain.AggregateLiveIPsByUser` 就是把它算出来，在唯一持有 `(面板, email) → 用户` 映射的那一层。

**覆盖率是带着走的。** 读不到的面板让**有客户端在其上的那些用户**的数字变成**下限**而不是总数，且只影响那些用户。把下限当总数显示，会在证据缺失时读作「这个账号没问题」——这正是本文档反复记录的那种失效。指标 `psp_live_ip_users_incomplete_total` 高于零就意味着 `psp_user_live_ips` 偏低。

「读不到」的认定在 2026-09-25 补齐了两个漏洞：流量轮询从连接池里**拿不到客户端**的面板，和抓取协程**没留下任何结果**的面板，以前都被读成「回答了、没人在线」，它们的用户于是被当作完整的总数上报；现在两者都记作读不到。没有在线地址接口的适配器（S-UI）一直是读不到。

### 12.2 观测的是 IP，不是设备

数据面只看得见连接和源地址，**没有设备这个概念**。一家人共用一个 NAT 出口读作 1，一台手机在 WiFi 和蜂窝之间切换读作 2。设备身份只存在于订阅层（见 §4.1）。代码里一律说 IP、绝不说设备——把它叫作设备，就是承诺任何一层都给不出的东西，和设备上限当初「看起来在执行」是同一个错误。

反过来，同一个 IPv6 /64 里的地址算**一个源**：一台手机每隔几小时就在自己的 /64 里换一个隐私地址，逐个计数会把一台手机算成一群人（§12.4.4）。

### 12.3 判定是策略，不是规则

「同时出现在两个国家就是共享」这条朴素规则**两个方向都会错**，而且都很贵：它冤枉一个手机偶然走了运营商境外 PoP 的用户；它放过一个朋友恰好在同一国家的共享者。它还会**抖动**——一次噪声采样报警、下一次采样解除，运维方很快学会忽略这个报警。**会抖动的异常检测比没有更糟**，因为它把真信号变成了背景噪声。

所以每一个旋钮都对应一类会被误判的真实用户（`domain.GeoAnomalyPolicy`；括号里是存储键，都在 `geo_anomaly.` 下）：

| 旋钮 | 默认 | 它保护谁 |
|---|---|---|
| `Scope`（`scope`） | `city`（城市·分级） | 决定**最细判到哪一级**，更粗的层级一并判定、各用各的容错：`city` 判国家、省、城市三级，`region` 不判城市，`country` 只判国家，`off` 关闭。无法识别的存储值按 `country` 判——默认已经是最细一级，「非法值保持默认」会让一个拼写错误去判城市 |
| `MaxPlaces`（`max_places`） | 1 | **国家容错**：同时 2 个国家即超限。第二个国家可能完全正常（公司 VPN、第二住所、境外家人），所以是个数字，不是写死的 2。键名早于分级，为兼容保留 |
| `MaxRegions`（`max_regions`） | 1 | **省级容错**，只数最宽的那一个国家里的省 / 州：同一国家同时 2 个省即超限——这正是大国运营方想问的信号。家里常开的路由器 + 外省的手机也会触发它，误报多就调到 2 |
| `MaxCities`（`max_cities`） | 2 | **城市容错**，同样只数最宽的那一个国家。比省级高一格，吸收「家宽和手机运营商在同省两个城市出口」这一对，第三个城市才超限 |
| `FlagAfterPolls`（`flag_after_polls`） | 3 | 迟滞。一次噪声只到 `suspect`，不报警 |
| `ClearAfterPolls`（`clear_after_polls`） | 6 | **刻意比上升慢**，否则账号在两次检查之间踩到线下就能甩掉标记 |
| `AllowAnywhere`（`allow_anywhere`） | false | 出差账号、团队共享凭据、运维自己的测试号——**整体豁免**，而不是为他们抬高所有人的阈值 |
| `CoTravel`（`co_travel`） | 空 | 真实跨境常客（如 JP/TW 双地）。**指名这一对**比抬高容错率更诚实：第三个国家仍然会触发。**只折叠国家**，大小写不限；含 `/` 的省、城市条目直接丢弃。共享同一国家的几行合并成一组，而且是传递的：`CN,HK` 和 `HK,MO` 两行即 CN、HK、MO 算一处，与行的先后无关。折叠后的名字取用户**实际出现过**的成员里代码最小的那个，所以原因文字和自动暂停的审计记录不会写出一个他没去过的国家 |
| `MinPlacedRatio`（`min_placed_ratio`） | 0.5 | 数据库陈旧或残缺时判 `unknown`，而不是悄悄变成「全员清白」 |

自动暂停自己的几个旋钮见 §12.5.2。

**为什么要分级——v1 的「`city` 永远不做默认」已经反转。** v1 把每个地址投影成粒度上的一个不透明「地点」，再和一个阈值比，这逼人二选一：`country` 在一个国家内部是瞎的，而「同时在两个省」恰恰是大国运营方最想问的；`city` 的阈值 1 会对每一个家宽和手机在同省两个城市出口的订阅者报警，所以 v1 规定 `city` 永远不做默认。现在三级同时判、各有容错，城市容错比省级高一格，吸收的正是那一对；再加上只判此刻仍在连接的地址（§12.4.3），一个通勤者不再被读成同时在几个城市。于是默认改成了城市·分级。

几条计数规则，各堵一种误判：

- **省、城市只在最宽的那一个国家里数**（按省数、按城市数各取最宽者，并列取国家代码最小的），从不跨国相加：一个人同时在两个国家是国家那一级的事，相加会让它在省级再被算一次。
- **只定位到国家的库行只算国家这一级。** 它是一个已定位的地址——它知道的国家是真的——但从不自成一个省或城市，否则粗库会凭空造出更细的分布。
- **国家代码先转大写**再计数和折叠：库回答 `jp` 时，既不会在 `JP` 旁边多出一个国家，也躲不过同行组。
- **一条连续计数贯穿三级**，理由里写的是**最粗**的那一级：一台从邻市游荡到邻省的第二设备自始至终都是超限的，按层级分别重新计数会让它躲过去。标记锁住期间也记住当初是哪一级，锁住状态的理由会带上「flagged at the region tier」这样的尾巴。

覆盖是**按键、整值替换**：分组 > 全局，**没有用户层**。v1 这里写的「逐字段继承（`ResolveGeoPolicy`）：用户 > 分组 > 全局」从来没有生产调用方，`ResolveGeoPolicy` 已删除。每个键单独覆盖，所以一个只打开「允许任何地方」的分组不必重述粒度和迟滞。存储值 `0`（或空）表示「从未配置」，由 `GeoPolicyFromSettings` 换成出厂默认——**分组把某项覆盖成 0（或负数），得到的是出厂默认，不是全局值**；覆盖成空值或非整数则相反，设置层解析不了、跳过它，沿用全局值，这条覆盖等于没写。两者在输入框里都只是一个数字（或空白），所以对这些整数键（三个容错、上升 / 解除次数、三个暂停阈值、「连续几次才暂停」、暂停时长），分组编辑器在打开了覆盖的输入框下方注明它实际的含义：0 或负整数写「= 2（默认）」，数字是该键的出厂默认；空值或非整数写「= 全局: 4」，全局本身也没配置时写「= 全局: 2（默认）」；正整数照字面生效，不加注。没打开覆盖的行显示继承来的「全局: …」，全局没配置（空或 0）时同样写成「2（默认）」。忽略名单只有全局，见 §12.4.4。

**非法值一律向「不指控」修复**：容错率 0 会让每个在线用户（包括坐在家里的）都被标记，所以配置错误必须退化成沉默，而不是退化成对全机队的诬告。逐项是：无法识别的粒度按 `country`。其余每个数值——三个容错、上升与解除次数、可定位比例、三个暂停阈值、「连续几次才暂停」、暂停时长——存储值 ≤ 0 都按「从未配置」换成**出厂默认**，负数和 0 一样，不是夹到 1 或 0：容错 1 / 1 / 2，上升 3 次、解除 6 次，比例 0.5，暂停阈值 1 / 2 / 3，「连续几次才暂停」**6**（一个被清零的字段不能把一次采样变成一次暂停），时长 60 分钟。这一步在 `GeoPolicyFromSettings` 里（只收正数），所以 `sanitized()` 里那些夹到 1 或 0 的下限碰不到存储值，只兜底没经过它的策略。往上只夹两处：可定位比例大于 1 按 1，暂停时长超过 10080 分钟（一周）按 10080。最后，三个暂停阈值各自抬到不低于同级的标记容错——先换成出厂默认的暂停阈值也一样，若仍低于该级的标记容错就再抬上去。

### 12.4 七种状态，不是布尔

`disabled`（策略关闭）/ `exempt`（豁免）/ `unknown`（无法判断）/ `idle`（无连接）/ `clean` / `suspect`（超限但未持续）/ `flagged`（超限且持续）。

其中**只有 `flagged` 可以驱动自动响应**。`suspect` 刻意在线下——它是可见的爬升过程，藏起来会让最终的标记显得凭空出现。其余状态各自意味着「检测器不在能判断的位置上」，而它们看起来都像「零个标记」：**只盯着 flagged 那条线，无法区分一个干净的机队和一个已经悄悄停止工作的检测器**。指标 `psp_geo_verdict_total{state=...}` 按状态分标签，正是为了让分母保持可见。

判定顺序是固定的，每一步都有它的理由：

0. **距上次判定不足半个轮询周期：不判。** 这一行原样保留，不写库，也不进任何判定指标，只计 `psp_geo_samples_spaced_total`。管理员和运维员都能点的「流量看板 → 立即采集」直接调用 `PollOnce`；没有这一步，每点一下就是一次采样，连点三下就凑满「连续 3 次」，而 PSP 原生节点没有时间戳（§12.4.3），连「数据根本没变」都看不出来。定时轮询彼此相隔一整个周期，正常都会计入；但这一步只看时间、不看是谁触发的，所以定时轮询也会被跳过，至少有两种情况：一是紧跟在一次判过的手动采集之后——周期 5 分钟，T 定时判过，T+3 手动采集又判一次（已隔满 2.5 分钟），T+5 的定时离它只有 2 分钟，它判过的人全部跳过；二是把采集间隔调大到原来的两倍以上之后的第一轮——流量循环在上一轮之后已经按旧周期睡下，下一轮仍按旧节拍到来，`PollOnce` 却已读到新周期、按新周期的一半来比：5 改成 20，T+5 那一轮要求相隔 10 分钟，而 T 那一轮判过的人才过去 5 分钟，全部跳过；这一轮之后循环才换成 20 分钟，下一次判定约在 T+25。两种都只是这一轮不判，不会冤枉任何人。周期取「流量采集间隔（分钟）」，每轮现读；只有没接设置时（测试里）才是 0，即关闭。PSP 自己的时钟往回拨时也会读成「太早」——那只会暂停判定，不会冤枉任何人。
1. `disabled`、`exempt`：**不判**，而不是「判了、正常」。两者都把所有连续计数清零，暂停计数也在内，重新开始判定时不会有之前攒下的东西在等着。
2. **没有此刻在连的源，也没有被排除的源 → `idle`。** 上游窗口里只剩过期地址的也是 `idle`，理由写「no concurrent connections; N address(es) seen earlier in the upstream window」，而不是「没人」。
3. **有人在连，但每个源都被排除了 → `unknown`**，不是 `idle`：是 PSP 选择了不看（中转、共享出口、忽略名单），不是没人。
4. 地区库不可用 → `unknown`。
5. 能定位的比例低于 `MinPlacedRatio` → `unknown`。
6. 以上都过了，才按三级判超限（§12.3）。

第 2–5 步都**冻结**：标记计数和暂停计数都不动，既不累积也不消退。三条不对称的保护：

- **空闲不清除标记。** 断线一阵子再回来是最容易的规避手段。
- **`unknown` 不清除标记。** 账号不会因为我们的数据库坏了而被判无罪。
- **全部被排除也不清除标记。** 否则把流量绕进一个中转就能洗掉标记。

### 12.4.1 迟滞状态是持久化的

`geo_streaks` 表，一行一个用户：连续计数（`over` / `under` / `flagged`，标记所在层级 `tier`，暂停连续计数 `ban_over`），上一次判定（`state` / `reason` / `places`，`places` 现在只装国家），读数（窗口地址数 `live_ips`、`incomplete`、被判定的源数 `concurrent`、被排除的源数 `excluded`、结构化证据 `evidence`），以及 `updated_at`。

**必须跨进程存活**，否则整个 latch 设计失效：被盯上的账号会被一次部署自动赦免，而这个规律一旦被发现就是可以主动利用的。`tier` 和 `ban_over` 同理：丢了 `tier`，锁住的标记就说不出当初为什么；丢了 `ban_over`，每次部署都会让暂停的持续窗口从头计起。

两条写入约束，各自对应一种规避：

- **空周期不清表。** 全机队都没人在线时写一次空 map，不能变成把所有标记抹掉。
- **本周期没判定的行保留。** 每个持有客户端的用户每轮都会被判定，没连接的也会（计数冻结，这一行照写一遍，`updated_at` 随之刷新）；不在本轮结果里的，只有已经没有客户端的用户和因采样间隔被跳过的用户。把这些行删掉，等于让标记在没人判定的那一刻蒸发。

用 upsert 而不是先删后插：truncate 会让表在写入期间为空，那个窗口里崩溃就会清掉全机队的标记。四条约束各有测试，且都做了变异验证。upsert 的更新列表点名了每一列——漏掉的列会永远停在第一次写入的值上：一个月前的层级、一条永不清零的暂停计数、和旁边的判定不是同一轮的证据。

三条存储细节：

- `evidence` 是 JSON 文本列，**可空、无默认值**（MySQL 1101，`TestSchemaNoDefaultOnTextColumns` 守着）。没有证据只有一种存法——`NULL`，读作 `v: 0`，老版本写的行就是这样。轮询每轮整表读一次，那一读跳过 `evidence`（最宽的一列，轮询从来不用）；只有管理端列表读它。
- 每个地点在逗号拼接之前先去掉自身的逗号，读回来不会一分为二。
- `updated_at` 是两处判断的时钟：采样间隔（§12.4 第 0 步）和通知铃的 24 小时新鲜度（§12.5.1）。

### 12.4.2 管理端在哪看

**系统设置 → 基本设置 → 所有用户（全局默认） → 异地并发检测**：粒度、三个容错、可定位比例、上升 / 解除次数、同行组、允许任何地方、忽略名单，以及「自动临时暂停（默认关闭）」一块。粒度为「城市·分级」时，容错和暂停阈值下面各有一行「当前生效」：把 0 换算成出厂默认、把暂停阈值抬到标记容错之后，直接写出从几个开始算超限（「同时 2 个国家」本身就是那条线，「容错 1」还要管理员自己加一）。只在这个粒度下显示，因为只有它三级都判，别的粒度下这行字会承诺一条检测器根本不画的线。每个提示写的是「它保护谁」而不是「它是什么」——「省级容错 1 时，家里的路由器 + 外地的手机也会触发，误报多就调到 2」可操作，「省级的比较粒度」不可操作。

按分组覆盖在同一页左侧的范围栏，以及「分组 → 策略」里，分两个类别：「异地并发检测」（粒度、三个容错、上升 / 解除次数、同行组、允许任何地方）和「异地并发 · 自动临时暂停」（开关、三个暂停阈值、连续次数、时长）。**没有忽略名单**（只有全局）；可定位比例只能经 API 按组覆盖。

**日志管理 → 异地并发**：判定名单。每行带**依据**，不只是状态——「已标记」而没有「因为连续 3 次同时在 2 个地方，容错是 1」不构成动一个账号的理由，管理员只能盲信或无视，两者都让功能失去意义。现在每行还带：

- 层级（跨国 / 跨省 / 跨城）；
- 「仍在标记中」：标记锁住、但这一轮是 `idle` 或 `unknown` 的行；
- 「自动暂停中」及起始时间：只对 `geo_auto`。别的暂停原因是别人的决定，不标成检测器的动作；
- 地点按 国家 → 省 → 城市 分组并带数量，来自证据；老行（证据 `v: 0`）退回存储的国家列表；
- **中文界面按 ISO 代码显示中文省名**（2026-09-26）：界面语言以 `zh` 开头、国家是 `CN`、地点带着认得的省级代码 `rc` 时，省名显示成中文（广东；繁体界面经 OpenCC 是廣東）。旧的数字代码（2017 年之前的 `44` 等）同样识别。其他语言的界面、其他国家、没有代码或不认识的代码，显示地区库的英文名，和订阅日志、认证事件的地区列同一种写法。城市名不变。代码只用于显示，分组和计数仍按名字（§12.4.5）；
- **「相距约 N 公里」**（2026-09-26）：证据是 `v: 3`、且 `max_km` 大于 0 时，在地点下面单独一行显示，悬停写明它怎么算、只作参考。它**不参与判定**，也不写进「依据」那句话，英文 `Reason` 一个字节都没变：把距离放在「已标记」旁边的句子里，会被读成一个行程结论，而它不是。什么时候没有这一行、为什么没有不等于「同一地点」，见 §12.4.5；
- IP 一栏是「并发 / 窗口」，提示里拆开四类被排除的源；
- 当前**激活**的地区库只能定位到国家时，页头提示跨省、跨城两级不会触发。读不到库状态时不提示：没有「库是粗的」的证据，不等于它是粗的。

**「依据」按界面语言显示**（2026-09-26）。服务端的英文 `Reason` 一个字节都没变——日志、审计和旧的前端还在读它，每条分支的句子都有测试钉住——但每次判定另外写下一个 `why`，和判定在同一次写入里存进证据（证据从 `v: 2` 起）：分支代码（12 个，`domain.AllGeoReasonCodes()`）、句子点名的层级，以及这次判定**实际使用**的标记策略快照（粒度、三个容错、上升 / 解除次数、可定位比例）。快照必须存下来，因为策略是按分组解析的：界面若按全局设置重算，一个放宽了容错的分组会显示出厂默认的容错。其中「地区库关闭」和「可定位的太少」两条分支，只看存下的计数根本分不出来（库关闭时每个保留的源都记成未定位），所以代码不能靠推断。界面用代码、证据里的计数和行上的连续计数拼出句子：

- 本地化的句子不再列出地点，旁边的地点列已经全列了；
- 证据是 `v: 0` / `v: 1` 的老行、没有 `why` 的行、这一版不认识的代码或层级、缺了译文的键，都原样显示存储的英文；
- 两段拼成的句子（超限句加连续计数，解除句加层级）缺了开头那段就整句退回英文，不会把本地化的尾巴接在已经写了计数的英文后面；
- 一个 Go 测试要求每个代码在 zh-CN 和 en-US 两份语言包里都有对应的键，服务端加了分支而没加译文，构建直接失败，而不是永远显示英文。

老行在该用户下一次被判定时换成 `v: 3`。

排序按「谁需要一个决定」：已标记 → 锁住但闲置或无法判断 → 疑似 → 无法判断 → 正常 → 其余，同级内按最后判定时间倒序。锁存比状态活得久，排在前面才不会被埋进一堆 `idle` 里。

**通知铃**：两条仅管理员可见的条目，见 §12.5.1。

三条界面上的硬规则：

- **`unknown` 不能是绿色。** geo 库悄悄坏掉的机队，如果「无法判断」和「正常」同色，看起来就和一个干净的机队一模一样。`exempt` / `disabled` / `idle` 同理，一律不用成功色。
- **下限要标出来。** 有面板读取失败时那个数字是下限，旁边挂警告图标——把偏低的计数显示成总数，正是本文档反复记录的那种失效。
- **锁存要标出来。** 标记独立于这一轮的状态；状态列只显示「无连接」的已标记账号，如果不带「仍在标记中」，看起来就像已经解除。

接口（`GET /api/admin/geo-anomalies`，仅管理员）返回**全部状态**而不是只返回被标记的：过滤是客户端的事，因为分母必须可达。未接线时返回 503 而不是空列表——「没有可报的」和「这个构建报不了」不能长得一样。每行在 v1 之外多了 `tier`、`flagged`（锁存）、`ban_streak`、`concurrent_ips`、`excluded_ips`、`evidence`（`spots` 永远是 `[]` 而不是 `null`），以及账号当前的 `service_disabled_reason` / `service_disabled_at_ms`（服务正常时省略）。`places` 现在只装国家；`live_ips` 仍是上游窗口里的地址数。

### 12.4.3 新鲜度：「此刻在连」不是「30 分钟内见过」

3X-UI 的 `clientIpsByGuid` 返回的是**半小时的记忆**，不是此刻的画面：一个地址在它的连接关闭后还会在列表里留 30 分钟。把这份列表读成「同时」，一个通勤者的手机就同时在三个城市。

能区分「在连」和「记得」的是时间戳。按源码核对（3.4.2、3.8.5 与 main 三处机制一致）：3X-UI 每 10 秒扫一次 core 的在线表，**每一次仍发现该连接开着的扫描，都把时间戳刷成那次扫描的时刻**（unix 秒）；连接一断，时间戳就停在最后一次看见它的那次扫描。3X-UI 远程节点上的语义没有验证过。

3X-UI 适配器因此改用 `ports.LiveIPDetailReader` 读取，保留每个地址的**节点**和**时间戳**（还是同一次请求）。PSP 按节点判（`domain.FreshLiveIPs`），因为每个节点按自己的时钟扫描：

- 节点参考值 = 该节点这一轮所有地址里最新的时间戳，**包括不属于任何 PSP 用户的地址**——节点的时钟就是节点的；
- 参考值比上一轮**前进了**（或上一轮没有参考值），这个节点才算被重新扫过；
- 一个地址算「此刻在连」，当且仅当它没有时间戳，或者它的节点前进了、且它离参考值不超过 **120 秒**（12 次扫描的余量）。

由此得到的几条性质，每条都是刻意的：

- **没人走的节点整批过期。** 没人连接的节点不再被重新扫描，那一批时间戳原封不动，参考值不前进，整批读作过期——否则昨天的通勤会被当作证据重放一整天。
- **只比较同一个节点自己的时间戳**，PSP 和面板之间的时钟偏差因此无关紧要。
- **重启后的第一轮信任一次数据**：内存里没有参考值可比，退回 v1 的行为。
- **面板时钟往回拨**时，它的地址一直读作过期（`idle`），直到超过它原来最新的那个时间戳。这是安全的方向：只会暂停判定，不会冤枉人。
- 参考值只活在内存里，按 (面板, 节点) 记，有自己的锁，**按 max 合并**：定时轮询和手动采集可以重叠，慢的那一轮可能带着更旧的参考值回来，让它覆盖会使下一轮把一批没人重扫过的数据读成「前进了」。
- 时间戳的解析是宽容的：数字、小数、带引号的字符串都收，毫秒值除以 1000；解析不了的记 0（= 没有时间戳 = 在连），**绝不**因此报解码错误——那会把整块面板读成读不到。

**PSP 原生节点**只实现 `LiveIPReader`，没有时间戳，它的地址一律算作在连：在它上面窗口数就是并发数，挡住手动采集加速的只有采样间隔（§12.4 第 0 步）。

两个读数都留着：`live_ips` 仍是窗口数，`concurrent` 是真正被判定的源数。两者之差，就是记忆和被排除的地址各占了多少。

### 12.4.4 地址卫生：哪些地址不说明人在哪

每条规则都偏向排除：多排除一个地址，共享者少一个数据点；多留一个不该留的地址，诚实用户可能被读成同时在两个地方，而那正是运维方会据以动手的判定。

**源，而不是地址**（`domain.SourceKey`）。IPv4 一个地址一个源；IPv6 **按 /64 合并成一个源**。每个源拿最小的那个成员地址去查库，所以一台在 /64 里轮换地址的手机每轮查的是同一个地址，不会在两行库记录之间来回跳。证据里的网络数（IPv4 /24、IPv6 /48）**只用于展示**，从不合并源——同一个 /24 里的两户人家还是两户。解析不了的地址按原字符串算一个源：被计数，而不是被悄悄丢掉。

**四条排除，按固定优先级，第一条命中即归类**（`domain.ClassifyAddresses`），这样管理员看到的计数是稳定的：

| 顺序 | 类别 | 覆盖什么 | 为什么 |
|---|---|---|---|
| 1 | 内网 `internal` | 100.64.0.0/10（运营商级 NAT）、私有、回环、链路本地、未指定 | 这些地址定位不到地图上；CGNAT 地址还和同一个运营商网关后的陌生人共用 |
| 2 | 忽略名单 `listed` | 管理员填的 IP / CIDR | 面板不知道的中转、CDN、公司出口 |
| 3 | 本机节点 / 中转 `infra` | PSP 自己的节点与中转地址 | 经中转到达落地节点的流量带的是**中转**的地址；当成地点，中转背后的每个用户都会「同时在两个国家」——这是最常见的误报，而 PSP 自己就知道它渲染的每一个节点和中转 |
| 4 | 共享出口 `shared` | 同一时刻被 **3 个以上**不同账号持有的源 | 两个账号一个地址是一户人家；三个就是基础设施（校园网、运营商 NAT、办公室） |

一个既是私有地址、又在忽略名单上的源报为内网（更根本的理由）；三个用户经同一个中转到达报为本机中转，而不是共享出口。共享出口数的是**全机队同一时刻**的持有人，所以分类对全机队一次做完，不是逐个用户做。

**忽略名单只有全局**（`geo_anomaly.ignore_addresses`）。它刻意不在 `OverridableScopeKeys` 里，这就是「仅全局」的全部机制：一个地址是不是某人的中转，不取决于哪个分组在看。一行或逗号分隔一个，`#` 之后是注释，最多 256 条。它是异地并发里**唯一在保存时校验**的字段：`PUT /api/admin/settings/ui` 用轮询同一个解析器解析，任何一条非法就整体拒绝，并在 400 里点名每一条——因为这里的拼写错误**向放行方向失效**（本想排除的地址继续指控某人），而且下游没有任何东西能把它修回「不指控」。原文保存（只去掉两端空白），注释留得住。库里若已经存了非法条目（校验出现之前写的），轮询照样应用其中合法的条目并打 Warn，不会因为一条坏行关掉整张表。

**本机节点与中转的地址集在轮询之外维护。** 后台循环 `infra-address-loop` 启动时先刷一次——第一轮定时轮询在启动后一个周期才跑，若等自己的第一次滴答，那一轮就会把中转地址当成用户的位置——之后每 5 分钟一次。收集的是每个启用、非分隔符节点的 `ServerAddress`（不管 `HideDirect`：健康探测照样拨它，旧订阅的客户端也常常照样连），和每个启用中转的地址。字面量直接用（方括号、zone、IPv4 映射先规整）；主机名的解析结果缓存 10 分钟，同时最多 4 个、每个 2 秒。**解析失败保留上次的地址**，下次刷新重试；节点列表读不到就整套保留。停用的节点和中转**刻意不排除**：PSP 不经它路由的地址不是出口，排除它会把真在那里的用户藏起来。轮询读这个集合只是读锁下的一次 map 查找，**轮询路径上没有 DNS**。

DNS 视角是不完整的：GeoDNS、anycast 下，PSP 解析到的地址和客户端连的可能不是同一个。共享出口规则和忽略名单是它的后备。

**证据里永远没有 IP 地址，也没有坐标**（`domain.GeoEvidence`，当前 `v: 3`）：最多 12 个地点（按源数降序；每个带省级代码 `rc`，没有时省略），四类排除各自的源数，过期地址数，定位覆盖（已定位 / 未定位 / 带省 / 带城市），网络数，三级的分布和各自所在的国家，分布里相距最远的两个并发来源之间的距离 `max_km`（§12.4.5；为 0 时省略，`v: 2` 及更早的行没有它），以及判定的 `why`（§12.4.2；只有枚举和数字——分支代码、层级、粒度，几个整数阈值，和一个浮点的可定位比例 `min_placed_ratio`；`v: 0`、`v: 1` 的老行没有它）。

```json
{"v":3,
 "spots":[{"cc":"CN","region":"Guangdong","rc":"GD","city":"Shenzhen","n":2},
          {"cc":"CN","region":"Hunan","rc":"HN","city":"Changsha","n":1}],
 "excluded":{"shared":1,"listed":0,"infra":2,"internal":0},
 "stale":21,
 "coverage":{"placed":3,"unplaced":0,"region_known":3,"city_known":3},
 "networks":3,
 "spread":{"countries":1,"regions":2,"region_country":"CN","cities":2,"city_country":"CN","max_km":540},
 "why":{"code":"suspect","tier":"region","scope":"city","tol":{"countries":1,"regions":1,"cities":2},
        "flag_after":3,"clear_after":6,"min_placed_ratio":0.5}}
```

例子里深圳与长沙两个中心相距 642.06 公里，两边的精度半径各 50 公里，减去之后 542.06，取整为 540。

### 12.4.5 距离与省级代码：只作参考

> 2026-09-26。从 authcore v0.5.0 起，地区库的一次查询除了名字，还带回省级代码、网络的坐标和库给出的精度半径。这一版拿它们做两件**只显示、不判定**的事：中文省名（§12.4.2）和并发来源之间的距离。`EvaluateGeo` 不读距离，有测试把 0 和 20020 公里下的判定钉成一样。

**省级代码 `rc`** 取自库的 `subdivisions[0].iso_code`，即 ISO 3166-2 去掉国家前缀的那段（`CN-GD` 里的 `GD`）。

- `domain.NormalizeRegionCode` 去掉两端空白，只接受 1–3 个 ASCII 字母或数字，再转大写；别的一律丢弃（`CN-GD`、`GUAN`、非 ASCII），界面退回名字。先查 ASCII、后转大写是有意的：Go 的 `strings.ToUpper` 把 `ſ` 变成 `S`、`ı` 变成 `I`，顺序反过来 `gſ` 就成了 `GS`（甘肃）。丢弃而不是修补，最坏只是显示英文名；修补可能显示一个错的省。
- **它是显示属性，从来不是键。** 地点、省、城市、三级的分布和判定仍按（国家，省名[，城市]）分组，和没有代码时一模一样。同一个省的几个来源给出不同的代码（库的缺陷）时取字节序最小的那个（`PreferRegionCode`），同一个省每轮只显示一个代码，和来源的先后无关。有测试把「没有代码 / 同一个省两个代码 / 只有部分来源有代码」三种输入下的观测和判定钉成一样。
- 没有省名的来源没有代码：代码是省的名字，没有省就没有东西可叫。
- 代价：按名字分组，就意味着库在窗口中途改了一个省的名字，照样会多出一个省（§13.3）。代码没有解决这一点，也不打算解决——按代码分组会改变判定。
- MaxMind 把香港、台湾作为国家（`HK`、`TW`），澳门按同一条 ISO 3166-1 规则也是（`MO`），所以它们照旧显示国家代码；代码表里收了这三个，只在某个库把它们归到 `CN` 之下时才用得上。

**距离 `max_km`**：此刻同时在连的来源里，相距最远的那一对。

- **哪些来源参与**：排除之后留下的（§12.4.4），定位到了国家，**并且定位到了国家之下**（有省，或者只有城市也算），库还给了有效的坐标。
- **怎么算**：每一对的有效距离 = max(0, 球面距离 − 两边的精度半径)，球面距离按半正矢公式、地球平均半径 6371 公里，跨 180° 经线的一对不需要特殊处理；所有对里取最大，按 10 公里四舍五入。**先减半径再取最大**，而不是先挑最远的两个中心再减：最远的中心往往是最含糊的记录，那样算出来的是含糊，不是距离。
- **只定位到国家的来源不参与**，理由和省、城市两级一样：粗记录不能制造更细的分布。它还坐在国家的中心点上——MaxMind 自己的测试数据把只到国家的中国网络放在 (35, 105)、半径 100 公里——和一个半径 20 公里的深圳来源配对，读出来是 1520 公里；换成不给半径的库，是约 1640 公里。一个人就这样和自己相距一千五百公里。
- **每个用户每轮最多配对 256 个不同的点**。超过时按点上的来源数降序、再按纬度、经度、半径升序取前 256 个，结果是一个确定的**下限**，宁可少报。真实账号远到不了这个数，上限只是让一个病态账号拖不慢轮询（256 个点是 32,640 次距离计算）。
- **最远的那一对可能不在列出的 12 个地点里**：地点列表按源数截断，距离按全部的点算。
- **按库区分**（authcore 的说明）：GeoLite2 / GeoIP2 City 四项都有。DB-IP City Lite 有坐标、没有半径，距离就是两个中心之间的直线距离，可能偏大（只到省的记录坐在省的中心）；它的省级代码只在记录带 `iso_code` 时才有。ipinfo Lite 和国家级的库什么都没有：不显示距离，也没有中文省名。
- **0 或缺省不等于「同一地点」。** 在 `v: 3` 上，缺省的意思是可配对的点不到两个——包括根本没有查库（粒度 `off`、地区库不可用）和库不给坐标——或者每一对减去半径之后都不到 5 公里、取整为 0（最常见的是都落在彼此的精度半径之内）。在 `v: 2` 及更早的行上，它的意思是「没有记录」。所以界面只对 `v ≥ 3` 且大于 0 的值显示。
- 坐标只活在一次 `ObserveGeo` 调用里，落库的只有取整后的公里数（§13.7）。

**为什么订阅多地（§13.3）不带距离。** 算起来不贵，也不带地址，照样不做：

- 那是 7 天的窗口。几天里拉取地点之间的最远距离量的是出行的范围，不是同时；放在「已标记」旁边，正好引出这一版刻意不做的「不可能的行程」读法。
- 移动网络的出口按网关定位，常常定位到号卡所属的省（§13.3，未实测），省与省之间的距离量的是网关，不是人。
- 中文省名已经给出了省级判断需要的尺度。
- 将来真要在那里放距离，有用的是互不相连的两组之间的**最小**距离，而不是最大值；到时候拿数据定。

**「不可能的行程」检测没有做**，推迟到有数据再决定。它需要的是按时间排序的（时刻，位置，半径）序列：

- 订阅拉取（`sub_logs`，默认保留 7 天）和面板登录（`auth_events`，默认 90 天）本来就有地址和时间，可以像登录国家（§13.6）那样每轮在内存里重新定位、用完即丢，不需要新的落库。
- 并发轮询的样本需要跨轮的状态：要么每个用户一份只在内存里的上一轮位置（重启即丢，对一个只观测的信号可以接受），要么把粗网格落库——后者放松了「不落库坐标」这一条，需要单独决定。
- 还得定下几个参数：库不给半径时怎么办（给一个下限，比如 50 公里，或者跳过这一对——否则城市中心的抖动会读成移动）；最大合理速度（约 900 km/h 的航空速度，加上机场的固定余量）；最小时间间隔（否则很短的间隔除出巨大的速度）；最小距离；与本节相同的排除；还有地区库更新会移动中心点。
- 做不做，看 `psp_geo_spread_km{state}`（§12.6）：并发距离按判定状态的分布——诚实账号有多常同时出现大距离（移动网关、分流），多常被半径吞掉（0 那一档）。连续样本之间的速度这一版不收集；需要的话，拿一份数据库副本里的 `sub_logs` / `auth_events` 和同一个 mmdb 离线算，不必给 PSP 加任何落库。

**没有实测的**：真实 GeoLite2 City 库里中国各省用的是哪一套代码，没有逐条列举过（手头没有 City 库）。已知一次真实查询返回的是字母代码（`ZJ`），MaxMind 自己的测试库把唯一一条中国省级记录写成数字代码 `22`（吉林），两种都认。DB-IP 的中国代码、中国网络在 GeoLite2 里真实的半径分布（测试数据里一律 100 公里；半径普遍这么宽的话，很多行会是 0，也就不显示）、移动网关的定位，同样未实测。不认识的代码只会退回英文名，不会显示一个错的省。

### 12.5 响应：默认只观测，可选限时自动暂停

嫌疑不是证据。分割隧道、公司 VPN、代理链、在国外的家人——都会**诚实地**产生这个信号。在不知道真实误报率的情况下武装自动动作，就是把付费用户锁在门外的标准做法。

所以**默认只观测，并在通知铃里提醒管理员**。唯一的自动动作 `geo_auto` 默认关闭、按分组开启，并且每一步都可逆：有时限、到时自己解除、从不覆盖别人的决定、管理员随时能恢复。

#### 12.5.1 通知铃（仅管理员）

| 条目 | 计数 | 何时消失 |
|---|---|---|
| `geo_anomaly`：「N 个账号被标记为异地并发」 | **标记锁住**、且 24 小时内被判定过的账号 | 后续判定解除了标记，或这一行 24 小时没有再被判定 |
| `geo_auto_suspended`：「N 个账号因异地并发被自动临时暂停」 | 服务原因是 `geo_auto` 的账号 | 到时自动解除，或管理员恢复 |

- 数的是**锁存**，不是这一轮的状态：`idle` 和 `unknown` 冻结连续计数，一个已标记的账号断开连接不能因此从铃里消失。被判定的用户每轮都会重写一行（§12.4.1），所以 24 小时这道界只滤掉检测器**不再判定**的行：用户没了客户端，或者轮询本身停了——后者由诊断页的 `poll_dead` 报告，不归这里。
- 服务原因 `geo_anomaly`（管理员手动的地理暂停）不计入第二条：铃报告的是自动化做了什么，不是某人刚刚自己做了什么。
- 两条都是**单条带计数**（和 `login_security` 一个形状），不是一人一行。每个打开的管理页每分钟都在拉这个接口，一人一行会把名字放进去、每行一次用户查询，库一坏就是四十行的铃。铃的任务是「去看异地并发页」，名单和依据在那一页。
- 两条都**仅管理员**：接口对运维员可见，处理器会剔除仅管理员的条目并重算角标——和异地并发页只给管理员是同一个理由。点击都打开「日志管理 → 异地并发」。
- 数据源可以不接线；计数失败打 Warn、跳过这一条，不会让整个铃变空。

#### 12.5.2 可选：`geo_auto` 限时自动暂停

开关和阈值都在 `geo_anomaly.` 下，**全部可按分组覆盖**——这正是给一个组单独武装、或给一个装着已确认误报的组单独解除的方式：

| 键 | 默认 | 含义 |
|---|---|---|
| `ban_enabled` | 关 | 开关 |
| `ban_max_countries` / `ban_max_regions` / `ban_max_cities` | 1 / 2 / 3 | 暂停阈值，含义同三个容错，各自自动抬到不低于同级的标记容错 |
| `ban_after_polls` | 6 | 连续几次超过暂停阈值才暂停（5 分钟一轮约 30 分钟） |
| `ban_duration_minutes` | 60 | 暂停时长，1–10080（7 天） |

**什么时候到期**（`EvaluateGeo` 的 `BanDue`，以下同时成立）：

- 该用户所在分组的生效策略开了 `ban_enabled`；
- 这一轮的判定是 `flagged`——只有它能驱动自动响应（§12.4）；
- 这一轮的样本超过**暂停阈值**，默认即同时 2 个国家，或同一国家 3 个省，或 4 个城市。暂停阈值不低于标记容错，所以超过暂停线一定也超过标记线：没有人会因为一个标记本身认为正常的分布被暂停；
- 连续 `ban_after_polls` 次被判定的样本都超过暂停阈值。暂停计数是**单独的一条**：介于标记容错和暂停阈值之间的样本保住标记计数、打断暂停计数。「持续」必须是连续，否则三次里被看见两次的共享者，迟早会因为从未持续过的证据被暂停。被采样间隔跳过的样本不算；`idle` 和 `unknown` 冻结它；豁免和关闭清零它。

**到期即消耗**：计数归零。被暂停的用户会变成 `idle`，`idle` 冻结计数，不消耗的话，解除后的第一个超限样本就会立刻再暂停一次。

**谁不会被自动暂停**：只有服务**确实在跑**的账号才有资格——服务轴上没有任何原因，且 `AccessSnapshot` 说服务正常。这排除了：账号被停用的；已到期的；**实时算出**已超流量的（`geo_auto` 在 `AccessSnapshot` 里排在到期和配额前面，暂停他们会把真实状态藏起来，用户和管理员都只会看到「已暂停」）；处在紧急访问窗口里的（那是一份服务承诺，检测器没有资格打破）；以及被任何别的原因暂停的。不符合资格的到期暂停照样被消耗，计为 `skipped_held`。

**在哪一步执行**：轮询末尾的 Phase 4（`enforceGeo`），**在计量数据落库之后**，每一轮都跑，不管这一轮读没读到在线地址——解除只取决于时钟。两种转换都要在线推送到用户所在的每块面板，都要拿 `ResyncMembership` 也在用的那把每用户锁；放在落库之后，它们就拖不慢这一轮流量的持久化。先解除、后暂停：一轮撞上上限时先放人再抓人。

**每轮上限各 20**：

- 暂停：按用户 ID 从小到大取前 20 个，结果是确定的；其余**延后**——把他们的暂停计数放回阈值，下一个超限样本就会再次到期，计为 `deferred`。不符合资格的在截取之前就被剔除，一群已被暂停的用户占不掉名额。
- 解除：只数**已到期**的（否则二十个更早开始的 7 天暂停，会让一个到期的 60 分钟暂停一整周都排不上），暂停最久的优先；其余下一轮再解，计为 `lift_deferred`。

**轮询被取消时**（管理员关掉了「立即轮询」的页面、请求超时被前端放弃、应用正在关闭）：

- **不再开始新的转换**，每次转换之前都检查一次。还没轮到的解除下一轮再解，计为 `lift_deferred`；还没轮到的暂停按上限延后的同一方式处理——把这一轮 Phase 1b 存下的那一行写回去，只把暂停计数放回阈值，下一个超限样本就会再次到期，计为 `deferred`。不这样做的话，它们会在已取消的上下文上各自失败成 `*_error`，暂停那一侧还会丢掉已经消耗的计数。
- **已经写入的转换会做完**。条件写成功之后，重新读行、推送到各面板、推送失败时排队的 `user_push_config` 重试，都在与调用方取消脱钩、但有上限的上下文上完成（推送 2 分钟，排队另给 30 秒，推送用完了自己的时间也不会连累排队）；审计行和上面那次写回同样如此（各 30 秒）。否则一次解除会让 PSP 各处都显示「服务正常」，而上游客户端仍是停用的、也没有任何重试在排队，只能等对账的兜底（默认最长约一小时）；暂停那一侧则反过来放行。

**写入是条件写，从不覆盖别人的决定。** 暂停只在服务原因为空（`''` 或 `NULL`）时写入（`SetServiceStateIfClear`）。谓词写在 `UPDATE` 本身里，而不是先读后写——先读后写会被下一个写入者抢在中间。所以管理员的暂停、被拦截客户端、人工的 `geo_anomaly`、配额暂停，一个都不会被替换；输了就计 `skipped_held`，不发邮件、不推送、不写审计。写入在每用户锁之内，并且写入那一刻持有紧急访问锁：紧急访问的授予要么先看到 `geo_auto` 而拒绝，要么暂停先看到授予写下的原因而跳过。没有这把锁，一次授予可以在两者之间把 `geo_auto` 换成 `traffic_exceeded`，而下一次周期滚动会把后者解除。

**用户看到什么**：

- **面板照样能登录**：这是服务轴，不是账号轴，用户仍可以登录门户自助。
- 存下的说明是中文（后端不知道读者用什么语言），写分布和时长，**不写任何地点**，例如「检测到账号同时在同一国家的 4 个城市使用，代理服务已临时暂停，约 60 分钟后自动恢复」。地点只留在管理端（日志、审计、异地并发页）。分钟数是**施加时**生效的时长；之后改时长只改变何时解除，不改这段文字。
- 门户对 `geo_auto` 有自己的提示（2026-09-26）：标题「服务已临时暂停」、警告级别（它会自己解除），不再和管理员的暂停共用「服务已暂停」。**中文界面**的正文仍是上面那段存下的说明，它写着分钟数；**其他语言的界面**显示本地化的通用说明（「检测到账号在多个地区同时使用……到时会自动恢复」），不写分布、时长或地点——以前英文读者看到的整段说明是一句中文。管理员手动暂停（`service_manual`）写的备注照旧原样显示，不分语言。邮件不变，仍是中文。
- 暂停邮件（「检测到账号在多个地区同时使用，代理服务已临时暂停，到时会自动恢复；如有疑问请联系管理员」）**每个账号每个 UTC 日最多一封**，其他原因仍按分钟去重：检测器按时解除，持续共享的人不久又被暂停，按分钟去重会整天每个周期发一封。代价是明示接受的：去重槽位是至多一次，当天第一封若 SMTP 失败，它排队的重试会发现当天已被占用，那天就不再补发。
- **自动解除不发恢复邮件**——暂停邮件已经说了会自己恢复。管理员手动恢复照常发恢复邮件。

**解除只看时钟，不看判定**：服务原因是 `geo_auto`，且 `service_disabled_at` 加上该用户分组**当前**生效的时长已经过去（没有时间戳的视为立即到期）。

- 用的是当前时长，不管 `ban_enabled` 现在还开没开：关掉开关只停止新的暂停，不能把进行中的困住；改时长也作用于进行中的暂停。
- 这一轮**读不到**该用户分组的设置（例如一次数据库抖动）时，不解除，留到能读到的那一轮再算，计为 `lift_deferred`，并记一条 Warn。读不到时判定退回出厂默认是安全的方向（出厂默认不开自动暂停，最多让暂停晚到，不会造成暂停），拿它给暂停计时却会提前放人：分组存的是 24 小时，60 分钟就解除了，之后也没有任何东西把它补回去。
- 轮询开头的用户快照只负责**提名**；决定是在每用户锁下**重新读这一行**之后做的，截止点是「现在 − 时长」：一个被管理员恢复、又被另一轮并发轮询重新暂停的用户，时间戳晚于截止点，会被拒绝——**更新的暂停永远不会被旧快照解除**。清除本身也是条件写（原因仍是 `geo_auto` 才清），读和写之间落下的管理员决定同样不会被撤销。到期判断在 Go 里做而不在 SQL 里，因为 SQLite 把这个时间戳按写入方的时区存成文本。
- 解除的延迟最多是时长加一个轮询周期（撞上每轮上限时再多一轮，读不到分组设置的每一轮也再多一轮）。

**审计**：执行者 `geo-detector`，动作 `geo_auto_suspend`（之后：层级、带地点的理由、时长分钟）和 `geo_auto_lift`（之前：暂停时刻，没有时为 null；之后：时长分钟），都带时间。没有发生的转换只计数，不写审计。施加时另有一条 Warn 日志 `geo auto-suspension applied`。

**管理员能做什么**：

- 在「用户管理」里恢复。运维员也可以，和 `geo_anomaly` 一致（运维员看不到异地并发页和这两条铃）。每一次人工恢复 `geo_auto` 都计为 `lifted_admin`：它和 `suspended` 的比值就是自动化的误报率。
- **不能手动设置 `geo_auto`**：设置服务状态的接口对它返回 400，人工的地理暂停请用 `geo_anomaly`。`geo_auto` 由检测器从头到尾独占：它的按时解除认的就是这个原因，手写一个会变成一个悄悄到期的「人工」暂停，还会污染误报计数。
- **恢复之后仍持续超限，会再次被暂停**（再攒满 `ban_after_polls` 次）。PSP 没有用户层设置，所以没有按人豁免：确认是误报的账号，请移进关闭了自动暂停、或允许任何地方的分组。
- 一次失败的暂停写入（`suspend_error`）同样消耗了计数，要再攒满 `ban_after_polls` 次才会再次到期。

两种地理暂停的区别：

| | `geo_anomaly` | `geo_auto` |
|---|---|---|
| 谁写 | 管理员（一个人的决定） | 只有检测器 |
| 谁解除 | 管理员 | 到时自动解除；管理员也可以 |
| 暂停邮件 | 「……管理员已暂停服务……」，按分钟去重 | 「……已临时暂停，到时会自动恢复……」，每天最多一封 |
| 恢复邮件 | 有 | 自动解除没有，管理员恢复有 |
| 通知铃 | 不计入 | `geo_auto_suspended` |
| 人工恢复 | 不计数 | `lifted_admin` |
| 用户侧状态 | 已暂停（`manual_suspended`），原因不同 | 同左 |

#### 12.5.3 硬性暂停优先于配额与紧急访问（地理之外的行为变化）

`geo_auto` 能按时解除的前提，是周围的机制不会先替换或解除它。v1 时它们会，而且对管理员自己的暂停早就会——这一版一并修掉，**影响超出地理**，发布说明必须写。

硬性暂停（`domain.HardServiceHold`）= `blocked_client`、`service_manual`、`geo_anomaly`、`geo_auto`，正是 `AccessSnapshot` 在查看紧急访问窗口**之前**就返回的那几个原因，有测试把这个谓词钉在这条行为上。优先级：账号锁定 > 硬性暂停 > 紧急访问 > 到期 > 配额。

- **配额不再覆盖硬性暂停**：轮询发现超额时不再把它换成 `traffic_exceeded`（换了的话，下一次周期滚动会把它当配额暂停解除——管理员的暂停就在月初蒸发了），也跳过配额下限推送（上游客户端本来就是停用的）。
- **周期滚动不再解除硬性暂停**：以前单凭遗留的账号轴标记 `AutoDisabledReason=traffic_exceeded` 就会触发恢复，而恢复会清掉服务原因，不管它是什么。
- **管理员改用量**（`SetPeriodUsage`）照常保存用量，但不再用配额原因替换硬性暂停。
- **`SetServiceSuspendedAndSync` 在新读出的行上再查一次**：配额原因遇到硬性暂停返回 `ErrConflict`，不写、不发邮件、不推送；轮询和改用量把它当「已被暂停」而不是错误。只拒绝配额：管理员或被拦截客户端策略用一种暂停换掉另一种，仍然是更新的主动决定。管理员请求把一个已被硬性暂停的用户设成 `traffic_exceeded`，现在得到 409，而不是把暂停替换掉。
- **紧急访问在硬性暂停下不可用**：状态为 `service_held`，`UseEmergencyAccess` 在写任何东西之前就拒绝。否则一次授予会花掉一次次数、什么也恢复不了，还会把暂停换成 `traffic_exceeded`，被下一次周期滚动解除。

**残余竞态**（明示接受，都需要几件事恰好同时发生）：

- 一次配额写入仍可能落在 `SetServiceSuspendedAndSync` 读行与写行之间的那几毫秒里。这条路径（管理员与配额）从来不拿每用户锁，要堵上得把它也改成条件写。
- 一次由过期轮询快照驱动的周期滚动恢复，在「管理员恢复 + 另一轮并发轮询重新暂停」之后，仍可能清掉一个新的 `geo_auto`。
- 管理员和配额路径与 `ResyncMembership` 不互斥（原本如此）；地理的两个方法拿每用户锁，下一次下限推送或愈合会收敛漂移。

### 12.7 升级与降级

不需要数据迁移。AutoMigrate 给 `geo_streaks` 加五列（`tier`、`ban_over`、`concurrent`、`excluded`、`evidence`），老行读作 `""`、`0`、`0`、`0` 和 `v: 0`，异地并发页对它们退回存储的地点列表。没设置过的键取出厂默认；`ban_enabled` 默认关闭，所以在管理员主动开启之前，**不会自动暂停任何人**。

判定会变。升级前先看一眼 `GET /api/admin/settings/ui` 和每个分组的覆盖：

| 存储的 `scope` / `max_places` | 升级前 | 升级后 |
|---|---|---|
| 未设置（`""`） | 只判国家，同时 2 个国家超限 | **城市·分级**：同时 2 个国家，或同一国家 2 个省，或 3 个城市即超限。疑似和已标记会变多，而且进通知铃 |
| `country`，N | 同时 N+1 个国家超限 | 层级不变，另加新鲜度与地址排除 |
| `region`，N | 同时 N+1 个省超限 | 省级改看 `max_regions`（默认 1），国家看 N。**N > 1 时把 N 抄到 `max_regions`** |
| `city`，N | 同时 N+1 个城市超限 | 城市改看 `max_cities`（默认 2），省级按默认 1 一并判，国家看 N。**重新设定 `max_cities` 与 `max_regions`** |

另外几条：

- `places` 现在只装国家；老行在下一次被判定之前仍显示旧值。
- 同行组里含 `/` 的条目会被丢弃。v1 会把条目整体转大写，而库里的省、城市名保留原样的大小写，所以这类条目实际上匹配不到（除非库里的名字恰好全是大写）。
- 每次重启（包括这次升级）后的第一轮轮询信任一次在线地址数据（§12.4.3）。
- 进程开始定期解析节点与中转的主机名（每 5 分钟刷新一次地址集，解析结果缓存 10 分钟；只解析，不拨号）。
- 硬性暂停的行为变化见 §12.5.3。

**降级之前**，先恢复（或等它自动解除）所有 `geo_auto` 用户：不认识这个原因的旧版本，`AccessSnapshot` 会一路落到「正常」：订阅照常下发，下一次推送就把上游客户端重新启用。新加的五列留在表里无害——AutoMigrate 从不删列。

**省级代码与距离（2026-09-26，§12.4.5）**：

- 不需要迁移，没有 DDL。证据在每个用户下一次被判定时整行重写成 `v: 3`。轮询不再看见的用户（已经没有客户端的），行一直停在 `v: 2` 或更早：没有距离、省名显示英文——这是对的，它的意思是「没有记录」。
- 订阅日志、审计日志、认证事件三个接口里的 `region` 对象**一个字节都没变**：`domain.GeoLocation` 新加的代码、坐标和半径都是 `json:"-"`，有测试钉住只输出原来的四个键。
- `psp_geo_spread_km` 在第一次有用户带着两个以上可配对的来源时出现；每次重启、每次重置都从零开始。
- **降级**：旧版本用普通的 JSON 解码读 `v: 3` 的证据，跳过它不认识的 `rc`、`max_km`（更早的版本还跳过 `why`），于是省名显示英文、不显示距离；它的轮询把被判定的行重写成它自己的版本。指标随之消失。

## 13. 只提示的风险信号（2026-09-26）

> 四个新信号——订阅多地、设备数、用量变化、登录国家——每小时按账号算一次，结果只给管理员看：**不暂停、不禁用、不修改任何账号，也不通知账号本人**。同一轮还改了 §12 的两处显示：异地并发页的「依据」按界面语言显示（§12.4.2）；门户上的 `geo_auto` 提示有了自己的标题和警告级别，每种语言都是，非中文门户的正文另换成本地化的通用文字（§12.5.2）。新行为由单元测试、组装后的应用级测试和前端组件测试覆盖，没有实机记录；x-hwid 的请求头名和哪些客户端会发送它、中国移动网络的省级定位精度，都**没有实测**。

### 13.1 为什么需要：§12 看不见走中转的用户

§12 的异地并发检测（下称 v2）判的是代理的实时连接。经中转到达的流量带的是中转的地址，而中转地址按 `infra` 排除（§12.4.4）——排除是对的，否则中转背后的每个用户都「同时在两个国家」。代价是：**一个始终经 PSP 中转接入的用户，每个源都被排除，永远读作 `unknown`**。一个以中转为主的机队，v2 对其中大多数人是瞎的。

订阅拉取不一样。客户端更新订阅通常直接请求面板，不经它自己代理的中转，所以 `sub_logs` 里的来源地址就是客户端所在的地方，不管它平时的流量走不走中转。`sub_logs` 本来就记着地址、UA 和客户端类型（默认保留 7 天）；每个客户端按自己的计时器更新订阅（`Profile-Update-Interval`，默认 24 小时——`sub.go` 里「每个活跃客户端每几分钟拉一次」的旧注释已更正），所以这份数据是**按天**的，信号也按天判。本节（下称 v3）在它之上做了两个信号（订阅来源的省份 13.3、客户端声明的设备 13.4），再加两个不看来源地址的：自己跟自己比的用量（13.5）和面板登录的国家（13.6）。

**刻意没做的**：任何信号都不触发自动动作（将来要做，就按 `geo_auto` 的路子给它单独的原因代码和按分组开启）；不按 x-hwid 执行设备上限，也不回 `x-hwid-*` 响应头；不做「不可能的行程」检测；没有按人确认、忽略或手动重算。

### 13.2 四个信号，七种状态

| 信号（`kind`） | 界面名 | 数据源 | 窗口 | 问的是什么 |
|---|---|---|---|---|
| `sub_spread` | 订阅多地 | `sub_logs` 的来源地址 | 最近 7 个自然日（含今天） | 同一个国家里，有几组互不相连、反复出现的省份 |
| `devices` | 设备数 | `sub_logs` 里客户端声明的设备 | 同上 | 反复出现的设备有几台 |
| `usage_shift` | 用量变化 | 小时流量汇总 | 今天之前的 35 个自然日 | 最近 7 天的日用量是否持续高于自己的基线 |
| `login_country` | 登录国家 | `auth_events` 里成功的登录 | 回溯 90 天，判最近 7 天 | 最近有没有从一个新国家登录面板 |

前三个信号的「天」是面板时区的自然日（`paneltz`），DST 那天也算一天；在零点拨快的时区（智利 `America/Santiago`、古巴 `America/Havana`），拨快那天没有 0 点、从 1 点开始，也照样是完整的一天——日期按当地正午定位，读库的边界取那天真正的第一刻。登录国家的 7 天和 90 天是从本轮时钟往回数的整 24 小时——登录时间是时刻，不是日期。

每个（用户，信号）存一行：v2 的七种状态之一（§12.4）加一个代码（`code`），说明判定停在哪条分支。代码的全集是 `domain.AllRiskCodes()`，每个信号的判定器都有测试要求它产生的代码恰好是这份列表；另一个 Go 测试要求每个（信号，代码）在两份语言包里都有句子。**没有总分，也没有信号之间的升级**：四个「疑似」是四行给管理员读的东西，不是一个关于这个账号的结论。和 v2 相同的几条规则：

- `unknown`（无法判断）、`idle`（无数据）、`exempt`、`disabled` 都不是「正常」，界面不用成功色（和异地并发页共用一张颜色表）。
- 非法设置向「不指控」修复（13.9）。
- **数据源这一轮读不到，受它影响的信号保留上一轮的行**，而不是拿残缺的数据重判——一个旧结论好过一个从缺失数据里推出来的新结论。

**运行方式**：后台循环 `risk-signal-loop`，启动后 2 分钟跑第一轮，之后每小时一轮。间隔是常量，不是设置：信号是按天的尺度，一小时足够新鲜，而且都不在轮询路径上。关停时由 `bgWG` 排空。每一轮从头到尾持有 `operationGate` 的读许可，和流量轮询、对账、健康检查、同步任务队列这些后台循环一样。这道闸唯一的独占方，是把一台已有的 3X-UI 服务器在线转换成 PSP 原生节点的那一步（节点回调 `POST /api/node-bootstrap/complete`，审计动作 `node_backend_conversion`，见 `docs/server-migration.md`）：它先等所有已放行的操作做完、新来的都排在它后面，然后才改写这台服务器保存的后端。风险计算不访问上游面板，但转换撞上正在跑的一轮时，也要等这一轮结束；转换这一步整体限时 60 秒（等待也算在内），超时即以 409 失败。每一轮：

1. 读全局设置（面板时区、各项保留天数、忽略名单、采集开关）。读不到就什么都不写，计 `error`。
2. 分页列出全部账号，每页 100（同一个账号在两页里出现只算一次）。
3. 删掉已删除账号留下的行（失败只打 Warn，照常往下走）。
4. 每个分组解析一次策略：风险策略，以及 `sub_spread` 和 `login_country` 沿用的异地并发策略（和轮询走同一个映射 `UISettings.GeoPolicySettings`、同一套默认值，所以一个分组的容错在两边是同一个意思）。**一个分组的设置读不到，这个组的账号这一轮不写行**、保留旧行，计 `partial`——拿全局或默认策略去判它们，等于把管理员为这个组关掉的信号又打开。
5. 用量变化（13.5）。
6. 订阅窗口：完整读到时判设备数（13.4）；本机地址集也已建成时，再判订阅多地（13.3）和登录国家（13.6）。
7. 一次 upsert 写入这一轮的全部行。

每一轮都从整个窗口重算。存储接口对 worker 只能写、不能读，所以它从不拿自己上一轮的输出来判。

**只观测，是结构上的，不是约定。** `risk.Service` 拿到的每个依赖都是窄接口——列用户、读设置、读小时汇总、流式读订阅日志、读认证事件、查地区库、「这是不是本机地址」、「地址集建好了没有」、「落地节点有哪些」——唯一能写的是只写 `risk_signals` 的存储。`TestRiskServiceCannotWriteServiceState` 钉住每个接口的方法集，并扫描包的源码：不许类型断言，不许导入 `internal/adapters` 或别的 `internal/service`，也不许导入 `reflect`、`unsafe`、`text/template`、`html/template`、`net/rpc`——`Users` 背后其实是完整的用户仓库，反射按名字就能调到它的写方法，模板和 `net/rpc` 也是通过反射按名字调方法，`unsafe` 直接改写内存。所以既传不进一个写入器，也没法从一个更宽的值里把它掏出来。它碰不到 `users`、服务轴、面板、邮件或审计。

### 13.3 订阅多地（`sub_spread`）

**窗口**：最近 7 个自然日，含今天；订阅日志保留天数（`sub_log_retention_days`）在 1–6 之间时取它——更早的行已经删了，按 7 天算会把那几天读成「没有拉取」。窗口从 `sub_logs` 按主键分批流式读取（每批 5000 行），逐批折叠进每个账号的窗口，只活在这一轮的内存里。SQL 的时间下界是 UTC 往前多取一天，精确的日界在 Go 里按面板时区切：SQLite 把时间当带时区的字符串比较，而 `sub_logs` 的行带着写入方的时区。不落在窗口日子里的行在 Go 里丢掉。

**地址卫生与 v2 相同、顺序相同**：内网 → 忽略名单 → 本机节点 / 中转 → 共享出口，一个 IPv6 /64 算一个源。这里的「共享出口」是**窗口内**有 3 个以上账号从同一个源拉取过，所以全机队一起分类。不在用户列表里的账号（例如刚删除的）既不被判定，也不计入别人的共享出口——一个幽灵账号不能把一户人家推成一间办公室。全机队剩下的地址一次批量查库。

**几个计数单位**：

- **省** = （国家，省 / 州）。只定位到国家的源不构成省——和 v2 一样，没有省就没有东西可以区分。
- **常驻省**：窗口里至少 `min_days` 天（`risk.min_days`，默认 3）有拉取来自它。一天是出行，七天里三天是习惯。
- **客户端**：声明了设备标识的，按标识（13.4）；没声明的，按**完整的 UA 字符串**。
- **连通**：同一个客户端在任何日子出现在两个省，就把这两个省连起来——同一台设备出过门，或者在家里的 WiFi 和运营商网络上都更新过。对被判定国家的全部省跑一次并查集，连通是传递的，而且**可以经过非常驻省**：宁可少报。
- **组**：连通的省为一组。`groups` 是含常驻省的组数，`groups_all` 是全部组数，按构造恒有 `groups ≤ groups_all`。

**只判一个国家**：常驻省最多的那个（再比省的个数，再取代码较小的）。其他国家只作为「其他国家的来源」列出，**不参与判断**，省也从不跨国合并。理由：客户端经自己的隧道拉订阅时，来源是落地节点在国外的出口，「本国 + 落地所在国」正是一个走代理的普通用户的样子；跨国的同时使用本来就归 v2 管。

**容错就是该用户分组的 `geo_anomaly.max_regions`**（省级容错，默认 1）。粒度、允许任何地方和可定位比例也都沿用分组的异地并发策略，这个信号自己只有开关和常驻天数——调一个就是调两个。

判定顺序，先命中者胜：

| # | 条件 | 状态 / 代码 |
|---|---|---|
| 1 | 该分组关闭了这个信号（`risk.sub_spread_off`） | `disabled` / `signal_off` |
| 2 | 分组的异地并发粒度是 `off` | `disabled` / `scope_off` |
| 3 | 粒度是 `country`（无法识别的值 v2 也按 `country` 读） | `disabled` / `scope_country`：这个信号判的是省，而管理员说了只看国家 |
| 4 | 允许任何地方 | `exempt` / `allow_anywhere` |
| 5 | 窗口内没有拉取 | `idle` / `no_fetches` |
| 6 | 窗口天数 < `min_days` | `unknown` / `retention_short`：日志留得不够久，什么都不可能出现那么多天 |
| 7 | 排除之后一个源都不剩 | `unknown` / `all_excluded` |
| 8 | 地区库不可用 | `unknown` / `geo_unavailable` |
| 9 | 可定位的比例低于分组的 `min_placed_ratio` | `unknown` / `low_placed` |
| 10 | 没有一个源定位到省 | `unknown` / `no_regions` |

**等本机地址集建成再判。** 这个信号一次判一整周。地址集在它第一次建成之前是空的——不是因为没有基础设施，而是还没收集——此时判，每个经中转的账号都会被读成从中转所在的省拉取。所以地址集从未建成过时（节点列表读失败不算建成，空列表算），这一轮跳过它、保留旧行，计 `infra_pending`，并打一行 Info。循环的第一轮本来就在地址集第一次刷新几分钟之后，这是守卫，不是日程。

**已知的误判**（前两条各有测试钉住，而不是藏起来）：

- **外省号卡**（误报）：一张外省号卡的手机，在家也被定位到号卡所属的省（中国移动网络的这个规律流传很广，但**未实测**）；它如果从不在家里的 WiFi 上更新订阅，就没有任何客户端把它和家里的路由器连起来，读作两组。补救：给那个分组调高 `max_regions`，或者关掉 `risk.sub_spread_off`。
- **同一个 App 同一个版本**（漏报）：两个人的 UA 完全相同，读作一个客户端，他们的省被连在一起。
- **经代理拉订阅**：TUN 或全局模式的客户端会经自己的隧道去拉（具体哪些客户端如此，未实测），来源于是落地节点的出口。出口等于 `ServerAddress` 的由 `infra` 挡掉，3 个以上账号共用的由共享出口挡掉，剩下的读作另一个国家，只作参考。仍可能报警的只有一种组合：同一个外国里有两个不同省的落地、账号的设备各自粘着一个落地、出口又不等于 `ServerAddress`（IPv6 出口、NAT）；即便如此，那个国家也要常驻省比本国多才会成为被判定的国家。补救：忽略名单。
- **面板在 CDN 或反向代理后面、又没配可信代理**：看到的来源都是代理的那几个地址，3 个以上账号共用，就全成了共享出口，结果是 `unknown` / `all_excluded`——安全的方向。
- **地区库更新时改了一个省的名字**：窗口里会多出一个省。同一个客户端在新旧两个名字下都出现过的话，会把它连回原来那组。省级代码（2026-09-26）不改变这一点：省仍按名字分组，代码只用于显示（§12.4.5）。中文界面上，新旧两个名字若带同一个代码，会显示成同一个中文省名、列成两行（没被连回同一组时，就在两组里）——读着奇怪，但这正是改名的线索。

**证据**（`v: 1`；没有地址、没有网络号、没有完整的设备标识）：窗口天数和起始日期、保留天数、`min_days`、可定位比例、容错、被判定的国家、`groups` / `groups_all`；最多 12 个省（省级代码 `rc`、日掩码、是否常驻、组号）；最多 10 个客户端（类型、标签、设备标识前 4 位、日掩码、去过哪几个省）；最多 6 个其他国家；四类排除的源数和定位覆盖。客户端的标签是它按拉取时间最新一次声明的设备标签；没有设备标识的，是截到 64 个字符的 UA。省级代码（2026-09-26）取这个省所有拉取里字节序最小的合法代码，没有时省略这个键；它只让风险信号页在中文界面上按代码显示中文省名（省的那一行和客户端「去过」的那一行，规则同 §12.4.2；其他国家那一行仍是国家代码）。证据仍是 `v: 1`：这个字段可有可无，缺了在哪个版本里都是同一个意思，没有读者需要区分。

### 13.4 设备数（`devices`）

**x-hwid**：部分订阅客户端会在每次拉取时带上一个稳定的设备标识和本机描述。PSP 读的请求头是 `X-Hwid`、`X-Device-Os`、`X-Ver-Os`、`X-Device-Model`，沿用 Remnawave 的约定。**这组头名、以及哪些客户端会发送它们，都还没有拿抓到的真实请求核对过**：用了别的头名的客户端读作匿名拉取，只会少算设备，所以界面的提示不点名任何 App。

**存什么，不存什么**：

- 原始 x-hwid **不落库、不写日志**，只在这一次请求的局部变量里。落库的是 `sub_logs.device_id`：64 位的 HMAC（16 位小写十六进制），消息里带账号 ID，所以两个账号共用一台手机读作两个互不相关的标识；泄露的 `sub_logs` 也没法拿一份已知设备号去比对，除非同时拿到面板密钥。密钥从面板密钥派生（`encryption_key`，旧配置下是 `jwt_secret`），带自己的标签 `psp/sub-device-id/v1`：它既不是加密落库用的 AES 密钥，也不可能等于任何 JWT 签名（JWT 的签名输入总带 `.`，这个标签没有）。
- 标识先截到 256 字节、去掉两端空白，只接受 8–128 个字节、每个都是不含空格的可打印 ASCII，再**转成小写**（客户端换了大小写，仍是同一台）。不合格的一律当匿名拉取。客户端若发的是固定的占位值而不是真实的设备号，那个账号的所有设备会被并成一台——少算，是安全的方向。
- `sub_logs.device_label`：清洗过的「系统 版本 · 机型」。每个头先截到 256 字节，丢掉非法 UTF-8、控制字符和格式字符（包括能让文字倒着显示的双向覆盖符），合并连续空白；每段最多 32 个字符，合起来最多 64 个。
- 两列都随 `sub_logs` 一起过期。
- **只读、不改变响应**：状态码、响应头、客户端识别、被拦截客户端的判定都不受影响；PSP 从不回 `x-hwid-*` 响应头，客户端从应答里看不出它有没有被记录。读取函数不打日志、不返回错误，有源码守卫测试钉住。被拦截客户端的 403 和正常的 200 / 304 都会记录设备。
- **只给管理员看**：`GET /api/admin/sub-logs` 运维员也能读，所以设备字段不进 `domain.SubLog` 的 JSON；处理器按调用者**当前**的角色确认是管理员之后，才加上 `device_label` 和 `device_id4`（摘要的前 4 位，从不给完整摘要）。订阅日志表对管理员多一列「设备」：有标签显示标签，否则显示 `#` 加前 4 位，都没有显示「—」。

**采集开关 `risk.hwid_capture_off` 只有全局**：`/sub` 在知道账号属于哪个分组之前就要读它，而且「面板记不记设备标识」是整个面板的隐私决定。它不在 `OverridableScopeKeys` 里，按分组覆盖返回 400。关掉之后不再采集，已存的摘要随订阅日志过期。

**怎么判**。窗口与 13.3 相同，但**不定位**——同一台设备从哪个地址来都是同一台——所以既不需要地区库，也不等本机地址集，只要窗口完整读到就判。一个摘要就是一台设备；在窗口里至少 `min_days` 天有拉取，是**常用设备**：七天里三天是一台一直在用的设备，一天是借来的手机或者重装前留下的旧标识。

| # | 条件 | 状态 / 代码 |
|---|---|---|
| 1 | 该分组关闭了这个信号（`risk.devices_off`） | `disabled` / `signal_off` |
| 2 | **全局**关闭了采集 | `disabled` / `capture_off`：分组里那份拷贝不算数，`/sub` 记录这一周时听的是全局 |
| 3 | 窗口内没有拉取 | `idle` / `no_fetches` |
| 4 | 窗口天数 < `min_days` | `unknown` / `retention_short` |
| 5 | 没有一次拉取声明过设备 | `unknown` / `no_hwid`，证据里列出没声明设备的客户端 |
| 6 | 常用设备 > 上限（`risk.max_devices`，默认 3） | `flagged` / `over` |
| 7 | 连偶尔出现的算上，设备 > 上限 | `suspect` / `over_building` |
| 8 | 其余 | `clean` / `within` |

**大多数账号会是 `unknown` / `no_hwid`**，因为大多数客户端不发 x-hwid（这一点同样未实测）。它是灰色的，默认被过滤掉（13.8），不是「正常」。

**为什么只提示、不执行。** §4.1 的结论是设备上限只能在 PSP 的订阅端执行；订阅端现在确实能看见设备了，但看见的是**客户端自己说的**——可以伪造，而且多数客户端什么都不说。拿它执行上限，惩罚的是说实话的客户端，放过的是改一个头就能绕开的人。所以它只给管理员看，从不拦截拉取。`User.DeviceLimit` 仍然只是推给面板的值，哪里都不执行；`risk.max_devices` 是这个信号自己的阈值，和它无关。

**会多算的时候**：重装会换一个新标识，一台手机最多在一个窗口内读作两台——所以默认上限是 3 而不是 2。轮换面板密钥（`encryption_key`，或旧配置下的 `jwt_secret`）会改变所有设备标识，新旧标识最多共存一个窗口，大约 7 天。

**证据**（`v: 1`）：窗口天数和起始日期、保留天数、`min_days`、上限、常用数和总数；最多 12 台设备（标签、摘要前 4 位、日掩码、最后一次拉取、识别出的客户端名、是否常用），常用的在前；带与不带设备标识的拉取次数；最多 6 个没声明设备的客户端（UA 截到 64 个字符、日掩码）。标签和客户端名取按拉取时间最新的那一次；后来一次什么都没声明的拉取不会把它们抹掉。

### 13.5 用量变化（`usage_shift`）

这是**变化检测，不是共享检测**：家里多了一个人、多了一台设备、换了习惯、凭据被共享，在这里长得都一样，所以界面只说「用量变化」，从不说「共享」。

**数据**：小时流量汇总——唯一能回溯 35 天的流量数据（原始快照只留约一周），保留 `traffic_history_days`，默认 730 天。序列是**今天之前**的 35 个自然日，今天没过完，半天永远偏低。前 28 天是基线，后 7 天被判定。每个小时桶按它的**起点**归到面板时区的那一天：汇总里存的是 UTC 起点，按 UTC 日期归会把东八区的每个晚上都放错一天；在非整点偏移的时区，跨午夜的那个桶归到它开始的那天。

**基线是自己的中位数，只算开始使用以来的日子**——从基线里第一个用量大于 0 的日子到基线末尾。那之后的 0 是真的（账号在，没用）；那之前的 0 是账号还不存在的日子，算进去会把新账号的中位数砍半，然后指控它的正常用量。

最近的某一天**超标**，当它高于

```
max(floor(倍数 × 中位数 × 机队系数), 每日下限)
```

- **每日下限**（默认 3 GiB）：基线接近 0 的轻度账号，第一个真正用起来的星期不会读成变化。
- **机队系数**抹平全机队一起上涨的日子（假期、一季新剧）：其余账号当天的总量 ÷ 其余账号基线的中位数，不低于 1。**留一法**，算的是「其余」：小面板上一个大户就是机队的大头，把他算进去，他自己的上涨会抬高他自己的系数，替自己开脱。
- 阈值在 int64 的上限处饱和。浮点转整数越界在 Go 里是实现定义的，amd64 上最高的阈值会变成最低的。

| # | 条件 | 状态 / 代码 |
|---|---|---|
| 1 | 该分组关闭了这个信号（`risk.usage_shift_off`） | `disabled` / `signal_off` |
| 2 | `traffic_history_days` 在 1–35 之间 | `unknown` / `retention_short`：汇总在序列开始之前就被删了，最老的几天读成 0，基线被压低，会指控。35 也不够：清理删的是「现在减 N 天」这个时刻之前的桶，序列却从 35 天前的零点开始，今天一过零点，第一天就已经被删掉一截；36 天才能保住整个序列 |
| 3 | 最近 7 天全是 0 | `idle` / `no_usage` |
| 4 | 开始使用以来不足 14 天 | `unknown` / `warmup`：第一周的中位数是装机期的中位数 |
| 5 | 最近 7 天里 4 天以上超标 | `flagged` / `sustained` |
| 6 | 2–3 天超标 | `suspect` / `building` |
| 7 | 其余，包括只有一天超标（那是一次下载） | `clean` / `within` |

全机队的小时总和一轮读一次，每个被判定的账号再读自己的小时行。机队总和读不到，这个信号整体跳过、保留旧行；某个账号读不到，只跳过那一个账号。两者都计 `partial`。关了这个信号的账号不读任何数据，照样写 `disabled`——汇总读不到的时候，开关的状态也看得见。

**没有星期几的模型**：周末多用只占两天，最多到「疑似」；要到「已标记」，得最近 7 天里有 4 天都高过阈值。全机队一起的起伏由机队系数挡掉，剩下的就是它说的「用量变了」。

**证据**（`v: 1`，只有字节数、日期和比例）：截止日期、35 天序列、开始使用以来的天数、中位数、倍数、下限，以及最近 7 天每天的阈值、是否超标、机队系数（保留两位小数）。`retention_short` 和 `warmup` 只带序列、天数和日期。

### 13.6 登录国家（`login_country`）

**这是账号被盗的绊线，不是共享检测。** 用代理不需要登录面板——客户端拉的是 `/sub/<token>`——所以账号本人很少登录：看看流量、改个密码、绑 2FA。一次来自新国家的成功登录因此罕见而有指向性；而它对谁在用代理什么也不说。

**数据**：`auth_events` 里成功的登录，回溯 90 天；认证事件保留天数（`auth_event_retention_days`）在 1–89 之间时取它。按 `id` **升序**分页读，每页 200 条：200 是仓库层的上限，而循环遇到不满一页就停，页大小超过它就只会读到第一页。翻页用 keyset（下一页取「`id` 大于上一页最大 `id`」的第一页），不用偏移量：读的过程中日志两头都在动。新到的登录落在最大 `id` 之后，升序读时只会出现在最后一页；每小时的保留期清理则从最小 `id` 那头删——保留期不超过 90 天时它删的那一段正落在本次读的范围里（下界比它的截止点早一天），按偏移量翻页的话，被删行之后的每一行都会往前挪过页界、再也读不到，漏掉某国家更早的一次登录，会让之后从那里的登录被判成「新国家」。一页满了却没越过游标（仓库没按游标过滤）算日志不可读：这一类保留上一轮的行，本轮记为 partial，而不是同一页读到关机。SQL 的时间下界只是提前一天（UTC）的粗筛，精确的回溯、以及「晚于本轮时钟的登录不算」都在判定里做。没解析出账号的尝试（`UserID` 为 0）不属于任何人。

**哪些登录说明不了人在哪**（跳过，并按原因计数）：

- 内网、忽略名单、本机节点 / 中转——和订阅拉取同一套规则，逐个地址判：`domain.AddressExclusion` 就是在单个地址上跑一次 `ClassifyAddresses`，所以优先级不会和 v2 分叉。没有共享出口这一条：一次登录是一个账号的行为。
- **落地节点所在的国家**：账号本人的浏览器常常经自己的代理打开面板，出口就是落地节点的。落地节点是每个启用节点自己的 `ServerAddress`（字面量，或主机名解析出的地址），本机地址集刷新时顺带记下哪些地址是落地、哪些是中转。
- **中转所在的国家刻意不跳过**：中转通常就在账号本人所在的国家，跳过它就等于跳过每一次在家里的登录。从中转地址本身来的登录，仍按 `infra` 跳过。
- 定位不了的地址。

**已知国家** = 更早的已定位登录来过的国家，**加上**订阅拉取已经确立的国家（按分组的 `min_days`；定位到省或只到国家都算）。拉取反映的是客户端实际在哪，所以一个从没在家登录过面板的订阅者，第一次在家登录不会被指控。

**判定**：最近 7 天里的一次已定位登录，只有在它之前已经有 3 次已定位登录时才被判定；不足 3 次，没有东西可以说它「新」。被判定的登录来自不在已知国家里的国家，就是一个**事件**，有任何事件就标记。每个新国家只算一次——它的第二次登录会发现它已经已知——事件离开最近 7 天后，标记自然消退。

| # | 条件 | 状态 / 代码 |
|---|---|---|
| 1 | 该分组关闭了这个信号（`risk.login_country_off`） | `disabled` / `signal_off` |
| 2 | 分组的异地并发粒度是 `off` | `disabled` / `scope_off`（`country` 不关它：国家正是它判的东西） |
| 3 | 允许任何地方 | `exempt` / `allow_anywhere` |
| 4 | 最近 7 天没有登录（跳过的也算登录） | `idle` / `no_recent_logins` |
| 5 | 地区库不可用 | `unknown` / `geo_unavailable` |
| 6 | 最近的登录全被跳过或定位不了 | `unknown` / `unplaced` |
| 7 | 有事件 | `flagged` / `new_country` |
| 8 | 最近的已定位登录都还在学习期 | `unknown` / `learning` |
| 9 | 其余 | `clean` / `known_countries` |

**为什么要等订阅窗口。** 已知国家有一半来自拉取窗口，所以只有在这一轮**完整读到了**窗口、并且**本机地址集已经建成**（13.3）时才判；否则保留上一轮的行，这一轮计 `partial` 或 `infra_pending`。拿一个空的或残缺的已知集去判，每一次在家里的登录都会偏向「新国家」。登录日志读不到，同样保留旧行、计 `partial`。

**已知的盲区**：

- 在落地节点所在的国家里，它是瞎的。
- 走 CDN 的节点，主机名解析到 CDN，于是 CDN 的国家成了「节点国家」，VPS 自己的出口国家反而不是：经那条隧道的一次登录可能读作新国家。补救：忽略名单，或者让订阅拉取把那个国家确立为已知。
- 很少登录的账号学得慢，要先攒够 3 次。

**证据**（`v: 1`，没有地址）：回溯天数、保持天数（7）、学习期（3）；登录总数、最近 7 天的次数、被判定的次数；按原因的跳过数（`infra`、`internal`、`listed`、`node_country`、`unplaced`）；最多 12 个已知国家（排序，事件的国家在消退之前显示为事件、不列入已知）；最多 5 个事件（国家、时间、登录方式，新的在前）。

### 13.7 存储与隐私

**`risk_signals` 表**，一个（用户，信号）一行，每小时覆盖，**没有历史**：

| 列 | 类型 | 说明 |
|---|---|---|
| `user_id` | bigint | 和 `kind` 组成复合主键，两列都不自增 |
| `kind` | varchar(24) | 四个信号之一 |
| `state` | varchar(16)，NOT NULL DEFAULT '' | v2 的七种状态之一 |
| `code` | varchar(32)，NOT NULL DEFAULT '' | 分支代码 |
| `evidence` | text，可空，**无默认值** | 证据 JSON；`idle` / `disabled` / `exempt` 为 NULL |
| `updated_at` | bigint | 最后一次写入（毫秒），由存储层自己盖戳，写入方给的值不算 |

- **覆盖而不是追加**：每个信号每轮都从一整个窗口重算，旧行只是旧窗口；留着它们只会无界增长，又没有东西会读第二遍。
- **没有指向 `users` 的外键**：删用户是不级联的硬删除，而一张观测表绝不能挡住管理员的操作。读取一律 JOIN `users`，已删账号的行看不见，并在 worker 的下一轮里被删掉。
- **只存代码和数字，不存句子**：界面按语言本地化，存下一句英文，它就永远是英文。
- **写入之前整批校验**：`kind` 为空或超宽、`state` 或 `code` 超宽、证据不是合法 JSON 或超过 65535 字节（MySQL TEXT 的容量）、同一个（用户，信号）在一批里出现两次——都返回 `ErrValidation`，一行不写。三种数据库对这些情况各行其是：超宽值 SQLite 照存、PostgreSQL 拒绝、MySQL 视 SQL 模式截断或拒绝；一次 upsert 碰同一行两次，PostgreSQL 拒绝、另两个取最后一个。在这里校验，到哪儿都以同一种方式失败。证据必须合法，还因为管理端接口把它原样当 JSON 返回，一行坏证据会让整个响应失败。
- upsert 每条语句 200 行、同一个事务，更新列表点名 `state`、`code`、`evidence`、`updated_at` 四列。
- 和 geo 的存储一样，这是一个从数据库句柄直接构造的具体仓库，不是 `ports.Repos` 的字段：worker 写它、管理端接口列它、通知铃数它，各自只拿到自己声明的那个窄接口，读的一方拿不到写入器。

**`sub_logs` 加两列**：`device_id varchar(16)` 和 `device_label varchar(64)`，都是 `NOT NULL DEFAULT ''`。用 varchar 而不是 text：MySQL 不许 text 列带默认值，而正是这个默认值让 AutoMigrate 能在有数据的表上加 NOT NULL 列。这是写得最频繁的一张表，这次 ADD COLUMN 在 MySQL 8 上是即时的，PostgreSQL 11 以上只改元数据，SQLite 上是 O(1)。

**隐私**：

- **新代码不落库任何 IP 地址或坐标。** 原始 IP 仍只在原来的地方——`sub_logs.ip` 和 `auth_events.ip`，按各自的保留期。worker 在一轮的内存里读它们，这一轮结束就丢。
- **坐标只在一次判定的内存里存在：不落库、不写日志、不经任何接口；落库的只有取整到 10 公里的距离和省级代码**（2026-09-26，§12.4.5）。地区库从本地 mmdb 给出的坐标和精度半径，先到 `domain.GeoLocation`（`json:"-"`，订阅日志、审计、认证事件接口的 `region` 字节不变），再在一次 `ObserveGeo` 里变成配对用的点，调用结束就丢。风险信号的 worker 拿到的查询结果也带着坐标，但从不读它。守着这一条的有：一个结构测试，禁止任何落库或经接口返回的证据类型持有坐标或点类型、或带名字像坐标的字段；以及几条按字符串搜的测试，把输入的坐标拿到保存下来的异地并发证据、订阅多地 / 设备数 / 登录国家的证据里去找。新代码不加日志行。
- **原始 x-hwid 不落库、不写日志**（13.4）。
- `risk_signals` 里每个账号存的是：省和国家的名字加日掩码（省另带至多 3 个字符的省级代码）；客户端标签（设备标签，或截到 64 个字符的 UA）加 4 位摘要前缀；每日字节数；登录的国家代码、时间和登录方式。只有管理员能读，每小时覆盖，没有结论的行为 NULL，已删账号的行每小时清理。三个用到地址的信号（订阅多地、设备数、登录国家）都有测试，把每一个输入地址拿到保存下来的证据里去找。
- 异地并发的证据多出来的只有：一个 `why`（§12.4.2、§12.4.4）——分支代码、层级、粒度三个枚举，三个容错和上升 / 解除次数这几个整数，还有一个浮点数，可定位比例 `min_placed_ratio`；以及（2026-09-26，§12.4.5）每个地点的省级代码 `rc`（至多 3 个字符，就在已经存着的省名旁边，不多带任何信息）和分布里的一个整数 `max_km`（只有最近一轮，每轮覆盖）。没有地址，没有坐标。
- **账号本人看得到的变化只有门户上的 `geo_auto` 提示**（§12.5.2）：每种语言的门户都换成了标题「服务已临时暂停」和警告级别，以前它和管理员的暂停共用「服务已暂停」和危险级别；非中文门户的正文另换成不写地点的本地化通用说明，中文门户的正文仍是存下的那段说明。四个风险信号不出现在门户上，订阅响应也不变（不回 `x-hwid-*` 响应头）。邮件不变。
- `internal/service/risk` 和 `internal/pkg/subdevice` 自己的日志里没有地址、UA、标签或设备标识：worker 的日志只带计数、ID 和错误，`subdevice` 包根本不打日志（守卫测试只允许它导入列出的几个标准库）。
- **两条既有的路径，记录在案、没有改动**：
  - gin 的 Recovery 在 broken-pipe 引起的 panic、以及 `GIN_MODE=debug` 下的任何 panic 时，会把请求头整个打出来，只遮盖 `Authorization`。PSP 在没设 `GIN_MODE` 时用 release 模式。真打出来时，`X-Hwid` 会和订阅 token 印在一起——而 token 本来就在 URL 里。
  - GORM 日志会写出任何失败的、或慢于 200 毫秒的查询的完整 SQL。对 `sub_logs` 来说，那里面有 IP、UA、摘要和标签，从来没有原始 hwid。

### 13.8 界面与通知铃

**日志管理 → 风险信号**，仅管理员。接口在 `adminGroup`，理由和异地并发页一样：它按信号点名具体的人，而信号不是证据，怎么处理是管理员的决定。一个账号一行：

| 列 | 内容 |
|---|---|
| 用户 | UPN，没有时显示名，再没有时 `#` 加用户 ID |
| 订阅多地 / 设备数 / 用量变化 / 登录国家 | 状态标签，颜色和异地并发页共用一张表。悬停显示本地化的依据（数字取自这一行自己的证据，从不按设置重算）和这个信号自己的计算时间。没有行的信号显示「—」，提示「尚未计算」 |
| 异地并发 | 该账号的 v2 判定；标记锁住而这一轮不是 `flagged` 时另挂「仍在标记中」。点击跳到异地并发页 |
| 最后计算 | 各信号计算时间里**最老**的那个：一个被跳过好几天的信号（地址集一直没建成、扫描一直失败）要露出它的年龄，而不是躲在一个新鲜的兄弟后面 |

- **默认只列需要关注的账号**：任一信号 `flagged` 或 `suspect`，或异地并发 `flagged`、`suspect`、锁住。**「无法判断」不算需要关注**：一个没有客户端发 x-hwid 的机队，每一行都是「设备数：无法判断」，全列出来会把值得打开的账号埋掉。「显示全部账号」列出每一行——分母必须够得着。
- 排序：最严重的在前（已标记，v2 的锁存也算 → 疑似 → 无法判断 → 正常 → 其余），同级按用户名。
- 展开一行看证据：
  - 订阅多地：被判定国家的省，每格一天的日条（标题是面板时区的日期），「常驻」和「第 N 组」标签；拉取订阅的客户端和它们去过的省；其他国家的来源；覆盖和排除的计数。
  - 设备数：声明的设备（标签或 `#` 加前 4 位、日条、是否常用、最后一次、客户端）；带与不带设备标识的拉取次数；没带设备标识的客户端。
  - 用量变化：35 天的日用量柱，最近 7 天里超标的柱标红并画出阈值；下面一行写基线中位数、倍数、下限和超标天数。
  - 登录国家：已知国家、新国家登录的列表、各项计数。
- 接口 503 显示「本部署未启用风险信号」；一行都还没有时显示「还没有计算结果」，和「目前没有需要关注的账号」分开。
- 这一版不认识的信号种类，界面忽略：不画列，不算关注，不参与「最后计算」。

**接口** `GET /api/admin/risk-signals` 返回 `{"items":[...]}`：每个至少有一行的账号一项，按 `user_id` 排序。每项带 `upn`、`display_name`、`geo`（v2 判定的摘要：`state`、`flagged`、`tier`、`updated_at_ms`；v2 没有这个账号的行时为 `null`）和 `signals`（按显示顺序，每个带 `kind`、`state`、`code`、`evidence`、`updated_at_ms`；证据原样返回，NULL 就是 JSON `null`）。

- **返回全部状态**：`unknown`、`idle`、`disabled`、`exempt` 如果在服务端被滤掉，看起来都像「没事」，一个 HWID 采集或地区库悄悄停了的机队就会读成「没人要看」。过滤是客户端的事。
- 没接线时返回 503 而不是空列表。
- 读 v2 的行失败时返回错误，而不是把每个 `geo` 都填成 `null`：`null` 的意思是「检测器对这个账号没有记录」，而这里是没人能去看。
- 这一版不计算的信号种类（更新的构建在降级之前写下的行）不返回：没有东西再重写它，它的状态和时间都冻住了，混在活的判定旁边会被读成一个判定。只有这种行的账号不成为一项。

**通知铃**新增一条 `risk_signals`：「N 个账号有风险信号」，仅管理员，警告级别，盾牌图标，点击打开风险信号页。

- 数的是**账号**，不是行：一个账号两个信号被标记，还是一个要看的账号；数行会给铃一个没法和风险信号页对上的数。
- **只数 `flagged`**，`suspect` 在线下，和 `geo_anomaly` 一样。
- 四个信号**共用一条**，不是一个信号一条：铃的任务是「去看风险信号页」，是哪个信号、为什么，在那一页。
- 24 小时新鲜度，和 §12.5.1 同一个窗口：worker 每小时重写每一行，一个仍在被判定的标记一直在窗口里；掉出去的是不再被重写的行——循环停了、某个信号被跳过了好几天——那是历史，由「最后计算」那一列显示。
- v2 的异地并发标记不计入这一条，由 `geo_anomaly` 计。两条回答的是不同的问题，并成一个数就和哪个页都对不上。
- 运维员看不到这一条，角标按剔除之后的条目重算；计数失败只跳过这一条，不会让整个铃变空。

订阅日志的设备列见 13.4。

### 13.9 设置

全局值在 **系统设置 → 基本设置 → 所有用户（全局默认） → 风险信号（只提示）**，紧挨着「异地并发检测」：订阅多地沿用那一块的粒度、省级容错和允许任何地方，调一个的人应该看得见另一个。

| 键 | 接口字段 | 类型 | 存 0（或 ≤ 0、false）的含义 | 生效值 | 按分组覆盖 |
|---|---|---|---|---|---|
| `risk.sub_spread_off` | `risk_sub_spread_off` | bool | 信号开着 | 原样 | 可以 |
| `risk.devices_off` | `risk_devices_off` | bool | 信号开着 | 原样 | 可以 |
| `risk.usage_shift_off` | `risk_usage_shift_off` | bool | 信号开着 | 原样 | 可以 |
| `risk.login_country_off` | `risk_login_country_off` | bool | 信号开着 | 原样 | 可以 |
| `risk.min_days` | `risk_min_days` | int | 3 | 夹到 1–7 | 可以 |
| `risk.max_devices` | `risk_max_devices` | int | 3 | 原样（≥ 1） | 可以 |
| `risk.usage_ratio` | `risk_usage_ratio` | float | 3.0 | 低于 1.5 抬到 1.5 | 可以 |
| `risk.usage_floor_gb` | `risk_usage_floor_gb` | int | 3 | × 2³⁰ 字节 | 可以 |
| `risk.hwid_capture_off` | `risk_hwid_capture_off` | bool | 采集开着 | 原样 | **不可以，只有全局** |

- **开关是反向的**（`*_off`）。一个从没保存过这张表的安装，存的是零值，零值必须意味着「在观测」；正向的「启用」开关会让每个信号一直关着，直到有管理员找到这张表。**界面上两处开关的方向相反**：
  - 全局表单（范围栏选「所有用户（全局默认）」）按正向显示：标签是信号名，打开 = 信号开着，保存时取反写进 `*_off`；采集那一行同样是打开 = 采集开着。
  - 按分组覆盖的四行（范围栏选中某个分组时，以及「分组 → 策略」）直接编辑反向的键，标签写作「关闭：订阅多地」这样：打开覆盖、再打开这一行的开关，是给这个组**关掉**这个信号。没打开覆盖时显示的「全局: 关」，意思是全局没有关掉它，信号开着。
- **存储值 0 是「从未配置」**，设置层不替它填默认值。`domain.RiskPolicyFromSettings` 是解释存储值的唯一地方，和 `GeoPolicyFromSettings` 同一种分工：分组覆盖成 0，意思和全局的 0 一样，都是出厂默认。
- **非法值向「不指控」修复，保存时不校验**：`min_days` 超过 7 永远达不到，「已标记」会悄悄不再存在，所以夹到 7；倍数越低指控越多，所以低于 1.5 抬到 1.5，NaN 当作未设置，`+Inf`（「永不超标」）按最大的有限值算——证据里要写这个倍数，而 JSON 编码拒绝无穷大，这个账号的行就永远存不下来；下限换算成字节时饱和，而不是溢出成负数（负数等于没有下限）。表单下方一行「当前生效」写出修复之后的值。
- 订阅多地没有自己的容错，用分组的 `geo_anomaly.max_regions`、粒度、允许任何地方和可定位比例；登录国家用分组的粒度（只看 `off`）和允许任何地方。
- **按分组覆盖**：同一页左侧的范围栏和「分组 → 策略」里多了一个类别「风险信号（只提示）」，8 个键，没有采集开关那一行（后端拒绝它）。数字行在未设置时显示默认值 3。浮点行（用量倍数）的覆盖提示现在按服务端的 `strconv.ParseFloat` 判断能不能解析——之前一律按整数规则，一个 2.5 的分组倍数会被说成「不生效的覆盖」。判断用的是 `ParseFloat` 本身的移植（`web-react/src/utils/goParseFloat.ts`），对着 Go 生成的向量测试，服务端再拿同一份向量走一遍分组覆盖的解码：经 API 存进来的 `Inf`、`NaN`、`1_5`、`0x1.8p1` 都会生效，超出范围的 `1e400` 被跳过、沿用全局值；NaN 和不大于 0 的值一样，提示为默认值 3。
- 给一个分组单独关掉某个信号、或者调高它的阈值，是处理一个组里确认过的误报的方式（团队共用凭据从几个省拉取、员工在国外登录），不必放松整个机队。

`GET` / `PUT /api/admin/settings/ui` 带这 9 个字段。

### 13.10 升级与降级

不需要数据迁移。

**升级**：

- AutoMigrate 建 `risk_signals` 表（`schemaModels` 从 45 到 46），给 `sub_logs` 加两列。老的 `sub_logs` 行读作「没有声明设备」，所以在客户端带着 x-hwid 更新订阅之前，设备数都是 `unknown` / `no_hwid`。
- **x-hwid 采集在新版本一跑起来就是开着的**（`risk.hwid_capture_off` 默认 false）。不想采集的，升级后马上关掉。
- `risk_signals` 一开始是空的。第一轮在启动后约 2 分钟，之后每小时一轮。那时本机地址集还没建成的话，订阅多地和登录国家晚一小时出现；设备数和用量变化不等它。用量变化对已有 14 天以上小时汇总的账号马上开始判（`traffic_history_days` 默认 730）。
- 在有账号被标记之前，铃里不会出现 `risk_signals`。
- 异地并发的老行在下一次被判定之前保留 `v: 1` 的证据，「依据」列对它们显示存下的英文。
- 门户对 `geo_auto` 的提示换成标题「服务已临时暂停」和警告级别，每种语言都是；非中文门户的正文另换成本地化的通用说明，中文门户的正文不变（§12.5.2）。
- 9 个 `risk.*` 设置在第一次保存设置页时写入；没写入的都按出厂默认解释。

**降级**到只有 §12 的版本：

- 旧版本不认识 `risk_signals` 和 `sub_logs` 的两列，忽略它们；AutoMigrate 从不删表删列。
- 旧版本解码 `v: 3` 的异地并发证据时跳过 `why`、`rc` 和 `max_km`：「依据」列照旧显示英文，省名显示地区库的英文名，没有距离（§12.7）。
- 降级到的构建若已有风险信号、还没有省级代码，它的界面不认识订阅多地证据里省份上的 `rc`，显示英文省名；风险证据的版本本来就没变（`v: 1`），没有东西需要区分。
- 设置表里的 `risk.*` 行和分组覆盖里的 `risk.*` 行，旧版本都会跳过。
- 更新的构建写下、这一版不认识的信号种类，接口不返回（13.8）。

### 13.11 指标

| 指标 | 类型 | 含义，以及什么时候该看 |
|---|---|---|
| `psp_risk_refresh_total{outcome}` | 计数器 | 每小时一轮的结果，按优先级 `error > partial > infra_pending > ok` 取一个。`ok`；`partial`：某个数据源读不到，它影响的信号保留了旧行——某个分组的设置、机队或某个账号的小时汇总、订阅日志、登录日志，或某条证据编码失败；`infra_pending`：本机地址集还没建成，订阅多地和登录国家这一轮跳过；`error`：什么都没写——全局设置或用户列表读不到、保存失败，或这一轮被取消 |

- 启动后出现一次 `infra_pending` 是正常的。一直是 `infra_pending`，说明节点列表一直读不到——同时看 `psp_infra_addresses`（§12.6）。
- `partial` 持续出现，去看 Warn 日志，里面写着是哪一个源。
- 每轮一行 Info 日志 `risk signals refreshed`，带 `outcome`、`users`、`rows`、`flagged`、`infra_ready`、`ms`，只有计数。
- 循环停了：铃里的 `risk_signals` 在 24 小时后消失，风险信号页的「最后计算」露出它停了多久。
