# ADR 0027：`/sub` 的失败一律塌缩为不可区分的 404

- **状态**：已接受（v3.6.1-beta.3）
- **日期**：2026-08-14
- **相关代码**：`internal/transport/http/handler/sub.go`（`SubHandler.Get`）、`internal/transport/http/router.go` 与 `internal/transport/http/middleware`（`NewPerIPLimiter` + `SubPerIPPerMin` 按 IP 限流）

## 背景

订阅端点是**面板上唯一无需认证的写不动但读得到的入口**：它挂在 `gin.NoRoute` 上，路径形如 `/<前缀>/<token>`，token 就是凭据本身。任何人都可以对它发请求，而且它**必须**对未知 token 给出某种回应。

这就构成一个天然的探测面。v3.6.1-beta.3 之前，处理器对不同失败原因返回不同的状态码和文案：未知 token 是 404，而"token 有效但服务当前不可用"（禁用、过期、应急窗口用尽……）是带说明文案的 403。对**真正的用户**来说这很友好；对一个匿名探针来说，这是一个完美的 oracle——

> 404 = 没有这个 token；403 = **有这个 token，只是账号被停了**。

有了这个区分，穷举 token 就从"必须撞到一个既存在又可用的账号"降级成"撞到一个存在的账号即可"，而且被停用的账号往往正是攻击者最想找的（配额耗尽的、被封的、待处理的）。更糟的是，状态码本身就是答案，攻击者连响应体都不用看。

## 决策

**凡是"token 已解析出账号、但这次订阅不能提供"的分支，一律返回空 body 的 `404`，与未知 token 完全一致。真实原因只写进服务端日志。**

当前塌缩进同一个 404 的分支（`sub.go` 里逐条带 `log.Info("sub: blocked", …)`）：

- 未知 / 无法解析的 token（`domain.ErrNotFound`）
- 应急窗口已过期且停用原因是流量超额（`emergency_expired`）
- 应急窗口仍在时间范围内、但窗口配额已耗尽（`emergency_quota_exhausted`）
- `!access.CanLogin`（账号被禁用，含各类自动禁用）
- `!access.CanSubscribe`（服务被停，含各类自动停服）
- 被封客户端违规次数触发自动停服的那一次请求（`auto_suspended_blocked_client`）

设计要点：

### 1. 可诊断性不能靠响应体，靠服务端日志

每条分支都留下一行带 `user_id` 和具体 `reason` 的日志，管理员在审计页 / 用户页仍然看得到真实原因。**知情权被移到了已认证的一侧**——这正是本决策的全部内容：把"这个账号为什么不能用"从匿名可读，改成只有管理员可读。

合法用户拿到的是代理客户端上一句泛泛的"订阅不可用"。这被判断为可接受：用户会去联系管理员，而管理员手上有真实原因。

### 2. 应急配额那条分支的存在本身也有理由

`EmergencyQuotaExhausted` 这个门看起来和流量轮询的停服逻辑重复。它必须留在这里，是因为轮询要到**下一个周期**（最多几分钟后）才会拆掉应急窗口；没有这道门，`/sub` 会在这段间隙里继续下发一份能用的配置。谓词刻意与 `user.emergencyFloor` / 轮询侧的拆除逻辑保持镜像，两层执行不能漂移。

### 3. 500 与 400 不在塌缩范围内

设置加载失败、渲染失败返回 `500 internal error`（原始错误只进日志——公共端点绝不能把 DB / 内部细节吐给匿名调用方）；路径里根本没有 token 段返回 `400 invalid path`。这两类都不携带"这个 token 是否存在"的信息，所以不构成 oracle。

## 后果

**正面**：匿名探针无法仅凭状态码区分"无此 token"与"真实账号被停"。配合 `SubPerIPPerMin` 的按 IP 限流，穷举的成本回到"必须撞出一个既存在又可用的 token"。

**代价**：用户自助排查能力为零。"我的订阅拉不下来"这个问题只能由管理员回答。这是本决策明确接受的取舍。

**已知残留**：**被封客户端（blocked client）的实时拒绝仍然返回 `403 client not allowed`**，而它排在 token 解析**之后**。也就是说，一个带着会被拦截的 User-Agent 的探针，仍然可以用 `403` / `404` 区分出 token 是否有效——在白名单模式（`SubClientFilterMode` = whitelist，任何未匹配的 UA 都算被封）下尤其明显，随便一个默认 UA 就够了。这一支当年是**被明确讨论后特意留下的**，理由是可用性而非安全：v3.6.1-beta.3 的发版记录写着"唯一保留 `403 + body` 的是 `client not allowed`（用户用了不在 whitelist 的客户端，需要换 app —— 这条对用户必须可见）"。所以**不要**把它读成一处被遗忘的分支，也**不要**把它读成"因为安全所以特意保留"——它是一次以用户可自助排查换取残留 oracle 的取舍。同一处理器里因自动停服而触发的那次拒绝**是**塌缩成 404 的：两者的差别是"这次请求的 UA 不合规"（可自助修复）与"这个账号被停了"（不可自助修复），而前者的可见性代价就是本节记录的残留探测面。要重新评估这个取舍，就必须同时给出替代的用户提示路径。

**必须保持的不变量**（未来修改时不能破坏）：

- 任何新增的"账号存在但不能服务"分支，默认必须返回空 body 的 404，并把原因写进日志。新增一个"更友好"的状态码就是重开 oracle。
- 状态码之外，**响应体、响应头、响应时间**也不应携带区分信息。今天所有塌缩分支都写空 body 且在同一位置返回。
- 服务端日志里的 `reason` 字段是这套设计的可诊断性来源，不能为了"减少日志噪音"删掉。

## 考虑过但未采用的方案

- **按原因返回不同状态码 / 文案**（v3.6.1-beta.3 之前的行为）：正是被移除的 oracle。任何以"改善用户自助排查体验"为动机的重构都会回到这里——这是本 ADR 存在的首要原因。
- **返回 404 但在 body 里写明原因**：状态码统一了，信息泄漏原样保留。塌缩必须覆盖整个响应，不只是状态行。
- **对未知 token 也返回 403**（反方向统一）：同样消除区分，但会让所有正常的 404 探测（含误配的客户端）看起来像权限问题，且与 `gin.NoRoute` 上其它路径的语义冲突。
- **只靠限流，不做塌缩**：`SubPerIPPerMin` 抬高了穷举成本，但对一个有耐心或有 IP 池的攻击者来说 oracle 依然存在。限流是纵深，不是替代。
