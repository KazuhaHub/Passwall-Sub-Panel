# ADR 0033：Passwall Node 兼容信息与远程升级准入

- 状态：已接受
- 日期：2026-09-16

## 背景

Passwall Sub Panel 与 Passwall Node 独立发布。节点协议 v1 允许增加可选字段与能力，因此“能完成
基本同步”不等于“能执行远程升级”。如果面板只比较程序版本或在下发时临时查看能力，管理员无法在
服务器列表中提前识别风险，面板重启后也会丢失判断依据；更危险的是，面板可以创建一个当前节点永远
不会接收的升级任务。

远程升级还依赖安装方式。Linux/systemd 与受管 Docker 安装分别提供不同的宿主机助手；手动安装、旧版
节点或已停用助手仍可继续同步配置，但不得被当成可远程升级。程序版本、协议版本、能力和安装介质因此
必须分开建模。

## 决策

### 1. 协议范围与可选能力分开

共享 `passwall-node/protocol` 包是唯一的兼容判断来源。当前 `/v1/node/sync` 接受协议 v1；早期节点省略
`protocol_version` 时的 0 明确映射为 v1。破坏性协议变化必须使用新协议版本和并行端点，不得悄悄扩大
现有范围。

基本同步只由协议范围决定。创建 `agent.upgrade.v1` 任务还必须同时具备：

- `task.execution.v1`
- `task.expiry.v1`
- `task.agent.upgrade.v1`

增加新的升级语义时必须增加新的 task kind/capability，不能改变上述稳定字符串的含义。

### 2. 保存每一次通过身份验证的有效上报

面板在 `node_agents` 中保存最近一次有效上报的原始协议版本、完整能力集合和观察时间。能力不是粘性
授权：下一次报告不再包含某项能力时，持久快照也必须删除它。这样，停用或移除升级助手会立即关闭新
任务准入，而不会继续沿用旧能力。

持久快照只用于准入和运维可见性，不替代实际下发时对当前报告的再次检查。数据库快照满足但当前报告
缺少能力时，任务仍不下发。

### 3. 远程升级双重失败闭合

创建升级任务前必须有持久化观察，并通过共享兼容判断及完整升级能力检查。未知、协议不兼容或能力不全
均返回验证错误，不创建排队任务。创建后，task offer 仍以当轮报告的 execution、expiry 与 kind 能力
重新检查。安装助手还独立校验精确目标版本、预期旧版本、发行物校验和、状态 schema 与升级 contract；
协议兼容不能替代这些事务保护。

### 4. 服务器页面显示四种稳定状态

- `unknown`：尚无已验证观察；等待节点成功连接。
- `compatible`：基本同步兼容，且当前具备远程升级能力。
- `limited`：基本同步兼容，但远程升级能力不完整；继续服务，升级需人工处理。
- `incompatible`：协议版本超出当前已审核范围；阻止远程升级。

表格只显示可理解的结论和操作建议，不展示原始 capability 字符串。原始字段仍由管理 API 返回，供诊断
与自动化使用。发现新版时仍显示版本提示，但只有 `compatible` 行提供远程升级按钮。

### 5. 发布门包含已发布旧节点

Passwall Sub Panel 的普通 CI 继续测试当前固定的 Node 依赖；发布 CI 另外以真实 release tag 运行旧节点
矩阵。兼容矩阵位于 `docs/compat/node-v4.json`，测试强制它与共享协议常量、能力集合和 CI tag 列表一致。
删除旧版本前必须通过新的 ADR 修改支持策略，而不是直接从 workflow 移除。

## 后果

- 升级数据库会新增三列，旧行状态为 `unknown`，节点下一次连接后自动填充，无需重新添加服务器。
- beta1/beta2 继续完成 v1 基本同步，但因为没有升级能力显示 `limited`；beta3/beta4 只有启用其
  Linux/systemd 助手时才显示 `compatible`；beta5 至 beta7 同时支持受管 systemd 和受管 Docker 升级。
- Docker 远程升级只能建立在相同准入上；默认单服务 Compose 不启用此能力，管理员在安装弹窗“高级”中
  显式选择并生成双服务 Compose、实际运行 updater 后，Node 才会报告升级能力。
- 发布耗时增加，因为每个保留的旧 release 都要运行真实 wire contract；这是防止“一次面板升级使整批
  节点失联”的有意成本。

## 考虑过但未采用的方案

- **只比较 Passwall Node 程序版本**：相同版本可因安装方式或助手配置拥有不同能力。
- **只在 task offer 时检查能力**：会留下永远排队的任务，界面也无法提前说明原因。
- **能力一旦出现就永久记住**：助手被禁用后仍会错误开放升级入口。
- **PSP 为每个版本维护另一份 capability 表**：会与 Node 代码漂移；共享纯函数和机器可读矩阵更可审计。
- **面板升级时强制所有节点同时升级**：扩大故障域，违反基本同步与可选能力分离的兼容策略。
