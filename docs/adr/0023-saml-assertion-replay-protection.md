# ADR 0023：SAML 断言重放防护必须持久化

- **状态**：已接受（v3.9.2）
- **日期**：2026-07-29
- **相关代码**：`internal/ports/repos.go`（`SAMLReplayRepo`）、`internal/adapters/sqlstore/saml_replay_repo.go`、`internal/adapters/sqlstore/schema.go`（`ssoAssertionSeenRow`）、`internal/service/auth/saml.go`（`assertionAlreadyConsumed`）、`internal/service/auth/saml_replay.go`（进程内缓存）

## 背景

`crewjam/saml` 会校验断言的**签名**以及 `NotBefore` / `NotOnOrAfter` 时间窗口，但**不维护"已消费断言 ID"的集合**。这是库的明确边界，不是缺陷——SAML 规范把重放防护的存储职责留给 SP 实现。

后果是直接的：**一个被截获的断言，在它自己的有效期内可以被重复提交**。签名依然有效、时间窗口依然没过，库没有任何理由拒绝它。这一层必须由 PSP 自己提供。

PSP 早期实现了 `assertionReplayCache`（`saml_replay.go`）：一个带 TTL 惰性淘汰的进程内 map。它正确关闭了单进程内的重放窗口，但按其构造**有两个窗口关不掉**：

1. **重启即清空** —— 面板重启后集合为空，所有仍在有效期内的断言重新变得可重放。断言生命周期通常约 5 分钟，重启窗口完全落在其中。
2. **多实例互不可见** —— HA / 负载均衡部署下，实例 A 消费过的断言，实例 B 一无所知，照样接受。

这两个窗口不是理论问题：重启是运维常态，多实例是这个面板明确支持的部署形态。

## 决策

**新增 `sso_assertion_seen` 表，把已消费的断言 ID 持久化。** 这张表是**安全属性**，不是缓存优化，不能因为"看起来冗余"而省略。

关键设计约束：

### 1. `assertion_id` 必须是主键，`SeenOrAdd` 必须是单语句原子插入

实现用 `INSERT ... ON CONFLICT DO NOTHING`，靠数据库的唯一性约束保证"插入即占有"。

**不能用 read-then-write**。先查再写的话，同一个被窃断言的两个并发提交会**都**读到"未见过"，然后都被放行——重放防护在最需要它的并发场景下恰好失效。唯一性由数据库强制，而非应用代码，是这套机制成立的前提。

`TestSAMLReplayRepo_ConcurrentSubmissionsAdmitExactlyOne` 用 8 个并发协程提交同一断言，断言恰好只有 1 个被接受。

### 2. 窗口已关闭的行不算重放

冲突行如果 `expires_at` 已过，**不判定为重放**，而是原地接管该行的窗口。

理由：那个断言本身已经过期，SAML 库会独立拒绝它；反之若把过期行当成重放，一个被 IdP 复用的 ID 会把用户**永久**锁死。安全性不受损（过期断言本就进不来），可用性得到保护。

### 3. 存储层出错时回退到内存缓存，而不是拒绝登录

这是本 ADR 里唯一有真实张力的取舍。

- **fail-closed（拒绝登录）** 对安全控制是教科书答案，但一次数据库抖动会让**全部** SSO 用户登不进面板。
- **fail-open（完全放行）** 不可接受。

选择的是第三条：**回退到进程内缓存**。它的保护级别**恰好等于这张表存在之前的水平——永远不会更弱**，同时单进程内的重放仍被拦住。降级以 `ERROR` 级别记日志，确保它是**可见的**而不是静默的。

### 4. 内存缓存保留，且始终参与判断

两者任一命中即判重放：内存缓存能抓住表中行已被 GC 扫掉后的同进程重复提交，持久化表能抓住本进程从未见过的提交。互补而非替代。

### 5. 无保留期设置，由每小时清理循环回收

过期行挂在既有的 `pruneSAMLReplay` → `DeleteExpired` 上。**不提供保留天数配置**：窗口由断言自身的 `NotOnOrAfter` 决定，不是管理员偏好。

**表规模是有界的，且界限来自两处**：

- **写入需要有效签名。** 重放检查发生在 `sp.ParseResponse` 之后（`saml.go`：第 504 行校验签名与时间窗，第 544 行才做重放检查并写表），因此**只有通过签名校验的断言才会落表**。没有 IdP 签名私钥的攻击者无法插入任何一行——这张表不存在"被外部流量灌爆"的路径，这比 GC 更硬。
- **稳态规模 ≈ 每小时 SSO 登录数。** 行在 `expires_at`（断言 `NotOnOrAfter` + `MaxClockSkew`，通常几分钟）之后即可回收，但清理循环每小时才跑一次，所以行最多滞留约一小时。按每行百余字节估算，即使每小时上万次 SSO 登录也只有个位数 MB，且每小时清空一轮；常规部署为 KB 量级。

若清理循环长时间未运行（进程异常），行会累积，但每一行都已过期、下一轮扫描即可全部回收——不存在需要人工干预的永久增长。

GC 只删除已关闭窗口的行——若误删仍有效的行，GC 本身就会重新打开它要关闭的窗口。这一点由 `TestSAMLReplayRepo_DeleteExpiredOnlyRemovesClosedWindows` 守住。

## 后果

**正面**：重启和多实例两个重放窗口关闭；重放防护成为可依赖的安全属性而非尽力而为。

**代价**：每次 SSO 登录多一次数据库写入。考虑到 SSO 登录频率（远低于订阅请求），这个成本可忽略。

**运维**：`AutoMigrate` 自动建表，无需手工 SQL。回滚代码后该表成为闲置表，不影响运行。

**必须保持的不变量**（未来修改时不能破坏）：

- `SeenOrAdd` 保持单语句原子插入语义；任何"为了可读性"改成先查后写的重构都会静默破坏并发正确性。
- `assertion_id` 保持主键/唯一约束。
- 存储层错误不得升级为"放行"，只能降级为内存判断。

## 考虑过但未采用的方案

- **只用内存缓存**（现状）：无法关闭重启与多实例窗口，正是本 ADR 要解决的问题。
- **Redis / 外部 KV**：能满足语义，但会给面板引入一个当前不存在的强依赖组件。数据库已是硬依赖，复用它成本最低。
- **依赖 IdP 侧的一次性断言保证**：不可控，且不是所有 IdP 都提供；SP 侧防护不能建立在对端配置正确的假设上。
- **fail-closed**：见上文取舍 3。
