# ADR 0034：前端需要「同步状态」时，后端应给出什么

- **状态**：**已接受（2026-09-18）：选择档一「资源任务状态」，实现与验收待完成。** 完整 operation 与上游配置验证不纳入本次范围。
- **日期**：2026-09-18
- **相关代码**：`internal/transport/http/handler/admin_user.go`（`X-Sync-Pending`）、`internal/transport/http/handler/user_me.go`、`internal/service/user/user.go`（`HasPendingSync`）、`internal/ports/repos.go`（`SyncTaskFilter`）、`internal/domain/types.go`（`SyncTask`）、`internal/domain/enums.go`（`SyncTaskType`）、`internal/transport/http/router.go`
- **前置**：`docs/react-data-freshness-plan.md`、`docs/react-data-freshness-plan-review.md` §12

## 背景

前端数据层改造已有实现；**其完成范围与验收结果由对应的实施记录说明，本 ADR 不代为表述。** 本 ADR 只讨论一件事：**当需要观察上游同步时，后端应提供什么契约。**

现有信号只有写操作响应上的 `X-Sync-Pending: 1`。**它目前主要通过全局 toast 呈现**——`api/users.ts` 的写方法（如 `setServiceStatus`）`await client.post(...)` 后**不返回任何值**，响应连 header 元数据都没有交给调用者，因此调用方无法据此做后续动作。

核实过的事实（2026-09-18）：

1. **该 header 共 7 处**，全部在写操作响应上（`admin_user.go` 六处、`user_me.go` 一处）。`List` / `Get` 不返回用户同步状态。
2. **没有可查询的契约**：`router.go` 没有用户写操作对应的 operation 路由；`SyncTaskFilter`（`ports/repos.go:90`）只有 `Pagination` / `Status` / `Type`，**没有目标过滤**。`SyncTask`（`types.go:1069`）本身带 `TargetType` / `TargetID` / `Payload`。
3. **`HasPendingSync`（`user.go:570`）不足以充当状态查询**：
   - 它只检查 `user_delete` / `user_resync` / `user_push_config` **三类**任务，**未包含用户相关的 `user_migrate`**（共享客户端迁移）。任务类型共 11 种，其中包含节点、邮件与证书任务——**用户同步检查本来就不应覆盖全部**，所以「3/11」本身不是缺陷。准确的说法是：**它只能说明所列任务类型的活跃情况，不能代表完整的用户同步状态。**
   - **查询出错时返回 `false`**（`user.go:579`），把「不知道」说成了「没有」。**这是明确的问题**，应作为新契约的禁止项。
4. 因此前端**不能**通过轮询 `Get` 或扫描任务列表来推断收敛：GET 不带该 header 不等于已同步；扫第一页没找到任务不等于不存在（历史失败、取消、分页、任务清理都会让这种判断失真）。

## 决策

**选择档一：新增用户资源任务状态接口。当前产品目标确定为「能持续查看这个用户还有哪些同步任务、是否仍在重试，以及当前保留的任务结果」，取代仅靠瞬时 toast 观察后台工作的体验。**

本次不建设完整 operation 数据模型，不承诺证明上游配置已符合期望。三个问题的边界如下：

| 产品问题 | 所需能力 |
|---|---|
| 当前有哪些相关任务、是否仍在重试？ | **本次选择：档一，资源任务状态** |
| 我点击的这次操作是否完成、结果是什么？ | **本次不做：档二，operation 与任务关联** |
| 当前上游实际配置是否符合期望？ | **本次不做：上游读回或版本确认**；单靠任务状态不能证明 |

**即便采用完整 operation，也必须定义「成功」的证据**：不能把「请求已发送」当成「配置已生效」。上游是否拒绝、是否被后续操作覆盖，都需要独立的可证明依据。

### 选择依据

1. 现有问题首先是任务不可观察：管理员能看到本地修改，却无法持续查看待处理和重试情况。资源状态直接补齐这个缺口。
2. 现有用户队列不是操作日志：`enqueueUserTask` 会复用同一类型、同一用户的活跃任务；`user_push_config` 执行时重新读取用户最新状态。一条任务可能承载多次修改，不能据此给某次点击分配可靠的完成结果。
3. 完整 operation 需要额外解决任务合并、目标代次、部分成功、证据保留与幂等关系；当前没有已明确的逐次操作追踪需求，先引入这些机制收益不足。
4. 全量上游读回会增加外部请求，并需要逐适配器定义配置比较与确认语义。本次只读本地任务存储，避免把打开状态卡变成对全部代理面板的探测。
5. 档一在准确命名和有界查询的前提下可以独立交付；以后增加 operation 或验证接口时，不需要推翻它的资源观察语义。

### 采用的契约：轻量资源任务状态

新增受权限约束的 `GET /api/admin/users/:id/sync-status`（自助版 `GET /api/user/me/sync-status`），回答「**当前可观察到哪些相关任务**」。

此处以及以下内容定义的是**待实现接口**，不是现有能力。两个路由共用同一服务层读取逻辑，按调用者权限生成 DTO；不新建 operation 表，不调用上游面板，不修改现有任务调度、重试或清理行为。

硬约束（不满足则不得发布——它们是为了不把现有缺陷搬进新契约）：

1. 语义是**可观察到的任务状态**，不是「本次写操作已应用到所有上游」。没有活跃任务只能叫 `no_active_tasks`，**不得命名 `synced`**。
2. **查询存储出错时返回错误 / `unknown`，不得复用 `HasPendingSync` 的 `false on error`。**
3. **查询必须联合限定**：`target_type = user` **且** `target_id` **且**一份**明确列出的**任务类型集合，并设置**返回数量上限**。**不能只加 `target_id`** —— 不同资源类型可能共享同一个数字 ID。
4. **授权由服务端依据目标执行**，不能只靠路由前缀；自助版走 `user_me.go` 一侧，不能让普通用户看到 admin 总队列。
5. 需要 `ports` → `sqlstore` 的有界目标查询；若要索引，依真实查询计划与迁移测试添加。

以下边界随本决策一并确定。

#### 查询范围、上限与成功响应

任务类型固定为以下四类，由服务端定义，不能由客户端扩大：

- `user_delete`
- `user_resync`
- `user_push_config`
- `user_migrate`

排除邮件、证书、节点任务及原生节点的其他任务队列；因此这个接口也不证明所有节点/控制器的工作已经结束。返回 `covered_task_types` 明示范围，后续增加类型必须同时评审其归属与状态语义。

成功响应至少提供下列字段，日期统一为 UTC：

| 字段 | 确定的语义 |
|---|---|
| `target_type` / `target_id` | 固定 user 类型及当前目标 ID |
| `target_exists` | 本次授权读取时用户行是否存在；仅完整管理员可读取已不存在的目标 |
| `observed_at` | 服务端完成本次读取的时间；不是上游配置确认时间 |
| `covered_task_types` | 上述四类任务的明确集合 |
| `state` | 仅 `active_tasks` 或 `no_active_tasks`；不得增加无证据的 `synced` |
| `active_tasks` | 当前 `pending` / `running` 任务，最多 20 条，按 `updated_at DESC, id DESC` 返回 |
| `active_tasks_truncated` | 是否还有未展示的活跃任务；不能从显示条数推导全部任务数 |
| `recent_terminal_tasks` | 当前存储保留的最近终态任务，最多 10 条，按 `finished_at DESC, id DESC` 返回 |
| `history_truncated` | 是否还有未展示的保留终态任务 |
| `history_scope` | 固定 `retained_only`，明确这不是完整操作历史 |

活跃查询与历史查询分开限量，分别可多取一条判断截断；`state` 根据成功取得的活跃查询结果生成，不能从混排分页的第一页推导。任一必要读取失败时不返回成功的部分快照。读取可能与任务处理并发，响应表示本次本地观察，不是对未来状态的保证。

任务项使用单独 DTO，允许字段为 `id`、`type`、`status`、`attempts`、`next_run_at`、`created_at`、`updated_at`、`finished_at`、`has_error`。不直接序列化 domain.SyncTask，不返回 `payload`、原始 `last_error` 或自由文本 `summary`，防止上游错误正文或历史任务携带凭证、URL 等信息。`has_error` 仅反映是否存有错误记录，不代替失败原因判断。

20 / 10 是首版响应上限，不是业务任务数量限制。实现时验证目标查询计划；需要索引则通过正常数据库迁移与三种数据库测试添加，不把“返回少”误当作“扫描成本必然低”。

#### 错误、失败记录与清理

- 任务存储未配置、目标权限核查遇到存储错误，或任务查询失败时，返回 HTTP 503 与稳定的 `sync_status_unavailable` 错误码；不得返回 200 + 空数组或 `no_active_tasks`。未认证、无权限及目标不可查询分别沿用认证/授权/404 语义。
- 客户端把读取失败呈现为“状态未知”；上次成功快照若保留，必须带观察时间与失效提示，不能继续当作当前结论。
- `pending` 且 `has_error=true` 可以显示“有执行错误记录，任务待重试”；它仍是活跃任务，不是已结束的失败。
- 现有终态是 `succeeded`、`canceled`、`retired`，没有独立 `failed` 状态。本次保留真实状态，不虚构字段。`canceled` 可能来自人工取消或重试耗尽；仅凭旧的 `last_error` 是否存在不能区分原因，UI 使用“已停止/取消”，不猜测是谁取消或为何停止。
- 历史 `succeeded` 只说明该任务被现有执行器标为成功；任务可能因目标已不存在而正常结束，也可能被后续修改覆盖，不能据此显示“当前上游已同步”。
- 活跃任务与历史结果分栏展示。历史失败线索不覆盖当前资源状态，也不把旧成功提升成当前成功。
- purge/保留期清理后，只显示“当前未查到保留记录”；`history_scope=retained_only` 始终存在，不声称“从未执行”“全部成功”或知道具体哪些记录被清理。本次不增加历史墓碑或审计账本。

#### 目标权限与删除

- 完整管理员可查询任意用户 ID 的任务范围；用户已硬删除时仍可返回 `target_exists=false` 及保留任务，支持查看删除任务。任意不存在的 ID 返回相同结构，不由此证明该 ID 曾经存在或已删除成功。
- operator 仅可查询**当前仍存在且角色为 user**的目标。目标是 admin/operator 时返回 403；目标不存在时返回 404，不从历史 payload 或任务类型猜测旧角色。
- 自助接口只采用已认证身份的 user ID，不接受请求方指定他人目标；用户已不存在或不再能认证时遵循既有认证/404 行为，不放宽登录门槛。
- `pending_delete` 但用户行仍存在时，按当前目标权限正常读取；operator 在硬删除后停止观察，并显示“目标已不可查询”，不提示上游删除已确认完成。
- 授权失败、目标不存在和数据库故障必须可区分；任何查询错误都不能导致放宽目标过滤或权限。

#### 前端展示与轮询

1. 已保存的用户/服务状态仍立即按现有查询层重取；任务状态卡独立呈现，标题使用“后台同步任务”，不命名“上游已生效”。
2. 将相关写响应的 pending 元数据交给调用者，值域使用 `reported` / `not_reported`。header 只用于提示需要观察，缺失不能视为成功；已有全局 toast 与卡片提示去重。
3. 状态区域打开时主动读取一次，不以 header 为唯一入口，确保前次操作或后台迁移产生的任务也可被发现。写操作报告 pending 后可在当前目标的状态区域启动观察；不为用户列表每一行常驻轮询器。
4. 写响应报告 pending 或首次发现活跃任务后，以 **15 秒**为初始间隔，最多观察 **5 分钟墙钟时间**。只在区域仍打开、身份与目标未变、文档可见且网络可用时发起周期 GET；同一目标用一个 query key 去重，不叠加自动 retry。参数集中登记，可依据负载测量调整。
5. 没有活跃任务时停止快速轮询并显示“当前未发现待处理任务”，可重取用户事实一次；不得弹“上游全部同步成功”。新的写操作或手动刷新可启动新观察窗口。
6. 读取失败显示 unknown，可在剩余观察预算内等待下一轮；预算耗尽显示“自动刷新已暂停，最后观察时间为……”，保留手动刷新入口，不改变后端任务状态。
7. 隐藏期间不补发错过的轮次；回来时在预算内校验一次，超过预算则保持暂停。关闭区域、切换目标/账号、403/404 时停止观察并清理不该保留的数据；取消 GET 不代表撤销后端任务。

15 秒和 5 分钟是可调整的观察策略，不是上游收敛 SLA；后端重试可能显著长于这个观察窗口。

### 延后能力及重新评审触发条件

**档二：完整 operation 契约。** 仅在产品明确要求按一次点击给出完成回执、跟踪跨面板部分成功，或供调用方可靠等待某次操作时，另立 ADR/后端工作项。需补全：

- 稳定的 operation ID 与**资源/目标代次**——后来的禁用操作覆盖先前的启用时，旧 operation 的完成不能被解释成「现在仍然启用」。
- operation 与实际产生/复用的任务的关联规则（任务合并、去重、重复提交）。
- 终态区分 succeeded / failed / canceled·superseded / unknown 等**可证明**状态；`done` 只表示结束，不等于成功。
- 跨面板部分成功的聚合规则；任务 purge 不能抹去用户仍可能查询的证据。
- 目标级授权、保留期、进程重启与重复操作的幂等键、用户删除后的查询策略。

**上游配置验证。** 仅在产品明确要求证明当前目标配置实际已应用时建设。需要先按适配器定义读回字段/版本确认、期望配置代次、部分验证与过期证据的处理，不能简单增加一个 `verified: true` 就完成。即便未来与 operation 合并展示，任务结束与配置验证仍分别表达。

### 实施与验收

先实现 ports/repo 的联合过滤与 DTO，再接服务层、两个受权限约束的 handler，最后接前端状态卡与有限轮询。服务层仍只依赖 domain/ports，不导入 sqlstore；不要给通用列表传一个实际没有被消费的参数就当完成过滤。

发布前至少通过：

- 同数字 ID 的 user/node/其他目标互不混入，四类用户任务全部覆盖；记录超过响应上限时，活跃状态与截断标记仍正确。
- 存储错误、未配置 repo、权限核查错误均不返回“无任务”；401/403/404/503 在客户端行为可区分。
- 活跃重试、取消、retired、历史成功、purge 后空历史均按上述语义显示，任何路径都不从缺 header/空列表生成 synced。
- admin、operator、自助身份及目标不存在/待删除/硬删除的权限矩阵正确；DTO 不泄露 payload、原始错误或自由文本任务摘要。
- 快速切换目标、退出登录、慢响应晚到不串数据；隐藏暂停、返回校验、五分钟预算与手动刷新均可验证；无逐行轮询或重复 POST。
- 整个状态读取路径不请求上游面板，不增加任务，不更改重试/取消/保留策略；只读查询负载与新增索引在实际数据库规模下验证。

**本 ADR 的“已接受”仅表示以上选择与边界已确定，不能作为前端迁移或本接口已实现、已测试、已发布的证据。**

## 后果

- 得到可查询、可持续展示的相关任务状态；成本包括有界仓库查询、共用服务、管理/自助两个路由、权限 DTO、前端状态卡与轮询测试，不只是加一个 GET。
- 保留现有写接口和队列模型，新增接口是只读补充；旧客户端继续使用 header。现有 `HasPendingSync` 不作为新接口实现，旧 header 未报告 pending 仍不能证明无任务。
- 接受的局限是：不提供某次点击的完成回执，不证明当前上游配置一致；已清理历史不可恢复，operator 对硬删除用户停止观察。产品文案必须持续保留这些边界。
- 15 秒轮询增加本地只读负载，靠按目标去重、区域可见性、有限预算和数据库索引控制；上线后观察实际成本。
- 完整 operation 与上游验证只有满足上述触发条件才重新评审，避免把同一选型无条件反复提出。

无论哪一档：**停止本地轮询不等于取消后端任务**；前端预算耗尽时应显示「仍未确认完成」，请求失败显示「状态未知」——两者都不等于成功。

## 考虑过但未采用的方案

- **本次直接实现完整 operation。** 未采用：现有队列会合并操作并读取最新用户状态，缺少逐次操作归属；在当前任务可见性目标下引入代次、关联表和证据保留的成本过高。
- **把上游读回验证作为本次必需项。** 未采用：回答的是另一类问题，需逐适配器定义确认语义与额外上游负载；不能由队列状态推导，也不应偷偷塞进资源状态 GET。
- **让前端轮询 `GET /admin/users/:id` 直到 pending 消失。** 未采用：不成立的契约。GET 不带 `X-Sync-Pending`，且「服务状态已恢复」证明的是 PSP 的有效状态，不是上游已应用。
- **让前端扫 `GET /admin/sync-tasks` 找该用户的任务。** 未采用：该接口没有目标过滤；第一页没找到不等于不存在。
- **用现有 `HasPendingSync` 直接暴露成一个端点。** 未采用：它的类型覆盖不完整（缺 `user_migrate`），且出错返回 `false`——直接暴露会让这两个问题固化成对外契约。
- **重复 POST 写操作来探测状态。** 未采用：那会再次执行写操作。
- **把 `X-Sync-Pending` 当成 operation 协议的现成实现来用。** 未采用（且已在计划书 v2 中撤回该主张）：它是写响应上的一次性提示，不是可轮询的资源。
