# ADR 0031：原生任务 ID 使用新启动 incarnation，不跟随数据库回退

- 状态：已接受（ID 铸造机制）；不表示 expiry / retention / restore 上线闸已完成
- 日期：2026-09-11

## 背景

Node 以完整 `task_id` 作为 durable journal 主键。PSP 恢复旧数据库后，如果使用回退的数据库
自增序列、持久化 namespace 或本地时钟重新生成相同 ID，旧结果可能被误用于新操作。

还有一个不同的问题：备份可以复活一个已经执行过的旧任务。新 ID 的唯一性无法解决它；如果
Node 也丢失执行证据，给操作换新 ID 甚至会绕过去重。每个 TaskID 的执行去重也不等于业务请求
天然 exactly-once：PSP 备份可能同时丢失请求级幂等记录。

## 决策

1. 每个新的任务铸造器用 `crypto/rand` 生成 192-bit issuer incarnation，只存在于进程内存中；
   后续 ID 使用该 incarnation 和 CAS 递增的 uint64 计数器：
   `tsk1_<48 位小写 hex incarnation>_<16 位小写 hex counter>`。
2. 一个进程的生产任务入口共享一个铸造器；多个 replica 分别初始化。构造失败必须禁止创建
   新任务，计数器耗尽必须拒绝，不能回绕或降级使用时间/数据库序列。
3. 在数据库事务重试之外铸造 ID。回滚允许产生计数空洞，不允许复用已铸造的 ID。
   `CreateOrGet` 幂等命中时返回已有行和它的原 ID；不能用新生成的 ID 重写已有任务。
4. 普通进程重启后的新任务使用 fresh incarnation；已持久化的 queued/offered/terminal 任务
   保留原 ID。不能因为 issuer 不属于当前进程就拒绝合法旧任务或其他 replica 的任务。
5. 当前只落地可测试的铸造器，不新增生产任务入口，也不把它当作恢复检测器。开放真实任务前，
   仍须完成双方同义的不可变执行授权截止时间、结果证据接收、保留期和恢复演练。

## 后果与恢复边界

- 新进程的随机 incarnation 不来自数据库备份，因此数据库回退不会确定性重用计数空间；
  随机性仍是工程上的概率唯一性，不是外部共识或 rollback detection。
- 全部合法字符都是小写 ASCII，固定 70 字节，符合共享协议的 128 字节 TaskID 上限，避免
  MySQL 默认大小写折叠造成两份字节身份对应一个数据库键。
- 不支持带运行中 issuer 的 CRIU/VM 内存快照恢复后直接继续创建任务。必须停止并 fence 全部
  writers，以新进程启动，不能让两个恢复副本同时沿用一个 incarnation/counter。
- Node journal 丢失/回退、双端同时回退或超出受支持恢复窗口时，必须在启用副作用 worker 前
  执行显式 restore-finalize 和副作用核对；没有结论的旧操作保持待核对，不能自动换 ID 重试。
- 单边 PSP 恢复还可能遗失 task 行、offer 标记或 terminal tombstone，而 Node 仍持有较新结果。
  后续恢复通路必须先持久隔离这些证据再确认收到，不能将其误认作完成新任务，也不能永久毒化
  heartbeat。仅实现本 ADR 不代表该通路已经存在。
- 截止时间、最长支持离线/备份窗口、完整结果保留期及最终身份清理策略，是独立的生命周期
  契约；不能从 incarnation 的随机位数推导出一个安全清理期限。

## 考虑过但未采用的方案

- **数据库自增、持久 namespace + counter**：备份恢复会同时回退它们，不能独立保证新 ID。
- **时间戳/按时间排序 ID**：时钟回退、数据库恢复和克隆需要另外的防复用机制。
- **每次创建随机 UUID**：可提供概率唯一性，但没有显式区分 issuer incarnation 与局部序列，
  难以直接测试序列耗尽和诊断发行来源；现有 UUID 生成器继续用于原有用户/客户端身份。
- **新增外部共识/租约服务**：可提供更强 fencing，但不是当前独立、多平台和 Docker 部署的
  必要依赖；本方案不宣称替代完整状态回滚后的外部 fencing。
