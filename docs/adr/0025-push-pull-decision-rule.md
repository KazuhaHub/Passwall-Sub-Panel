# ADR 0025：推还是拉——决策规则，以及 PSP 今天为什么没有选择权

- **状态**：**已接受**（规则本身）。其中 Q2a 对 PSP 当前架构的结论是**既成事实的记录**，不是选择。
- **日期**：2026-09-07
- **相关代码**：`internal/adapters/xui/client.go`（`doJSON`、`clientWriteLocks`）、`internal/transport/http/handler/node_enroll.go` 与 `enrollscript/enroll.sh`、`internal/pkg/safehttp`、`internal/domain/traffic_cap.go`、`internal/service/reconcile`、`internal/service/sharedclient`
- **前置决策**：[`data-plane-plan.md`](../data-plane-plan.md) Phase 2、[ADR 0024](0024-psp-native-node-backend.md)

## 背景

「配置该由节点拉还是由 PSP 推、遥测该由谁发起」这个问题在设计讨论里被反复重新提出，每次都从零开始。原因不是没人回答过，而是**问题本身的框法是错的**：它把四五件互不相干的事挤进了一个二选一。

一次覆盖 PSP 全部 138 个跨边界数据项的审计，把一版看起来合理的四问规则（谁拥有真相 / 谁能拨号 / 有无截止时间 / 如何失败）逐条套上去，**四个问题全部被真实代码反证**。其中最有说服力的一条：

> 把这四个问题套到 `2fcff2a^`（[流量下限缺陷](../traffic-floor-defect.md)修复前的代码）上，**四个全部返回「符合」**——符合在一个「100 GB 的用户在 55 GB 被切断、新周期第一天零使用也被停」的线上缺陷上。
>
> 一条能给它本该抓住的 bug 打全绿的规则，不是规则。

本 ADR 记录修正后的规则，以及规则暴露出的、关于 PSP 当前架构的一个结论。

## 决策

### 规则

按顺序问，前一问的答案会作废后面某些问题。

**Q0｜这是「状态」还是「调用」？**

调用的参数在请求发生前不存在，结果只作为它的后果存在——它没有 owner、没有稳态、没有版本，Q1–Q5 一概不适用。对调用要问的是：调用方能不能阻塞、超时多久、丢了响应会留下什么。只有当「不能阻塞」时它才转化为状态（一行任务 + 一行结果），而**这是要主动付的代价，不是换个拨号方就白得的**。

PSP 里的调用：`ScanRealityTargets`（管理员敲进来的目标 + 只有节点能做的现场测量）、`ListXrayVersions`、`WebCert`、连接测试。

**Q1｜谁拥有真相？→ 决定数据的方向**

三个答案，不是两个：

- **PSP 拥有** → 期望态，流向节点。
- **节点拥有** → 观测态，流向 PSP。
- **JOINT** → 值是 `f(PSP 的量级, 节点的原点)`。`client.totalGB` 就是这一类：`panelLifetime + headroom`，两边都无法单独说出它。判成前两类中的任何一类都会造出坏设计——判「PSP 拥有」得到的就是那个真实缺陷，判「节点拥有」则整个 PSP 离线安全网消失。JOINT 强制三件事：**写前必须现读节点那一半**；**相等比较无效**（期望值会在 PSP 没参与的情况下移动），只能用带方向偏置的容差；以及检查这个意图**在节点的坐标系里能不能表达**。
- **CONTESTED** 是合法终态：owner 在运行时由「哪边有非空值」决定（`Node.Flow` vs 面板自己的 flow）。终态动作是**不修、记一个稳定的 issue code、交给人**。

Q1 之后还有两个必问的追加项：

- **节点会不会自己推导这个字段？** 会 → PSP 不能推自己的意图，必须推**节点会自己算出来的那个形式**。`client.enable` 就是：3X-UI 有自己的 cron 会按过期时间重新停用，直推 `u.Enabled` 会得到一个每周期一次、每次带 Xray reload 的永不收敛循环。PSP 因此必须建模节点的推导规则（`EffectiveEnabled`）并随上游版本维护它。
- **方向是不是随事件变？** `inbound.remark` 在「管理员在 PSP 改」时是 PSP→节点，在「reconcile 发现漂移」时是节点→PSP。这类字段要按 **(字段, 写入事件)** 而不是按字段来定，并且一旦某条路径宣告它归运维所有，**写这个结构体的每条路径都必须携带现值**。

**Q2a｜你控制节点上的软件吗？**

不控制 → **拨号方已经由别人替你决定了**，Q2b 作废。你只能围绕别人给你的可达性做设计。

**Q2b｜（仅当 Q2a 为是）谁能拨号？**

问的是**主机或进程**，永远不是配置对象。多个配置对象映射到一个可拨端点时，还欠两个答案：一条连接怎么复用 N 个对象，以及**部分失败**（端点可达但其中一个对象不收敛）怎么表达。

并且对**每一个观测**单独问一次：**有没有第二条失败模式不相交的路径？** 便宜就留着。一个通道无法报告它自己的中断；健康探测和控制面之所以有价值，正是因为它们**可能互相矛盾**。

**Q3a｜截止时间在「写」还是在「读」？**

在写 → 买一条 nudge 通道（「你配置变了，来取」），nudge **不搬运 payload**，payload 仍按 Q1/Q2 走。

在读 → **nudge 一文不值**。知道截止时间到了的是观察方，唯一的修法是观察方发起，而观测就骑在这次发起上。「有人卡在那儿等这个值」是最尖锐的形式（见 Q0 列的那几个）。

**Q3b｜这个截止时间能委派吗？**

判据：**一个节点，单靠自己的状态 + 一个推下来的常量，能不能判定这个谓词？**

- 能 → **下放一个绝对值**。这比任何 nudge 都好，因为它不需要任何通道。墙钟到期（`MAX(ExpireAt, EmergencyUntil)` 推一次，节点自己判）就是这一类，规则里必须给它留一个位置。
- 不能（跨节点聚合）→ 那就**禁止把按节点的近似说成满足了截止时间**，必须把残差写下来。`Σ_面板 用量 ≥ 配额` 属于此类：PSP 拥有配额，每个面板只拥有一个加数且看不见其他加数。参见 `PanelQuotaCap` 误差预算第 3 项（`P × headroom` 放大）。

**Q4｜失败与自证**

- **分开存**：期望态和观测态必须是两个字段。用观测覆盖期望的那一刻，确认退化成同义反复。reconcile 推完 `UpdateInbound` 后 `GetInbound` + `inboundcfg.Capture` 覆盖自己的快照，然后报告 `Fixed=true`——`config_sync_state` 的 `"drift"` 从来没被写过，根子在这里，不是有人忘了写。
- **够新**：和「分开存」正交，Q4 不能只要前者。`EnsureInboundDeletable` 安全**恰恰因为**它没有缓存副本：现读、读失败就拒绝执行删除。照搬「持久化成独立字段」会把现读换成缓存读，把更危险的版本打成更合规的版本。**观测值只有在年龄有界且在使用点被检查时才能授权动作**；做不到就必须在决策时刻现读，且读失败必须阻断动作。
- **覆盖度**：观测的覆盖度要和它限定的值**写在同一次写入里**（`geo_streaks.incomplete` 已经是这个形状）。并且——代码还没做到这条——**从观测派生出来的值不继承它的可重放性**：累计计数器能跨过丢失的一轮自愈，由它算出来的那一行周期快照不能。
- **否定的出处**：**谁负责制造「这次没到」这个证据，它和被观测对象共享失败模式吗？** 观察方自己造出来的否定是一次测量；从上报方的沉默推断出来的是一次阈值猜测；由上报方自己报告的否定，在最需要它的时候一文不值。
- **累计 vs 增量**和推 vs 拉**正交**。累计值可重放，与谁发起无关。

**Q5｜这个字段有几个写入方，靠什么串行化？**

Q1 谈的是**权威**，Q5 谈的是**同时性**，两者不是一回事，而前四问完全没覆盖后者。

### 这套规则套到 PSP 上的结论

**Q2a 对 PSP 当前架构的答案是「否」，这决定了其余一切。**

- 一个 PSP「节点」是 `(panel_id, inbound_id)` 一行配置，不是一台主机。**N 个节点共享同一个面板、同一个进程、同一份凭据、同一把写锁**（`clientWriteLocks` 是包级 map，键 `baseURL \x00 email`）。「全队最不可达的那台节点」在这个模型里不是一个良构的属性——同一面板上的两个节点按定义可达性相同。
- 节点是 **PSP 不拥有、不安装、不在上面放任何代码**的第三方软件。一键安装脚本 `enroll.sh:36` 拒绝在没装 3X-UI 的机器上运行，`:32` 明写「不安装 3X-UI、不改你的 inbound」，它在节点上的**全部足迹是往 3X-UI 自己的 `api_tokens` 表插一行**（`:93-94`），然后退出。S-UI 连注册流程都没有——贴 URL 和 token 而已。
- 因此**「让节点主动拨号」不是设计选择，是向两个上游项目提的功能请求**。要满足它，PSP 就得不再是一个兼容层。
- PSP 拨号（`xui/client.go:347` `doJSON`）；唯一的节点→PSP 方向是一次性的注册回调（`node_enroll.go` `Callback`），它不写入面板任何东西。可达性靠 `safehttp` 的放行策略解决（RFC1918 与 CGNAT `100.64/10` **故意允许**，这样叠加网络后面的面板能工作），而不是靠翻转拨号方。

**推论：PSP 今天没有拉/推的选择权，Q3 也随之塌缩**——PSP 既然是拨号方，nudge 和 payload 就是同一次调用，不存在独立的 nudge 通道，也不需要。

**这个问题随 [ADR 0024](0024-psp-native-node-backend.md) 一起解冻，不早于它。** 在 PSP 拥有自己的节点后端之前，重开这场讨论没有可执行的落点。

## 后果

**规则是判据，不是流程。** 它的价值在于让「凭直觉觉得该拉」这类主张必须落到某一问上，并且被真实数据项反证。规则本身也是被这么建立的——上一版就是这样死的。

**翻转拨号方要偿还的、今天由「单一拨号方」白送的四样东西**，任何未来的自研后端设计必须逐条给出替代品：

| 今天靠什么 | 靠的是什么性质 | 翻转后谁来做 |
|---|---|---|
| 对远端一行的互斥（`clientWriteLocks`，包级） | 所有写都发自同一个进程 | 节点侧必须指名一个互斥机制 |
| `UpdateInbound` 的读-改-写窗口（一次持锁往返内读回 `settings.clients[]` 再注入，保证配置推送永远删不掉客户端） | 同上 | 异步应用期望态就没有这个窗口 |
| 失败域独立的第二观察者（健康探测） | 两条路径 | 一个拨号方会让控制面故障和数据面故障产生一模一样的沉默 |
| 「这次没到」由 PSP 自己的传输层制造（能区分「答了但 0 个 inbound」和「答了但解析不出来」） | 观察方即证据制造方 | 变成「被观测组件对自己是否故障的自述」 |

**分母不在这张表里**，因为推**不会**摧毁它：PSP 两种模式下都有自己的节点表。真正变的是——完整性今天由观测本身携带（一个解析成功的 200 就是「截至此刻枚举完整」的断言），改成推之后它变成上报方的自我断言，**而它恰好在上报方坏掉时无法验证**。

**不能破坏的不变量：**

- 观测态**不得**覆盖期望态。要确认，就多存一个字段。
- 授权破坏性动作的观测值，年龄必须有界且在使用点被检查；做不到就现读、读失败就阻断。
- 任何按节点的近似**不得**被表述为满足了一个跨节点的截止时间；残差要写下来（见 `PanelQuotaCap` 误差预算）。
- 一个 owner 在运行时决定的字段，**每条读它的路径必须用同一个 resolver**（`xrayspec.FirstClientFlow` 就是为此提升上来的）。

## 考虑过但未采用的方案

**「配置节点拉、遥测节点推」当成两套机制。** 这是机场生态（XrayR / V2bX / soga）的形状，方向上没错，但把它理解成两套机制是错的：在那套设计里它们是**一次往返的两个 payload**——节点定期拨一次控制面，上行带遥测、下行取配置。同一个发起方、同一条连接。而对 PSP，Q2a 让整件事根本不成立。

**「配置拉，拉失败回退到推」。** 方向反了。拉失败的两种原因里，「节点→PSP 断了」时 PSP 往往也拨不回去（而节点在 NAT 后面恰恰是选拉的那个场景），「节点自己没起来」推也救不了。推真正的优势是**延迟**不是可达性，所以正确排法是**推催 + 拉兜底**：推失败由拉兜底，不是拉失败由推兜底。

**按数据项固定 owner（只有 PSP-owns / node-owns 两个答案）。** 这正是上一版规则的死因：它给 `totalGB` 的两个答案都是坏设计，给 `enable` 的答案会造出带 reload 的写循环，而 `flow` 的 owner 根本是运行时决定的、`remark` 的方向是随事件变的。必须有 JOINT 和 CONTESTED。

**把 nudge 当成截止时间的通用答案。** 它漏掉了两类：截止时间在读那一侧（nudge 无用），以及可以**下放绝对值**从而根本不需要通道（墙钟到期，严格优于 nudge）。

**把「观测持久化成独立字段」当成 Q4 达标。** 分开存和够新是两个正交属性。只满足前者会把 `EnsureInboundDeletable` 这类「因为没有缓存副本才安全」的 fail-closed 设计改成更危险的版本，并且给它打更高的合规分。

**先写代码再补规则。** 已经试过了：`reconcile` 的包注释描述了三个触发点，实际只有一个存在。L1 尚有自知之明（注明「not yet wired」），L2「搭 5 分钟流量轮询的轻量扫描」则以现在时写着，而它不存在——`LevelLight`（它本该运行的深度）全仓库只有自己的常量声明和消费它的那个分支，两个 `RunOnce` 调用方都传 `LevelFull`。**一条以现在时书写的设计叙述，会在实现漂移之后继续被当成事实引用。** 该注释已随本 ADR 一并改写。
