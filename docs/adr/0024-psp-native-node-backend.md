# ADR 0024：自研节点后端作为一个 PanelKind，而不是一套新架构

- **状态**：**已接受（形状），协议待定稿** —— 2026-09-08 产品门与技术前置作业先后完成；§2「只加一个 `PanelKind`」已被调研推翻，需按「2026-09-08（同日稍晚）」一节重写。
- **日期**：2026-09-04
- **相关代码**：`internal/ports/xui.go`（`PanelClient` 及各可选能力）、`internal/adapters/panel`（`Registry` / `Pool`）、`docs/panel-adapters.md`、`internal/transport/http/handler/node_enroll.go`（节点自注册）
- **前置决策**：[`data-plane-plan.md`](../data-plane-plan.md) Phase 2
- **后续决策**：[ADR 0025](0025-push-pull-decision-rule.md) —— 推/拉的决策规则。其 Q2a 记录了本 ADR 落地前 PSP 在这个问题上没有选择权，因此那场讨论随本 ADR 一起解冻。

## 与既有决策的关系（先读这一节）

**这个问题已经被回答过一次，答案是「不自研」。**

[`data-plane-plan.md`](../data-plane-plan.md) 的 Phase 2 决策门用实测数据关掉了这扇门：推送侧余量 **225×**（约 5600 用户才饱和），一轮 poll 的 p95 只占周期 1.9%。原话是「它要解决的瓶颈在这个规模下不存在」。重开条件也写死了：

- `psp_push_sem_carryover_total` 持续增长
- 一轮 poll 的 p95 超过轮询间隔的 50%
- 用户数进四位数，或 `panel_fetch` 增长到周期的一半

**截至本 ADR 写作时，一条都没触发。**

那么本 ADR 为什么还存在？因为它论证的是**另一个理由**。Phase 2 关掉的是**性能**这扇门；`data-plane-plan.md` 自己在「决策时必须同时接受的代价」里，把另一扇门单列了出来：

> **换来**：数据模型所有权。beta.7 修的四个静默清零 **没有一个是 PSP 写错代码**，全部源于与 3X-UI 整结构 Save 语义的阻抗失配。

下文「我们真正买到的是什么」那张表里的每一条，都落在**所有权**这一类，没有一条是性能。它们不会因为余量还有 225× 而消失。

**但那份文档同样写明了这一条的性质：**

> **换走**：运维方在 3X-UI 界面上的操作习惯……自研后端等于砍掉这个逃生口。**这是产品决策，不是技术决策。**

所以本 ADR 的定位是：**如果所有权的论证成立，形状长这样**。它不替性能那扇门重新开锁，也不替产品决策拍板。状态因此是「搁置」而不是「草案」——草案暗示它在走向被接受，而它在等一个不属于架构层面的判断。

**还有一件 `data-plane-plan.md` 留下、至今没人做的作业**，且很可能直接影响下文的协议选择：

> **先查再定**：3X-UI 3.7.0 自己已有 master/node 推送协议（`/inbounds/pushClientTraffics`、`node-sync` token scope、节点 mTLS、`/nodes/history/*`）。花半天搞清它的成熟度与协议形状——可能可复用……不查就自己造，风险是重复造一个明年被上游做得更好的东西。

这半天应当在本 ADR 转为「已接受」之前花掉。

## 2026-09-08：产品那扇门被回答了

**所有者决定自研。** 理由是兼容税，原话：「每次 3X-UI 和 S-UI 更新，想要兼容我们的功能太麻烦了，特别是 **API 调用层面的更改，影响范围太广**。」

这正是上文「换走运维方在 3X-UI 界面上的操作习惯……**这是产品决策，不是技术决策**」所等的那个判断，而它属于所有者。本 ADR 不再等它。

**同一天的生产实测，必须和这个决定记在一起**（22.2 小时窗口，667 轮 poll，轮询间隔 120s，25 用户 / 5 面板）：

| Phase 2 的重开判据 | 触发线 | 实测 | |
|---|---|---|---|
| 一轮 poll 的 p95 占周期 | 50% | 2998ms → **2.5%** | 差 20 倍 |
| `panel_fetch` 占周期 | 50% | 2827ms → **2.4%** | 差 20 倍 |
| 用户数 | 四位数 | **25** | 差 40 倍 |
| `psp_push_sem_carryover_total` | 持续增长 | 并发闸等待 p95 **0.048ms**，无争用 | 未触发 |

**三条判据一条都没有触发，而且都差一到两个数量级。**

写下来是因为它决定了这个决定将来会被怎么记住：**自研不是因为跑不动**。`data-plane-plan.md` Phase 2 用实测关掉的那扇性能门**至今仍然关着**，本 ADR 走的是它旁边那扇——所有权。任何未来的复盘若把这件事归因为性能，与记录不符。

推论也要写清楚：**性能不会替这个决定兜底**。如果自研后端在规模上比适配器方案更差，那不是「早晚要付的代价」，那是净亏损——因为适配器方案在当前规模下还有 20 倍余量。新后端的性能预算是「不比现在差」，不是「以后总会用上」。

**状态仍然是「搁置」**，因为上面那半天的作业还没花。产品门开了不等于技术前提齐了：不查上游就自己造协议，风险是重复造一个明年被上游做得更好的东西——这条约束是本 ADR 自己立的，不因为决心而失效。

## 2026-09-08（同日稍晚）：那半天的作业花掉了，而它推翻了本 ADR 的核心论断

调研结论见 [psp-node-agent.md §7](../psp-node-agent.md#7-上游协议调研已完成-2026-09-08)。三条与本 ADR 直接相关：

1. **3X-UI 的 master/node 协议不可复用。** 它的 `node-sync` 不是一套节点协议，而是同一套面板 API 加一张 21 条路由的白名单（`internal/web/controller/api.go:91`）；它的「节点」必须**是**一台完整的 3X-UI 面板。复用它等于让我们的 agent 变成 3X-UI，正是本次要摆脱的那笔兼容税。**「不查就自己造」的风险已解除——查过了，没有可借的东西。**
2. **`/inbounds/pushClientTraffics` 与 PSP 的配额下沿推送是同一个设计。** 上游那段注释写着它是「节点侧的展示/执行输入，节点从不把它折回自己上报的计数器」——与 PSP 的 `PanelQuotaCap` 逐字同构。这是一次独立收敛，说明这个形状是对的。
3. **机场生态那派（XrayR / V2bX）的方向是节点拨出**，而 XrayR 的上游仓库**已被清空**（HEAD 是一次 "Clear all files"），由 V2bX 代表。

### 由此触发本 ADR 自己写下的重写条件

上文「未决问题」第 1 条立过一个判据：

> **这条直接决定本 ADR 的核心论断成不成立**：「只是再加一个 `PanelKind`」仅在沿用 RPC 拉模型时为真。若选期望状态收敛，契约就不是 `ports.PanelClient`，它会长在适配器模型**旁边**而不是里面，本 ADR 需要重写。

[psp-node-agent.md §7.5](../psp-node-agent.md) 选的正是节点拨出。**所以这个条件成立了，本 ADR §2「其它什么都不用改」这个卖点不再完整成立**——这一点在 [psp-node-agent.md §0](../psp-node-agent.md) 里已经从另一个方向（port 被上游塑形）独立得出并主动放弃过，两条推理在同一处会合。

同一条未决问题里被称为「尚未评估的折中」的那个方案，现在是计划本身：**`psp` 适配器在 PSP 侧仍实现 `PanelClient`,但方法体写 PSP 自己的期望态，由 agent 收敛。** 它当时附带的风险与条件原样保留，不打折：

> 风险是语义漂移——`AddClient` 返回成功将意味着「意图已记录」而非「节点已生效」，而「写入成功却什么都没发生」正是这个项目反复踩到的失败形状。**只有在收敛滞后成为一等可见状态时才可接受**。

这不是一句免责声明。**v3.9.2-beta.20 整版就是这个形状**——起点是一条用户报告，顺着它的形状排查下去，一共**八处**，各自独立：`pushClientConfigToAll` 结构上无法报告推送失败、`CurrentPeriodUsage` 把读失败吞成 0 让配额上限失效、禁用节点/分隔标题后订阅继续发它、轮询周期改了静默无效、`created_at` 被编辑抹掉（两处仓储）、`bool` 列存不下 `false` 导致「新建的禁用节点」是启用的（三张表）、重试入队失败被吞成成功（七个调用点）。所以这个条件要当作**开工前置**，不是收尾事项。

> 原文写的是「本次发布（v3.9.2-beta.18）刚刚修掉的两个缺陷」。两处都错：beta.18 与 beta.19 是误发（tag 打在一个月前的提交上，什么都没发出去，见 CHANGELOG），而排查最终找到的是八处而不是两处。**修正后这条前置只会更强，不会更弱。**

**订正**：上文未决问题第 1 条把 `nodes.config_sync_state` 称作「已有 `synced` / `drift` / `pending` 的雏形」。查证后这个说法不准确，而且不准确的方向恰好要紧：

**`"drift"` 在后端没有任何一处会被写入。** 它只出现在 `domain/types.go` 的类型注释、`admin_node.go` 的字段注释，和前端 `NodesView.tsx` 的调色板里——节点列表那个橙色「配置漂移」点**永远不会亮**。实际只有两个状态会落库：`pending` 和 `synced`。

原因不是漏检。`reconcile` 确实通过 `InSync` 比对出漂移，但它在**同一次调用里**就地解决（`axisAReversePush` 关时采纳线上配置，开时反向下发），随后 `markSynced`。**节点从不在 `drift` 上停留**,所以没有任何读取者能看见它。

今天这是合理的：PSP 主动拨号，**检测与修复是同一个瞬间**,「已经修好了」是不展示中间态的正当理由（代价只是前端留了一块渲染不到的死分支）。

**但这正是本节那个折中方案会打破的假设。** 期望态收敛之后，检测与收敛不再同时发生，「节点实际配置与我们不一致」第一次成为一段真实存在、有长度的区间——而它就是「`AddClient` 返回成功却什么都没发生」的样子。现有这一列是为同步世界建的，**表达不了一个有长度的不一致**：它只有「已一致」和「下发失败待重试」，没有「已记录意图、尚未生效」，更没有「意图已下发但节点确认迟迟不来」。

所以开工前置的准确表述是：**先让收敛滞后成为一个有长度、可观测、能超时的状态**，而不是「把已有的三态接上」——因为第三态今天并不存在。

**状态改为「已接受（形状），协议待定稿」**：技术前置作业已完成，本 ADR 描述的所有权论证成立；但 §2 的「只加一个 PanelKind」需按上述折中重写，且重写前要先补齐收敛可见性。

## 背景

3X-UI 与 S-UI 转为**只做兼容**。新节点走自研后端，交付形态是**单文件二进制 + Docker**。

需要先回答的问题是：这会推翻多少现有结构。

答案是**几乎不会**。PSP 的上游访问早就走了一层与厂商无关的适配器：持久化行用 `xui_panels.kind` 选适配器，`adapters/panel.Registry` 把 `domain.PanelKind` 映射到构造函数，`Pool` 允许多种实现同时在线并按面板 ID 路由（`docs/panel-adapters.md`）。

**所以自研后端是「再加一个 PanelKind」**。它上面的节点管理、客户端下发、流量轮询、订阅渲染、异地并发检测，全部不用改。

这一点值得写下来，因为直觉上「自己做后端」听起来像是要重做数据面。不是。要做的是**一个实现 `ports.PanelClient` 的 agent**，加上一个把 HTTP 调用翻过去的适配器。

## 我们真正买到的是什么

这不是「不想依赖别人」。适配 3X-UI 的代价是具体的，这个会话里每一条都实测过：

| 现状 | 根因 | 自研后能否消失 |
|---|---|---|
| **设备数上限从不生效** | 3X-UI 只在客户端拉取**它自己的**订阅端点时才认设备，而 PSP 接管了订阅 | 能。执行点搬到我们控制的一端 |
| **并发 IP 上限需要 fail2ban**，且 `XUI_ENABLE_FAIL2BAN=1` 会静默关掉它 | 上游把执行绑在 fail2ban + 一个只认字面量 `"true"` 的环境变量上 | 能。agent 直接在 core 层断连，不需要防火墙层配合，也就没有那两道闸 |
| **3.7.0 上用户名/密码模式不可用** | `/login` 被 CSRF 挡住，而 PSP 在登录成功之后才取 token | 能。认证是我们自己定的 |
| **能力差异**（S-UI 存不下 `limitIp` / `limitHwid`；`limitHwid` 要 3.7.0） | 两个上游的 client 模型不同 | 能。一套模型 |
| **`flexjson`、信封怪癖、版本门** | 反向适配别人的 API | 能。两端同一个作者 |
| **面板地址不能填 `127.0.0.1`** | SSRF 拨号守卫（这条**不会**消失，也不该消失） | **不能**，且不应该 |

最后一行是重点：自研后端**不会**让网络拓扑的约束消失。节点自注册（PR #29）已经把这个问题从「让人填对」变成「机器自己确定」，那个机制与后端无关，会一直有用。

## 决策

### 1. 新增 `domain.PanelKind` = `psp`

按 `docs/panel-adapters.md` 已有的五步流程接入。适配器住在 `internal/adapters/pspnode`。

### 2. agent 的 API 直接照 `ports.PanelClient` 的形状设计

> **⚠️ 2026-09-08 已被推翻。** 所有者的方向修正：「我们不要被 3X-UI 带偏了。我们自己的为主，后续只兼容 3X-UI 和 S-UI，而不再主动向着他们。」
>
> 本节原来的论证有一个没说出口的前提：`ports.PanelClient` 是中立的。它不是——**它的形状是被 3X-UI 的 API 塑出来的**。照它设计 agent，等于把上游的模型搬进我们自己的后端，然后永久留在协议里。
>
> 实证：`BulkSetEnabled` 与 `BulkDetach` 在**生产代码里零调用**（只出现在 port 声明、两个适配器、以及被接口逼着实现它们的测试替身中）。它们在这个接口里的唯一原因是 3X-UI 提供了这两个端点。
>
> 修正后的方向见 [psp-node-agent.md](../psp-node-agent.md) §0。要点：**agent 的线上协议按 PSP 自己的领域模型设计**，`ports.PanelClient` 是内部接口、可以随后重塑，两者的阻抗由**我们自己的 `psp` 适配器**吸收——放在我们能看见也能拆掉的地方。
>
> 代价要记明：本 ADR「其它什么都不用改」这个卖点**被主动放弃了一部分**。它当初是决策依据之一，所以这里不含糊过去。

以下为原文，保留供对照：

`PanelClient` 目前是 **21 个必需方法**，加上 `CapabilityProvider` / `PanelUpdater` / `CoreUpdater` / `WebCertProvider` / `LiveIPReader` / `RealityScanner` 这些可选能力。

适配 3X-UI 时，这 21 个方法是把 PSP 的意图**翻译**成别人的 API；自研时它们是**直接映射**。这消灭了适配层里绝大部分复杂度——不需要 `flexjson` 容忍类型漂移，不需要猜信封形状，不需要按版本开关能力。

**能力仍然要如实声明。** 早期版本的 agent 大可以不实现 REALITY 扫描或证书管理，那就不声明——`reportCapabilityGaps` 会照常把缺口报出来。这条纪律不因为「后端是自己的」而放松：能力回答的是「这个部署能不能做」，不是「这个项目打算不打算做」。

### 2.5 core：xray 与 sing-box 都支持（已定）

代价是把刚从上游消除的那层适配请回 agent 内部一次。接受它的理由是协议覆盖：砍掉 sing-box 会丢掉 `hysteria2` / `tuic` / `naive` / `anytls` 四个协议，xray 适配器一个都没有——这笔学费 S-UI 适配器已经替我们付过。

### 3. agent 拥有什么，PSP 拥有什么

| | 归属 |
|---|---|
| 用户、分组、配额、订阅、渲染、异地并发判定 | **PSP**（不变） |
| inbound 配置的**真相源** | **PSP**（不变，和现在的 import/create 一致） |
| proxy core 进程（xray / sing-box）的生命周期与配置落盘 | agent |
| 客户端在 core 里的增删改 | agent |
| 按客户端的流量计数、在线 IP | agent 采集，PSP 拉取 |
| 并发 IP 上限的**执行** | agent（在 core 层断连，不依赖 fail2ban） |
| 设备上限的执行 | **未定** —— 见下方「仍然未决」 |

### 3.5 独立仓库（2026-09-08 追加）

agent 单独开仓库，目标是**别人也能用**。价值不在「代码分开放」，而在**协议成为一份公开契约**——XrayR / V2bX 被广泛采用正是因为它们实现的是一套可被多个面板驱动的协议。

**但这会在我们自己的两个仓库之间，重建我们正在逃离的那个问题。** 今天改 `ports.PanelClient`，编译器会指出每一个调用点；仓库一拆，协议就是一份没有编译器把关的线上契约——而「上游改 API、影响面铺开、没人第一时间知道」正是本 ADR 存在的全部理由。

三条必须同时成立的约束，详见 [psp-node-agent.md](../psp-node-agent.md) §0.5：

1. 协议类型定义住在 agent 仓库，PSP 以 Go module 引用（一份真相源，两侧类型被编译器检查）
2. 协议有显式版本与兼容策略——**PSP 已有的那整套** `internal/version/compat*.go`、能力声明、版本探测，反过来施加到自己身上
3. `psp` 适配器必须有对着真 agent 跑的契约测试（仓库内已有 `client_live_test.go` 的先例）

**建议等协议定稿再建仓库**：PSP 一旦 `import` 了它的 module path，改名成本就上来了；空仓库买不到东西，却提前锁死名字。名字也不该叫 `psp-agent`——按它是什么命名（外部控制面驱动的 xray / sing-box 节点后端），不按谁在用它命名。

### 4. 交付：单文件二进制 + Docker

二进制而不是包装上游安装脚本。理由是具体的：这个会话里包 3X-UI 安装脚本的方案，第一个卡点就是**发行版差异**（一台机器的 apt 源 404 了一个包，就让整个流程在最后一步死掉）。静态二进制没有这个面。

- 版本钉死 + 发布校验和
- 发行版无关
- 升级 = 换文件重启，回滚 = 换回去

Docker 作为并列形态，不是二等公民。

### 5. 复用已有的自注册机制

PR #29 的令牌 / 回调 / 候选地址探测 / 探通才落库，与后端无关。自研 agent 接入时只换脚本体：不再读 `x-ui setting -show`、不再往 `x-ui.db` 插 token，而是安装 agent 并让它自己上报。

**注册协议本身不用改。**

## 后果

**要写的东西**：agent（core 生命周期、配置落盘、客户端 CRUD、流量与在线 IP 采集、IP 上限执行、自身的 HTTP API 与认证）、`pspnode` 适配器、发布流水线（多平台二进制 + 镜像 + 校验和）、安装脚本。

**不用动的东西**：节点/客户端/流量/渲染/订阅的所有服务层，异地并发检测，注册机制，权限模型。

**必须继续维护的东西**：3X-UI 与 S-UI 适配器。「只做兼容」不等于「可以腐烂」——存量部署仍在用，而 `Pool` 本来就支持多种实现同时在线，混合机群是常态而不是过渡态。

## 仍然未决

诚实列出来，这些会实质影响工作量，不该在动工前含糊过去：

1. **agent 与 PSP 之间谁主动？** 同类系统分成很干净的两派：

   | | 代表 | 方向 | 契约形状 |
   |---|---|---|---|
   | 机场生态 | XrayR / V2bX / soga 对 V2board、SSPanel | **节点拉** | 拉期望状态 + 报用量 |
   | 面板直连 | Marzban / Marzban-node（mTLS，节点监听 2000/3000） | **面板连节点** | RPC |

   **真正的差别不在方向，在契约形状。** 机场生态那派根本不做 RPC——面板只发布期望状态，节点自己收敛，然后回报用量。这与 PSP 现在的 21 个同步方法是两种东西：前者对 NAT 友好、节点不需要暴露管理端口、加节点时面板侧什么都不用配。

   **这条直接决定本 ADR 的核心论断成不成立**：「只是再加一个 `PanelKind`」仅在沿用 RPC 拉模型时为真。若选期望状态收敛，契约就不是 `ports.PanelClient`，它会长在适配器模型**旁边**而不是里面，本 ADR 需要重写。

   一个尚未评估的折中：适配器在 PSP 侧仍实现 `PanelClient`，但方法体不发 RPC，而是更新 PSP 自己存的期望状态，由 agent 轮询收敛。这样上层服务不动，线上协议却是节点拉。**风险是语义漂移**——`AddClient` 返回成功将意味着「意图已记录」而非「节点已生效」，而「写入成功却什么都没发生」正是这个项目反复踩到的失败形状。只有在收敛滞后成为**一等可见状态**时才可接受（`nodes.config_sync_state` 已有 `synced` / `drift` / `pending` 的雏形）。
2. **设备上限到底在哪执行。** PSP 的订阅端点是唯一能看见「同一用户的全部拉取」的地方；agent 只看得见连接。放 PSP 更正确，但那是另一个功能，不属于 agent。
4. **配置漂移的处理。** 现在靠 `lifecycleWriteReason` 的收敛守卫比对面板侧现状。agent 可以做成无状态（每次全量下发），代价是 core 重启频率。
5. **agent 的认证与升级通道。** 谁能命令一台 agent 换二进制，是个安全边界问题，不是运维便利问题。

## 考虑过但未采用的方案

### 抛开适配器模型，为自研后端单独做一条通路

最初的直觉。放弃的理由是它买不到任何东西：节点、客户端、流量、渲染、异地并发检测全都写在 `ports.PanelClient` 之上，另起一条通路等于把这些全部再写一遍，然后永远维护两份。而 `Pool` 本来就支持多实现同时在线——混合机群是要长期存在的常态，不是迁移期的临时状态。

### Fork 3X-UI 改成我们要的样子

看起来省事，实际把我们正想摆脱的耦合继承了下来：还是别人的 client 模型、别人的信封形状、别人的 CSRF 与认证设计，外加一份长期的上游分叉维护成本。上表里那些根因，fork 一个都消不掉——它们大多来自「订阅由 PSP 发放，而执行留在面板侧」这个错配，不是来自代码质量。

### 不写 agent，PSP 直接对 xray / sing-box 的 API 说话

诱人，因为省掉一整个组件。但机器上仍然需要有东西负责：配置文件落盘、core 进程的启停与崩溃恢复、按客户端的流量累计、在线 IP 采集、以及升级。这些不会因为 core 暴露了 gRPC 就消失——只会变成「PSP 远程管理一台它没有代理的机器」，而那正是今天 3X-UI 在替我们做的事。agent 是那份工作的名字，不是额外的一层。

### 第一版就做 agent 反向长连回 PSP

能穿 NAT，很诱人。但它要求把 `PanelClient` 的调用方向整个翻过来（21 个方法从「PSP 拉」变成「经由一条常连推」），影响面远超一个适配器。而自注册（PR #29）已经把「地址怎么定」从人的判断变成了机器的探测，拉模型最主要的痛点因此已经缓解。**留作未决项 1**，等有真实的 NAT 节点需求再评估，不在第一版承担这个改动。

### 只支持一种 core（只 xray 或只 sing-box）

会更简单，但这是**已经付过学费**的取舍：S-UI 适配器带来的四个协议（`hysteria2` / `tuic` / `naive` / `anytls`）在 xray 适配器里一个都没有。agent 内部支持两种 core 意味着把刚从上游消除的一层适配请回来一次，所以这条列在未决项 3，需要先看清楚要覆盖的协议集合，而不是凭偏好定。
