## 1. 推还是拉：一句话和一张表

**一句话：节点主动连面板，但面板说了算。**

「推还是拉」这个问句本身是混的——它把五件不同的事挤成了一个词。拆开之后每一件都有确定答案：

| 问的到底是什么 | 答案 | 为什么 |
|---|---|---|
| **谁拨号**（网络方向） | **节点拨向面板** | 节点不需要公网 IP、不需要开入站端口、不需要证书。这是机场生态里 V2bX 胜出的真正原因，跟性能无关（§7.5） |
| **谁决定配置** | **面板，节点没有发言权** | `NodeReport` 结构上**没有任何字段**可以陈述期望配置——不是约定，是类型层面就写不出来（§8.3） |
| **配置怎么过去** | **一次往返，面板在响应里下发**（周期由 `next_poll_s` 驱动，默认 5 秒——见设计文档 §8.7 与下面 B2） | 看着像「拉」（节点先开口），语义上是「推」：节点上行 `NodeReport`，面板**在知道节点刚报了什么之后**算出三段下发。节点不是在问「有什么变化」（§8.3） |
| **用量怎么上来** | **节点上报累计值，每个心跳都发** | 累计值可重放，丢一轮自愈；面板做单调差分，跟今天读面板的 `LastRaw*` 基线是同一套。**数字没变也照发**——否则「死掉的上报器」和「没人用的空闲节点」长得一模一样（§6、§7.3） |
| **谁判断节点还活着** | **面板独立判定，节点无权自证** | `last_seen` 超过 N 个心跳周期即判失联。节点拨出的代价就是「这次没到」的证据变成了故障方的自述，这条代价必须由面板侧的独立判定买回来（§7.5） |

**明着付的账**：交互式操作（探测 Reality、装 core、升级 agent）最长要等一个轮询周期，
多步流程逐步累加。**结账方式是把周期做短**——默认 5 秒、由 `next_poll_s` 驱动，
PSP 忙时可以说「1 秒后再来」。5 台 × 每 5 秒 = 1 req/s,代价可忽略，延迟与今天的秒级等价。
**不做长轮询**（部署路径上有 Cloudflare），理由与完整推导见设计文档 §8.7。

**为什么今天的 PSP 不是这样**：对 3X-UI / S-UI，ADR 0025 Q2a（「你控制节点上的软件吗」）答案是**否**，
所以 PSP 只能自己拨进去推。**自研之后 Q2a 变成是，Q2b 才第一次成为真问题**——上面那张表是它的答案。

### 顺带说清楚：谁做什么

| | 做 | 不做 |
|---|---|---|
| **PSP（面板）** | 真相源、铸造期望文档、聚合全局配额、判定失联、订阅渲染、异地并发检测 | 不拨号进节点、不解析 core 配置 |
| **Passwall-Node（节点）** | 接文档 → 生成 core 配置 → 管进程 → 报累计计数器和收敛状态 | **不决定任何配置**、不做聚合、不自证健康 |

## 2. 工作分解

三条轨道。**A 是关键路径**（不做完，C 无从开始），**B 可以完全并行**，**C 依赖 A3 和 B2**。

### 轨道 A：PSP 侧的三条硬前置（§8.6）

这三条是 ADR 0024 明写的开工闸门。**它们和新仓库无关，现在就能做，而且不做完协议实现无处落地。**

---

#### A1 — 客户端行身份稳定（ADR 0025 债务 1c）

**做什么**：把 `email` 从 `psp_clients` 的唯一键降级成**可变属性**，行按稳定身份查。

**为什么这是第一件**：协议主键定为 `cli_{psp_clients.id}`（§8.3），而这个 id
今天**不稳定**——`psp_client_repo` 的 Upsert 按 `(panel_id, email)` 查，
而 `email` 是渲染产物：`clientplan.go:314-324` 在面板只需一个客户端时去掉分区后缀，
**分区总数跨越 1↔2 就 re-key** → 查不到旧行 → 建新行 → 新 id → **累计计数从 0 重来**。
用户会被瞬间打到配额上限。协议的主键站在这个地基上，所以它必须先修。

**完成判据**（缺一不可）：
1. 一个客户端跨越 1↔2 分区边界后，`psp_clients.id` **不变**，`LastRaw*` 基线**不变**。有测试。
2. 改域名（`rules.Domain`）导致全量 email 重算后，同上。有测试。
3. 唯一键不再包含 `email`；迁移把现存行按稳定身份归并，**不丢基线**。
4. 变更是**机制性**的：改了签名让编译器走遍所有调用点，而不是加一个「记得调用」的校验函数。

**碰的地方**：`internal/adapters/sqlstore/psp_client_repo.go`、`internal/domain/pspclient.go`、
`internal/pkg/clientplan/clientplan.go`、schema + 迁移。

---

#### A2 — 期望文档只能有一个铸造者（ADR 0025 债务 1b）

**做什么**：让「这个客户端应该是什么样」只有**一处**算得出来。

**为什么**：今天不存在装期望客户端状态的本地行，**三处各自现算，而且算出的值不同**。
更糟的是 `node.go` 推的是**管理员表单原文**，今天之所以安全**只因为** xui 适配器做了读-改-写补齐。
自研 agent 不会替我们做这件事——RMW 一撤，表单原文就直接成了下发内容。

**完成判据**：
1. 一个函数产出期望客户端文档，原来那三处**不存在了**（不是「改成调用它」，是删掉）。
2. 铸造**内容幂等**：CAS 之前先比 canonical 内容，相同则不铸新版本（§8.3）。否则「重算并写回同值」的空写会让稳态零载荷正好在 churn 最多的路径上失效。
3. 有测试证明：同样的输入连算两次，`etag` 相同、`version` **不涨**。

**碰的地方**：`internal/service/node/node.go`、`internal/service/user/`、`internal/service/sharedclient/`、
`internal/service/inboundcfg/`。

---

#### A3 — 落库位置：agent 表 + 每流状态

**做什么**：PSP 今天没有「agent / 主机」这一行。要建：

1. **agent 表**：`agent_id`（注册时铸）、`epoch`、`last_seen`、注册凭据。
2. **每流一行**：`(stream, applied_version, applied_etag, pending_since, last_seen)`，三个流各一行（`config` / `roster` / `directives`）。
3. **把 `psp_client_inbounds.provisioned` 那个 bool 换掉**：变成 `(state, applied_version, first_failed_at)`，
   `state ∈ {applied, pending, rejected, blocked}`（§8.3 的对象四态）。

**为什么第 3 条是硬要求**：ADR 0024 的开工闸门要的是「有长度、可观测、**能超时**」的状态。
一个 bool 表达不出「试了三天还在 pending」，也表达不出 `rejected`——
而 `rejected` 是唯一一格「重试同一内容没用」，**必须能超时升级成 Issue 交给人**。

**完成判据**：
1. `pending` 和 `rejected` 都能超时升级成 Issue，有测试。
2. 迁移把现存 `provisioned=true` 映射成 `state=applied`，`false` 映射成 `pending`（**不是 rejected**——没试过和试过失败不是一回事）。
3. 收敛判据用 **etag 相等**，不是 version 相等（版本回滚 A/B/A 时不产生假的未收敛）。
4. `last_seen` 的失联判定**不读任何版本号**（§8.6 第 4 条）。

**碰的地方**：`internal/adapters/sqlstore/schema.go` + 新 repo、`internal/domain/`、迁移。

---

#### A4 — desired / observed 列拆分（原 task #61 残留）

**做什么**：节点表上，「管理员配的端口/协议」和「探测观测到的端口/协议」分成两组列。

**状态**：**已解锁**。它原本卡在洞 4，洞 4 已在 §8 拿到答案。

**为什么**：§8.3 写死了「`NodeReport` 只能写 `observed_*`，永不写 `desired_*`；
健康探测目标的 host 与 port 只能来自期望文档」。同一张表上两种含义共用一组列，
接上 `inboundcfg.Capture` 与 `SpecFromNode` 就是 ADR 0025 债务 3(d) 换了个入口重来一遍。

**完成判据**：探测结果写不进 desired 列（**类型或 schema 层面写不进，不是靠约定**）；
UI 上两者分别显示，不一致时可见。

---

#### A5 — §4 成本表按真实拓扑重算

**做什么**：文档改动。真实拓扑是 5 台 agent、合计 9 个监听器、T=120s。
9 是 `(panel_id, inbound_id)` 的行数，**不是主机数**——三份提案的成本表都用了不存在的「9 台机群」。

**注意**：方向性结论不变，但**「94% 的收益来自节点拨出，不来自文档拆分」这一条不许记在文档拆分的账上**。

### 轨道 B：Passwall-Node 仓库（可与 A 完全并行）

#### B1 — `protocol/conformance` 一致性测试

类型已经守住了五条决定（见该仓库 README 的表）。剩下三条**类型守不住，必须靠测试**：

1. **引用完整性的三态裁定**（§8.3 那张表）：`roster_ahead_of_config` 是**自愈中的正常态，不告警**，
   超过 K 轮才升 Issue；`attachment_unknown_listener` 是 PSP 侧缺陷；监听器被拒 → 挂载记 `blocked`，
   **该 client 不得判 applied**。
2. **闸态迁移**：`applied` / `pending` / `rejected` / `blocked` 之间哪些迁移合法，
   以及两个可超时态的超时行为。
3. **残差算术**：滞后的聚合值**不许被表述成「满足了上限」**（§8.4）。

**完成判据**：三组测试各自能被一个**故意写错的实现**打红。写完之后，
对每条至少构造一个变异体，确认它真的被抓住——本仓库反复出现的失效模式是「测了函数，没测调用点」。

#### B2 — agent 骨架：拨出、同步循环、应用文档

**做什么**：`POST /v1/node/sync` 的客户端侧、三段的应用、状态上报。**先不碰 core。**

**必须照做的几条**（写错了很难在后期发现）：
- **应用顺序**：config 新增与修改 → roster 全量 → config 删除。
- **join 必须可重入**。**禁止 `requires_config_version >= N` 这类门**——§8.5 点名说，
  这正是后来者会顺手改成门的那种字段。可重入的 join 严格强于一个有序投递保证。
- **交集为空仍物化 client，绝不删除**（删除会让累计计数从 0 重来）。
- **epoch 变高就清零本地已提交版本**。没有这条，一次 DB 还原会让 agent 永久拒收、
  无限期以旧配置服务，唯一出路是重装——**而 DB 还原是常规运维事件**。
- **心跳数字没变也发**。
- `objects[]` 对 clients 是**含零值的全量枚举**。
- **轮询周期照 `next_poll_s` 走，默认 5 秒，不要写死 120 秒**（§8.7）。
  120 秒会把「新增用户生效」从今天的秒级变成最坏两分钟——退步的正好是有人盯着等的那条路径。
  5 秒 × 5 台 = 1 req/s,可忽略；延迟 ≤5s,与今天 `provisionNodeMembers` 写下的「within seconds」等价。
- **轻量轮询要带 `partial: true`,省掉 `objects` / `clients` / `subjects`**;
  全量报告按 `full_report_seconds` 走，**默认 60 秒**。每 5 秒发一次全量逐客户端计数是纯浪费。
  **`partial` 的零值是「全量」,这个方向不能反**——理由和变异验证见 §8.7 与
  `protocol_test.go` 的 `TestPartialReportFailsSafe`。
- **两个周期都由 PSP 下发，节点不存策略**;`full_report_seconds` 缺失或为 0 → **每轮都发全量**。
  判定用 `protocol.ShouldSendFull`,**不要在 PSP 侧再实现一遍**——PSP 得能精确预测 agent 的行为。
- **`full_report_seconds` 需要一个管理员设置项**（PSP 侧，A3 那批 schema 工作里一起做）。
  它不是「能配就配一下」:这个周期是 `overburn_headroom_bytes` 的上界，
  旋钮换的是**带宽 ↔ 允许超用多少**。写 UI 提示时要说清这一点，别写成「上报间隔」。
- **不要为了延迟去做长轮询**。部署路径上有 Cloudflare（源站超时约 100 秒，超过即 524）,
  挂起请求是在别人的超时阈值边上跑。它是后手，不是首选——真需要亚秒下发时再启用，协议不用改。
- **产生 Issue 时立即发一次报告，不等周期**（用 `partial` 报告，§8.7）。
  节点知道自己身上出了什么事，这是它相对 PSP 的信息优势；配额撞线、core 崩了、某段配置被拒，
  都不该等满一个周期。**上行用事件驱动，下行用轮询**——因为「有东西要取」只有 PSP 知道。
- **不要试图让节点自己猜什么时候该拉配置**（例如「有用户连上来就拉一次」）。
  推翻的推理见 §8.7：新用户的配置没到，他就连不上，事件根本不会发生——触发时机与需求反相关。
  拿「未知凭据来敲门」当触发器更糟：那是攻击者可控的触发器，而且 core 刻意不暴露这个事件。

#### B3 — core 配置生成 + 进程管理

**明确排在最后。** §10 写得很清楚：不要先写 core 管理。
前面几步的价值**全部**依赖 C2 的契约测试能跑起来；先写 core 会得到一堆没有验收标准的代码。

### 轨道 C：合流（依赖 A3 + B2）

#### C1 — `internal/adapters/pspnode` 最小实现

## 3. 顺序

```
A1 ─→ A2 ─┬─→ A4
      A3 ─┘        ╲
                    ╲
B1 ─→ B2 ────────────╫─→ C1 ─→ C2 ─→ B3
                    ╱
A5（随时，独立）────╯
```

- **A1 必须最先**：A2 和 A3 都建立在「行 id 稳定」之上。
- **A2 与 A3 可并行**，两个人可以同时开工。
- **轨道 B 从第一天就能并行**，它不依赖 PSP 侧的任何一条。
- **C2 是整件事的验收**。在它跑绿之前，其余全是未经检验的推断。

## 4. 十条不要（每一条都在设计里有出处，也都是接手的人最容易犯的）

1. **不要把 email 或任何派生串当协议主键**——包括 `partKey.canon()`。canon 是**位置相关**的，
   同一个客户端的 canon 会因为**别的节点**出现或消失而改变（§2.4 ① 的订正）。
2. **不要加 `requires_config_version >= N` 的门**（§8.5）。
3. **不要给三态字段加 `omitempty`**。`quota_headroom_bytes` 的 `null` / `0` / `N`
   在线上必须可分辨——「我不知道」和「无限额」同列正是 `traffic_cap.go` 那个缺陷。
4. **不要让心跳在没有流量时跳过**（§7.3：V2bX 正是这样翻的车）。
5. **不要让 `NodeReport` 写 `desired_*`**，健康探测目标只能来自期望文档。
6. **不要把版本差当存活信号**，失联判定只看 `last_seen`（§8.6 第 4 条）。
7. **不要在 `rejected` 上无限重试而不超时**——它是唯一「重试同一内容无用」的终态。
8. **不要让一台 agent 服务多个 panel 作用域**（§8.5 永久关闭）。跨 agent 求和折进一个标量基线，
   一台重装就让和值下降，`monotonicDelta` 在 `d < 0` 时返回 current——**这是超记，不是丢账**。
9. **不要在时间戳或版本号进 ETag**（§8.3）。ETag 是纯内容。
10. **不要在 PSP 里复制协议类型**。一份真相源，用 Go module 引（§0.5 约束 1）。
    这次自研要摆脱的就是「配置有两个来源」，在自己仓库里复刻一遍等于白做。

## 5. 还没定的（都不阻塞上面任何一条）

见 §9：构建矩阵与自升级机制、core 配置生成的抽象层、证书是 PSP 下发还是 agent 自签、
自注册凭据的具体形状（方向已定：注册时铸 `agent_id` + 长期凭据）。

**这些都可以等 C2 跑绿之后再定**，现在定等于在没有验收标准的情况下猜。
