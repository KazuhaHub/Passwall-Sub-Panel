# PSP／PN／第三方后端兼容、升级与 CI 规范

- 版本：1（规范草案，实施基线）
- 日期：2026-09-18
- 范围：PSP、Passwall Node（PN）、3X-UI、S-UI，以及影响代理连接的内核和客户端。
- 状态：目标采用有界双向验证、默认先升级 PSP；新增支持承诺须待测试证据齐全。现状与实施验收见第 9 节。

“必须”是实现与发布验收条件；“建议”允许注明理由后选择其他实现。本文不修改已有发布版本的
兼容声明，不删除 ADR 0033 已保留的旧 PN，不替代 ADR 0032 的任务生命周期边界。


实施任务、步骤和验收清单见 [兼容体系整改实施手册](compat-remediation-plan.md)。

## 1. 兼容声明的单位

兼容结论必须针对具体组合、功能和证据，不能仅根据软件版本大小、HTTP 200 或进程存活得出。

| 维度 | 判定对象 | 必要证据 |
| --- | --- | --- |
| 管理协议 | PSP 与 PN 或第三方 API | 认证、请求响应及业务语义验证 |
| 功能能力 | 禁用、到期、限额、任务、远程升级等 | 对应 capability 和真实行为验证 |
| 数据链路 | 订阅、客户端、后端内核 | 实际连接成功及应拒绝连接确实失败 |
| 升级 | 源组合到目标组合 | 真实历史数据、升级及重新收敛 |
| 回退 | 目标状态返回源版本 | 数据可读、身份和执行证据完整、服务恢复 |

API 测试不能替代数据链路测试；升级机制测试不能替代历史迁移测试；重新启动旧二进制不能
证明旧二进制能读取新程序已经修改的数据。不同维度的通过结论不得相互提升。

## 2. PSP 与 PN 的版本和协议

### 2.1 独立版本轴

分别记录程序版本／commit、协议代际、能力集合、状态 schema、升级 contract、安装方式、
内核版本及平台。不要求 PSP 和 PN 程序版本相等。程序版本定位实现，不能替代运行时能力。

现有 `/v1/node/sync` 的版本 0 映射为 v1 是明确的历史兼容规则，只适用于该端点及既有字段，
不能推广为“所有未知或缺失版本都接受”。破坏性变化使用新代际和并行端点，旧端点保留原语义。

### 2.2 演进规则

| 变化 | 规则 |
| --- | --- |
| 新增可选观测字段 | 必须证明旧接收端忽略字段后原有行为仍正确 |
| 新增配置字段 | 忽略后改变访问限制、凭据或路由语义时，必须能力门控 |
| 新增任务 | 新 kind 和能力标识；未声明支持时不得下发 |
| 修改字段类型、单位、缺省语义或已存在枚举含义 | 不得在原契约中直接修改 |
| 扩展枚举 | 明确旧接收端行为；未知值不得隐式映射为更宽松的授权 |
| 修改 capability 含义或任务效果 | 使用新的能力／任务版本 |
| 删除字段或端点 | 先弃用，建立可验证的迁移路径，再按支持退出规则处理 |

宽容解析仅适用于契约明确允许的扩展位置。未知任务不得执行；未知配置语义不得假装应用成功。
严格字段校验的任务参数等位置不能因为上报允许扩展而整体改成宽松解析。

PN 报告的是本次有效能力；能力撤回必须覆盖旧快照。PSP 创建任务时做持久观察准入，下发时
根据当前报告再次检查，PN 接收与执行前执行自身校验。旧 PSP 没有能力协商时，新 PN 必须
有经过测试的基础模式；不能为了兼容旧 PSP 接受不满足当前任务安全契约的命令。

### 2.3 支持方向与边界

目标采用**有界双向兼容**：候选 PSP 验证清单内旧 PN，候选 PN 验证清单内旧 PSP。
默认升级顺序为 PSP → PN，但每步必须通过第 5 节的中间组合校验。两个产品的软件版本号
不得互相比较；支持范围由精确实现和 profile 定义，不能通过发布时间决定谁“过新”。

已有正式承诺仍是清单内旧 PN 对新 PSP。反方向承诺按以下顺序启用：先选取仍维护的旧 PSP
release 固定到 SHA，运行基础 profile 与声明的升级／回退验证，再审核进入支持清单。
候选 PN 的反方向测试以清单中的旧 PSP 为发布硬门；清单外组合仅做非阻断观测。
尚未完成验证的反方向组合必须显示为未验证，不能因本规范落库就视为受支持。

反方向初始验证应包括当前维护线最近一个已发布 PSP，以及该维护线内最后一个尚未包含候选
协议扩展的已发布 PSP（如果存在）。二者相同则去重；不存在时记录原因，不虚构旧版本。
这样才能发现“新字段在旧接收端失败”的问题，而不是只测已经理解新字段的接收端。
继续保留的版本由维护清单明确，不采用“任意相差 N 个 beta”的隐含承诺。

基础管理 profile 至少覆盖配置收敛、用户凭据、启停／到期／额度、流量报告和重连恢复。
某组合不能满足全部要求时必须声明更窄的 profile，不得统一标为基础功能全部支持。
一次人工测量仅证明该组合与测试范围；共享 Go 类型编译成功也不是 wire 兼容证明。

每个后端区分“政策最低支持版本”“实现所需协议下限”和“最后实测版本”。低于政策下限
意味着不再承诺，不代表当前程序已实现自动拒绝；最后实测版本之外意味着未验证，不等于故障。
现有 PN `min_supported` 按 `released_nodes` 的发行顺序选取 CI 保留集合；它目前不是运行时
程序版本拒绝器。移动这个值必须同步说明协议是否仍接受旧节点，不能用缩小测试集合假装已经
完成协议退出。3X-UI 的编译下限保留，S-UI 未确立下限时不得编造。

**“supported”在现有代码里指三件不同的事，任何一处都不能代入另一处：**

| 说法 | 属于 | 语义与落点 |
| --- | --- | --- |
| `CompatStatus.supported` | 运行时判断 | 当前能跟这台第三方面板通话；`version >= 下限 && <= 最后实测`，低于下限即 `too_old`。见 `internal/version/compat.go` |
| PN `min_supported`／“supported set” | 测试选择 | 这一版还在 CI 里被跑。只有两条 workflow 与矩阵测试读取，生产代码零消费者 |
| 单行 `base_sync: "supported"` | 证据状态 | 在这一版上**验证过**基础同步。见 `docs/compat/passwall-node-v4.json` 的 `released_nodes` |

三者方向相反：运行时结论低于下限就**拒绝**，测试选择低于 floor 只是**不再测**，证据状态
只描述**已经测过什么**。混用会得出错误的保证——尤其把 `min_supported` 读成运行时拒绝器，
会让一次 CI 瘦身看起来像一次协议退出，也会让“新版本低于已测下限”被当成“新版本不受支持”。

预发布版本不自动继承稳定版本承诺，但显式列入清单的 PN beta 继续享有已声明的测试支持；
不能用“预发布一概不保证”取消 beta1–beta11 的既有承诺。

新版本采用保留 prerelease 的版本比较；预发布版本不得被当成对应稳定版。历史 PN 的
`beta1`、`beta10` 等标签必须按项目明确的历史排序规则或发布序列表处理，不能把它们当作
`beta.1`、`beta.10` 的数值 SemVer 标识，也不得重命名既有发行物。

## 3. 第三方适配与运行时检测

### 3.1 同一结论，不同检测方式

PN 使用经过认证的报告；第三方面板使用认证 API、版本信息、只读能力探测及已验证的适配
规则。适配器实现某接口不能证明远端支持它。能力必须同时满足本地实现、远端支持和安装条件。
缺少能力提供接口的生产适配器必须被注册检查或测试拒绝，不能沿用测试替身的默认全支持行为。

首次接入检查身份、版本、必需只读接口和响应结构。后台定期、手工测试、升级后重新探测；
执行写操作前复核对应准入。观察记录包含来源、观察时间、身份和适用的矩阵修订。

在线测试连接默认只读。创建、修改、删除客户及升级试验必须在隔离测试后端进行。不得使用
生产实例验证未知写 API。版本伪装或自定义构建只能作为自报身份，不能继承官方发布物的全部证据。

### 3.2 状态与操作权限分离

分别保存运行兼容状态、功能限制和升级资格；以下是目标语义，不是现有 API 枚举的直接替换。

| 状态 | 运行处理 | 新升级处理 |
| --- | --- | --- |
| 已验证 | 按对应 profile 管理 | 检查具体升级边后允许 |
| 基础可用、功能受限 | 保留已验证功能，拒绝缺失能力的操作 | 缺升级能力则手工处理 |
| 未验证 | 显示证据不足；不扩大功能授权 | 默认不得作为自动升级目标 |
| 已知不兼容 | 拒绝对应操作，报告影响范围 | 仅提供已验证修复路径 |
| 无法判断 | 显示未观察或过期原因 | 不凭过期观察开始高风险操作 |

网络故障不应抹掉最后有效观察，但过期观察不得显示为刚刚验证。新高风险操作要求执行阶段
的新鲜校验；具体超时属于各操作契约，必须有明确配置或常量及边界测试。

兼容清单采用内置基线与最后有效缓存，远端更新必须验证来源、schema、适用版本和修订。
未知 schema、损坏数据、异常回退不能替换有效缓存；回滚清单须有显式可审计流程。断网不凭空
变成“支持”，也不单因清单不可用停止已有代理。硬性协议不兼容和已知危险操作不能被 force 绕过。
若允许人工使用未验证组合，覆盖范围仅是证据不足，必须记录操作者、目标与理由。

控制端失联时保留最后有效配置，同时继续执行已下发的禁用、到期和额度限制。清单中的
advisory 必须描述具体受影响功能；不能未经评估就把新最低版本变成所有存量实例的停服命令。

## 4. 支持政策、验证证据与升级边

维护一份逻辑支持政策，允许按产品／major 分文件。由它选择 CI 测试组合、生成展示信息和
发布准入输入，避免 workflow 再手写另一份版本列表。政策与实测结果分开存储并相互引用。

### 4.1 最小数据契约

以下是新矩阵的目标字段要求；现有 `docs/compat/*.json` 不因本文自动升级格式。

| 记录 | 必须包含 |
| --- | --- |
| 政策头 | schema 版本、不可变修订、适用产品版本、发布时间 |
| 运行组合 | 精确实现身份或显式支持范围、后端种类、profile、能力限制、适用平台／安装方式 |
| 证据 | 唯一 ID、证据类型、双方 commit／发布物摘要、测试套件 commit、CI URL、运行时间、逐项结论 |
| 链路证据 | 额外记录内核、客户端、协议／传输／TLS 组合及测试目标 |
| 升级边 | 源与目标身份、安装方式、源／目标 schema、前提、升级证据、回退是否支持及证据 |
| 已知问题 | 精确影响范围、失败功能、操作限制、修复路径 |
| 支持退出 | 公告时间、停止维护／停止测试／移除协议的独立日期、迁移路径 |

状态分为政策承诺、实测通过、推定可用、未验证和已知失败，不能互相代换。只测试两个边界
不能声称范围内每个版本都实测；声明范围支持时必须说明抽样策略和风险，并保留已知坏版本的排除项。
S-UI 只有上限证据时不得凭空补最低支持版本。基础范围与精确例外的优先级必须确定且可测试。

**证据类型**：每条证据只属于一类，六类互不代换。这是对**证据**的分类，不是新的 API 状态
枚举，也不重命名 `CompatStatus`——那个是运行时结论，两回事。

| 类型 | 证明 | 不证明 |
| --- | --- | --- |
| `wire-contract` | 双方按协议的请求／响应与业务语义正确 | 真实代理内核、完整安装认证 |
| `adapter-live` | 对真实第三方发行物的认证与读写语义 | 版本范围内每个发布物、完整流量 |
| `dataplane` | 订阅经真实客户端与真实内核实际连通；应拒绝的确实被拒 | 其他协议／TLS 组合 |
| `upgrade-mechanism` | 升级与回退机制在受控身份下正确 | 历史代码之间的数据兼容 |
| `historical-upgrade` | 真实旧程序造出的数据被新程序读取并收敛 | 未声明的升级边 |
| `artifact-runtime` | 最终发布的归档／镜像在原生目标上可运行 | 源码重建与发布物等价 |

一条声明若其对应类型尚无证据，必须显示为未验证，不能用相邻类型顶替——例如 `wire-contract`
通过不构成 `dataplane` 证据，`upgrade-mechanism` 通过不构成 `historical-upgrade` 证据。

历史记录不可被新代码测试覆盖成“旧二进制也支持”。扩大旧 PSP 支持范围必须使用旧 PSP
实现验证；修改文案或比较函数不能增加那个旧程序实际拥有的能力。

### 4.2 维护责任

PSP 仓库维护整体支持政策及第三方认证，PN 仓库维护自身协议和升级契约；两仓 CI 读取政策的
固定修订。接口变更方负责补契约与反方向验证；发布方负责目标发布物、升级边和运行证据。
跨仓变更以不可变 SHA 关联，不能互相跟随 main 形成不可复现的循环依赖。

新增上游版本依次经过发现、隔离验证、证据生成、支持政策 PR、发布兼容清单。监测新 release
与兼容失败是不同事件，网络／认证失败也不能当作上游没有发布。监测不得自动抬高已测试上限。

现有旧 PN 支持不缩减。未来退出支持必须单独审核政策与迁移路径；建议预告不少于 90 天且
覆盖两个项目发布周期，正式采用时写入日期。安全紧急例外须记录原因和补救方案。停止维护不
等于立即拒绝连接；移除 wire 支持必须另行决定并测试。

## 5. 升级与回退

升级按组合的有向路径判断：`(PSP A, backend A) → (PSP B, backend A) → (PSP B, backend B)`。
每一步中间状态必须受支持，且每条升级边有证据。先升级 PSP 是常见路径，不是无条件规则。
不存在安全中间状态时必须先提供桥接版本或明确停机迁移方案，不能要求“同时升级”规避问题。

执行阶段必须依次完成：

1. 固定源身份和目标 release／摘要，检查平台、安装方式、能力、schema 与支持路径。
2. 验证发布物来源和完整性，确认空间及备份，声明恢复方式和可能的连接中断。
3. 同资源串行执行；幂等重试不产生第二次升级，源版本变化后重新评估，授权不能无限延期。
4. 在契约规定的 deadline 内验证实际目标身份、重新认证、配置收敛、访问限制及必要的代理链路。
5. 验收通过后提交；失败按已验证回退边恢复并保留证据，无安全回退路径时进入人工恢复状态。

同 schema 也不是自动可回退证明：新版本可能写入旧版本不认识的内容。跨 schema 默认不允许
复用 PN 当前自动回退承诺；必须测试旧程序读取目标数据，或恢复一致性备份并说明数据丢失窗口。
备份恢复涉及任务执行证据和流量基线时必须遵守 ADR 0032，不能因程序恢复而重新授权已执行任务。

第三方面板无可靠升级／回退接口时，标记手工流程，不虚构自动恢复能力。后端面板升级可能连带
更新内核，验收必须使用升级后的实际内核。PSP 自身迁移按它实际支持的数据库方言验证。

批量升级按安装方式、平台、内核与后端种类分组，先单实例，再按已配置批次推进。批次提交前
全部验收通过；失败停止后续批次，不自动回退无回退证据的实例。不要在同一批同时升级控制端和节点。

## 6. CI 层次及测试矩阵

| 门禁 | 对象 | 必须证明 |
| --- | --- | --- |
| G0 静态与单元 | 两仓候选源码 | 格式／静态检查、race、协议边界、能力门控、数据库约束 |
| G1 双向协议 | 候选 PSP × 保留旧 PN；候选 PN × 清单内旧 PSP | 基础 profile、未知字段、缺失字段、能力撤回、任务到期与重放 |
| G2 真实适配器 | PSP × 指定第三方发行物 | 认证、读写语义、生命周期、共享客户端、所有权保护 |
| G3 代理链路 | PSP 输出 × 客户端 × 后端实际内核 | 实际流量、禁用／到期／限额拒绝、关键协议与 TLS 组合 |
| G4 历史升级 | 声明的源发布物 → 候选发布物 | 历史数据可用、重启收敛、失败回退及任务证据 |
| G5 发布物 | 最终归档／镜像及原生目标平台 | 身份、摘要、安装、运行、升级验收 |

G1 允许注入确定性核心 runtime，但结果必须注明不含真实代理内核与完整安装认证。
G2 使用隔离且固定摘要的后端，初始化过程可重复；同时检查 token／cookie 等所声明认证模式。
G3 至少验证当前支持的关键协议 profile；使用本地隔离目标服务，避免公网网站故障干扰结论。
流量测试须明确计量口径与容差，覆盖共享客户端去重、重启计数回退、首次采样和额度边界。
G4 必须让真实旧程序创建数据；同源码仅改变版本字符串的测试归入升级机制测试，不计入历史覆盖。

### 6.1 调度

- PSP PR：G0、现有旧 PN G1；涉及适配器、渲染、升级或 schema 时增加对应 G2／G3／G4。
- PN PR：G0、清单内旧 PSP G1；清单外旧 PSP 为观测。涉及升级、数据或核心时增加对应 G3／G4／G5。
- 每日及发现上游新版后：完整政策矩阵、候选上游验证、长期兼容回归。
- 发布：支持清单要求的全部门禁，对实际候选身份验收；不能仅复用另一 commit 的 main 绿灯。

先复用现有全量旧 PN 测试，不用此规范减少历史覆盖。未来矩阵膨胀时，PR 可选边界与受影响
profile，但发布仍验证承诺清单。第三方测试不需要无界笛卡尔积；每项正式功能承诺必须有对应组合。
数据库方言与业务升级测试按相关性覆盖，不要求把每种客户端再乘以所有数据库。

### 6.2 结果完整性

CI 必须在运行前计算预期 case ID 集合，运行后核对集合与终态：缺失、意外 skip、零匹配、
超时、环境启动失败、取消都是未通过。显式不适用必须在矩阵中给理由，不能在测试里静默跳过。
汇总 job 必须在失败／取消时也产生结论，并作为 branch protection 与 release 依赖。

历史源码固定到 commit，发布物固定到 digest，禁用开发机 go.work 替换；测试夹具只能适配
测试入口，不得修补受测旧实现以使其通过。若生产代码被修改，必须另列 patched 结果。
PR 不使用生产凭据或生产后端；外部 PR 不能通过高权限 workflow 执行任意候选代码。

源码重建结果与官方发布物结果分开记录。构建后对最终待发布归档／镜像验收，通过后再推广
到正式 release／渠道；失败候选不得进入自动升级清单。签名、摘要与验收必须绑定同一发布物。
保留通过和失败的结构化报告，支持承诺不能只引用会过期的临时 runner 日志。

## 7. 发布与维护验收清单

一次兼容变更完成必须同时具有：变更方向、受影响 profile、协议演进分类、精确测试组合、
运行结果、升级与回退边、已知限制，以及需要时的弃用公告。未改变升级路径的纯观测字段变更
可以说明“不新增升级边”，但仍必须通过清单内旧接收端的反方向测试；清单外观测按第 2.3 节处理。

发布清单的审核依据是结构化证据；测试与清单不一致时发布失败。测试发现未知上游故障时不
自动篡改旧兼容事实；修复后追加新证据。维护者可以撤销错误支持声明，但必须保留原因与历史修订。

## 8. 参考与采用范围

- [Kubernetes Version Skew Policy](https://kubernetes.io/releases/version-skew-policy/)：借鉴明确的组件跨度、支持窗口与升级顺序；不照搬它的版本数量或单向限制。
- [Envoy xDS protocol](https://www.envoyproxy.io/docs/envoy/latest/api-docs/xds_protocol.html) 与 [client features](https://www.envoyproxy.io/docs/envoy/latest/api/client_features)：借鉴协议／资源版本和可选能力分离；不引入 xDS 依赖。
- [Pact Can I Deploy](https://docs.pact.io/pact_broker/can_i_deploy)：借鉴以具体双方版本的验证矩阵决定部署资格；初期使用仓库 JSON 和 CI 报告，不要求部署 Broker。
- [Semantic Versioning 2.0.0](https://semver.org/)：保留预发布标识和正确优先级；版本承诺不能替代行为证据。

**六类里今天只有三类有实例。** 上表覆盖 `wire-contract`、`adapter-live` 和
`upgrade-mechanism`；`dataplane`、`historical-upgrade`、`artifact-runtime` **一条都没有**。
这不是遗漏，而是 P3／P4／P5 各自要产出的东西——在它们完成之前，任何声称“完整链路”“历史
数据兼容”“发布物已验证”的说法都没有对应证据可引，只能显示为未验证。

按以下顺序实施；每项独立提交与验收，不因本文落库自动标为已完成：

| 阶段 | 工作与归属 | 完成标准 |
| --- | --- | --- |
| P1 | PSP 政策 schema／case planner／结果校验器 | 保留已有矩阵派生；旧 PN 列表不缩减；case 固定身份；缺项／skip 拒绝 |
| P2 | PN CI 接入清单内旧 PSP，PSP 复用 G1 | 候选反方向组合通过完整基础 profile 后纳入支持；两仓硬门覆盖全部已声明组合 |
| P3 | PN 历史升级与 PSP 数据迁移门 | 真实旧发布物造数据；每条声明升级／回退边通过；不同安装方式分列 |
| P4 | PSP 第三方隔离 G2 与实际链路 G3 | 正式支持组合的访问、限制、计量及所有权测试通过 |
| P5 | 两仓发布门与运行时统一政策 | 最终摘要绑定证据；不支持路径被拒绝；缓存失败和旧 schema 行为有测试 |

P1 的具体 schema 与 P2 反方向验证的旧 PSP 清单应在实现 PR 中落地，不能从本文推测虚构发布记录。
在 P2–P5 完成前，产品不得显示超出已有证据的双向、自动回退或完整链路保证。
