# 上游兼容策略（3X-UI / S-UI / Passwall-Node）

PSP 同时对接三个上游。这份文档给它们**一套模型**，取代散落的约定——
在此之前，3X-UI 的规则在 `3xui-compat.md`，S-UI 的处在代码注释里，
Node 的根本没有。

> `3xui-compat.md` 仍然是 3X-UI 的**逐版本速查表与踩坑记录**，本文不复制它。
> 本文管的是三个上游**共同**的形状：边界是什么、谁定、什么时候动。

## 一句话

**每个上游都有两端：一条下限、一条上限。两端都会移动，方向相反。**

## 模型

| 概念 | 含义 | 低于/高于时 |
|---|---|---|
| **下限** | 仍被支持的最老版本 | 低于 → **拒绝**（`too_old`） |
| **上限** | 已实测通过的最新版本 | 高于 → **未验证**（`untested` / `unknown`） |

「未验证」是**第三态**，既不是支持也不是不支持——三态必须分开，
因为把"我没测过"说成"它坏了"和说成"它能用"是同样严重的错误。

### 两端会动，方向相反

- **上限上移**：验证过一个更新的上游版本之后抬上去。这是常态，只加验证。
- **下限上移**：**这是本节存在的理由。新面板没有道理永远兼容老节点。**
  每次上移都是一次**破坏性决定**——会挡掉一批还在跑的旧版本，必须记进历史事件。

上限抬不动是别人的节奏问题，下限抬不动是我们自己的债。

## 三边的现状

| 上游 | 下限 | 上限 | 判定 | 数据在哪 |
|---|---|---|---|---|
| **3X-UI** | `MinXUI` 编译常量 **+** JSON，取 `max()` | JSON `max_tested_xui` | `CheckXUI` | `internal/version/compat.go` + `docs/compat/v<major>.json` |
| **S-UI** | **只有 JSON**（`activeMinSUI`，**当前为空 = 未确立**） | JSON `sui_entries` | `CheckSUI` | `internal/version/compat_sui.go` + 同一份 JSON |
| **Passwall-Node** | **无版本下限**（只有协议版本区间） | 协议版本区间 | 无 | `docs/compat/node-v4.json` + `internal/version/node_compat_matrix_test.go` |

### 为什么 3X-UI 有编译常量而 S-UI 故意没有

`MinXUI` 是一条**代码级事实**：PSP 调 `/clients/*`，老面板根本没有这个端点，
二进制**可证明**驱动不了它们，所以写死并让测试钉住。

S-UI 没有等价的事实——适配器按**能力** gate，而且当时没有任何 S-UI 发布被验证过。
在这种情况下编一个常量等于**断言一件没人查过的事**，所以两个边界都只来自 JSON。

**这个区分是模型的一部分，不是不一致**：编译常量只有在下限确实是一条可证明的事实时才存在。

### Passwall-Node 的缺口

Node 没有版本下限，也没有 `CheckNode`。它有的只是**协议版本区间**：

- `protocol_version` 恒为 `1`，从没变过
- 面板在 `/v1/node/sync` 校验它，超出认识区间即**拒绝**
- 能力是**逐项**声明的，缺哪项就少哪个功能，不整体拒绝

也就是说：**"拒绝过新的客户端"那一半已经在了**，缺的是**下限那一半**，
以及让测试矩阵从数据派生。

## Node 专属：方向

**只保证「旧 Node 对新 Panel」。先升 Panel，再升 Node。**

理由是升级顺序是定的——面板先换，Node 自然落后一截；"Node 比面板新"只会在顺序搞反时出现，
那时正确的做法是**明确拒绝**，不是含混地凑合。

这不是我们的发明：Kubernetes 规定 kubelet/kube-proxy/controller-manager **不得比 apiserver 新**；
Elastic 规定 agent 不得比 Fleet Server 新一个 minor；Go 干脆把不对称写进承诺。
各家窗口不同（Kubernetes 3 个 minor、Consul 1 个、Nomad 2 个），**方向是一致的**。

### 「碰巧能容忍」不等于「受支持」

2026-09-19 实测过反向：`v0.0.1-beta11` 的 agent 对着 `v4.0.0-beta.19` 的面板跑通，
旧面板零报错。那是**加成式扩展**的功劳，也是**碰巧**——没人承诺过这个组合，
将来某个改动破坏它不会有任何测试报警，因为从没承诺过。
**不承诺的东西坏了不算 bug，这才是危险的地方。**

## Node 专属：判据是协议版本与能力，不是 tag 号

各家用的窗口单位是"落后 N 个版本"。**这个单位对 PSP 不适用**：
一次会话里就发过 beta10 和 beta11，在这里"落后 3 个版本"等于落后几个小时。

真正稳定的量只有两个：`protocol_version`（wire 世代）与**能力声明**。
**保证范围由协议版本决定，不由 tag 数量决定。** tag 只用来跑矩阵，不参与运行时判断。

## 规则（三边通用）

1. **两端都必须是数据**，不能散落在 CI 或代码里的硬编码。改边界 = 改数据。
2. **编译常量只能抬高下限，不能降低**（3X-UI 的 `max(常量, JSON)` 就是这个意思）：
   远端数据出事故时，编译期的事实仍然兜得住。
3. **下限上移是破坏性决定**，必须记进本文档的历史事件，写清挡掉了谁。
4. **pre-release 不进保证范围**。Envoy 明确不保证 alpha 内的兼容，Go 也说"发布前不承诺"。
5. **CI 的测试矩阵从数据派生**，不另维护一份——这是三边共同的债，见下。
6. **三态分开**：支持 / 不支持 / 未验证，任何一个都不许被折叠进另一个。

## CI 的债

| 位置 | 现状 | 应该是 |
|---|---|---|
| `test.yml` → `node compatibility (released range)` | 硬编码 `beta1…beta11` | 从 `node-v4.json` 派生 |
| `release.yml` → `Released Node compatibility` | 同一张列表再写一遍 | 同上 |
| `node_compat_matrix_test.go` | `wantReleases` 再写一遍 | 断言派生结果，而不是另抄一份 |
| `docs/compat/node-v4.json` | 只有行，没有"哪几行还支持" | 加 `min_supported`，作为下限 |

每发一版要改四处；而下限一旦确立，矩阵就能**停止增长**——这正是规则 3 的用处。

## 历史事件

- **2026-09-19 · Node 反向实测**：`v0.0.1-beta11` agent × `v4.0.0-beta.19` 面板跑通。
  记为"碰巧容忍"，**未**因此把反向列入保证范围。前置核对过 beta.19 的代码树确实没有
  `nodehost.go`/`nodemetrics`，否则测试没有意义。
- **2026-09-19 · §6 的 128 KiB 上限**：加成式扩展意味着**旧面板会收到不认识的字段**。
  面板在**原始字节层**量 `host` 子树长度（`node_sync.go` 用 `RawMessage` 先量后解），
  超限丢样本并计数——这是"陌生字段"唯一能在解码前拦住的地方。
