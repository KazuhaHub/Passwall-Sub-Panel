# 发布运行手册

版本：1；日期：2026-09-19。规则来源：[产品版本迁移实施手册](product-version-migration-plan.md) §3、§10；阶段来源：[统一实施顺序](implementation-sequence.md) S07–S09。

这份文档管**发布动作怎么做**。维护侧的例行步骤在 [兼容体系维护 SOP](compat-maintenance.md)。

> **今天的状态：全部手工。** V05（编号分配与候选构建）与 V06（渠道推广）尚未实施，所以下面每一步都没有对应的自动化，**第 7 节列出缺的是什么**。写"手工"是记录事实，不是把手工当设计。

## 1. 三种身份，先分清

| 对象 | 形式 | 谁在用 |
| --- | --- | --- |
| 产品版本 | `4.0.0`（三段、无 v） | 界面、API、构建信息、文件名、Docker 精确标签 |
| 发布 tag | `release/4.0.0` | Git、GitHub Release |
| Go module 版本 | `v0.1.0`（**带 v**） | 仅 Go 依赖工具 |

`release/` 是产品 tag 的命名空间，用来和 Go module 版本隔离。**不能**用 `release/4.0.0` 当 Docker 标签或文件名；**不能**用 `102.1.0` 为 Protocol 冒充模块版本。历史 `v…` tag 不改名、不 force push。

## 2. 发一个补丁（testing 候选）

1. 选定发布线与源码 commit。**编号在动代码之前定**，不在 PR 里随手改版本号。
2. 取当前发布线**已保留或已发布**的下一个 patch 号。并发的两个发布不能取到同一个号——用创建不可变 tag 的原子冲突结果确认，冲突就重读再取，**不覆盖已有 tag**。
3. 编号一旦绑上源码就不复用。构建失败允许留下空号。
4. 创建 `release/<三段版本>` tag，**构建一次**，同一个候选跑完整门禁（`deploy/compat/` 的校验器 + `check-case-set.mjs`）。
5. 把这一批精确制品上传到该 release，创建为 **draft**。draft 不进用户目录。
6. 证据齐全后把 `prerelease` 置为 **true** → **testing**。

**渠道来自 `prerelease` 元数据，永远不来自 tag 文本。** 纯数字产品版本没有连字符，按连字符判渠道会把所有正式版误判。

## 3. 转 stable

1. 选定一个**已验收**的 release，核对 commit 与制品 digest 没有变。
2. 确认 required 证据完整（`check-case-set.mjs` 的汇总）。
3. 只改 GitHub 的 `prerelease` 元数据为 **false**。
4. **不移动 tag、不重建、不替换附件、不要求已安装的实例重装。**
5. 更新 `latest`（仅正式版）与 Docker `latest` 到**已经验证过的那个 digest**。

> 同一个版本从 testing 转到 stable 是**改元数据**，不是发新版本。若修复代码或改变构建输入导致制品不同，**分配新补丁号**，不要在原 tag 下重新上传。

## 4. 修一个坏候选

代码变更必须新 patch。旧候选保留为历史，必要时**撤销推荐**——以更高 `revision` 的政策发布收紧规则，不是简单回退到低 revision（`version.ReleasesPolicy.Supersedes` 会拒绝更低的 revision，这正是原因）。

## 5. 推广中途失败

GitHub 元数据、Docker 标签和政策更新**不是跨服务原子事务**。任何一步失败：

- 保留已知有效状态，不猜测；
- 列出 `promotion_pending` 的**准确步骤**；
- 未完成的推广不引发节点自动重装；
- 重复事件按 `release_id + 目标渠道 + digest` **幂等**——事件会重复，也可能由不同 token 触发。

## 6. 回退

`stable → prerelease` **不是**常规回退手段。坏版本通过更高政策修订撤销推荐和新升级资格；已安装实例走已验证的恢复路径。不得通过把旧版本改成很大的数字来欺骗升级器。

## 7. 今天缺什么（不要假装已自动化）

| 计划项 | 状态 | 缺的是 |
| --- | --- | --- |
| V05 编号分配 | 未实施 | 串行分配、原子冲突确认、空号处理；今天靠人取号 |
| V05 候选构建 | 未实施 | 一次构建、平台验收、精确上传 |
| V06 渠道推广 | 未实施 | 复用原制品的晋升流程、幂等重放、`promotion_pending` 状态机 |
| C08 发布门回归 | 部分 | `deploy/compat/` 的校验器已在 CI；真实发布路径未演练 |
| S08 桥接验收 | 未实施 | 旧命名桥接链、宿主 helper/updater 的真实迁移 |
| S09 新命名首发 | 未授权 | 需要明确的发布授权 |

**发布授权与代码授权是两件事。** 改代码、合并 PR、构建候选、发布制品、推广渠道、部署生产是六种操作，通过上一项不授权下一项。

## 8. 每次发布后

- 支持政策是否仍然不超过证据（`docs/compat/verification-v1.json` 的 required 集合非空且都通过）
- 固定 SHA 是否仍可获取
- 旧的解析路径是否仍然能读历史清单
- 过期的 observation 是否有人处理

维护侧的完整检查表在 [兼容体系维护 SOP](compat-maintenance.md)。
