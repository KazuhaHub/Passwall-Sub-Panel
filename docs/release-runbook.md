# 发布运行手册

版本：1；日期：2026-09-19。规则来源：[产品版本迁移实施手册](product-version-migration-plan.md) §3、§10；阶段来源：[统一实施顺序](implementation-sequence.md) S07–S09。

这份文档管**发布动作怎么做**。维护侧的例行步骤在 [兼容体系维护 SOP](compat-maintenance.md)。

> **今天的状态：编号分配与候选构建已在发布工作流里，渠道推广仍部分手工。** 一次发布是**一次 `workflow_dispatch`**，tag 由 workflow 自己切（见第 2 节），不需要本地建 tag，也不需要为了改发布路径先开一个 PR。第 7 节列出仍然缺的部分。

## 1. 三种身份，先分清

| 对象 | 形式 | 谁在用 |
| --- | --- | --- |
| 产品版本 | `4.0.0`（三段、无 v） | 界面、API、构建信息、文件名、Docker 精确标签 |
| 发布 tag | `release/4.0.0` | Git、GitHub Release |
| Go module 版本 | `v0.1.0`（**带 v**） | 仅 Go 依赖工具 |

`release/` 是产品 tag 的命名空间，用来和 Go module 版本隔离。**不能**用 `release/4.0.0` 当 Docker 标签或文件名；**不能**用 `102.1.0` 为 Protocol 冒充模块版本。历史 `v…` tag 不改名、不 force push。

## 2. 发一个候选（testing）

一次发布 = 一次 `workflow_dispatch`，跑在 **`main` 的最新 commit** 上。表单四个输入：

| 输入 | 作用 |
| --- | --- |
| `tag` | **留空即切下一个号**。只有两种情况才填：一条线的**第一条**（没有可数的号），或某个 tag 已经在仓库里。 |
| `line` | `MAJOR.MINOR`（如 `4.0`）。tag 留空时必填——**一条线的第一条是"指定"出来的，不是算出来的**，仓库里没有任何东西知道下一个版本该落在 4.0 还是 4.1。 |
| `notes` | 写进附注 tag 的说明，也是读者唯一看得到的那份。留空则给一行标题。 |
| `channel` | `auto` 按 tag 形状读；`stable` / `testing` 明确指定。 |

编号**留空即自动**，规则是：**增量修复取第 4 段**（`X.Y.0.1`、`X.Y.0.2`…），第三段只在有人**指定**一条新线时才前进。取号由**本仓库**的分配器做（`internal/version` + `cmd/allocate-release-tag`），发布工作流调它，不再调用 Passwall Node 的实现——规则是共享契约，实现各自持有，共用同一份向量。

`tag` job 做三件事，顺序不能换：

1. **拒绝没跑过测试的 commit。** 它查的是 **Test 工作流**在这个 SHA 上的结论，不是"这个 commit 上的所有 run"——枚举所有 run 会把**正在运行的这次 release 自己**算进去（in progress、无结论），于是提交因为自己存在而被拒。
2. **调本仓库的分配器取号**，并把 `-on-commit` 一起给它：已经绑在这个源码上的号会被**续用**，重跑不会烧掉新号。
3. **创建并推送附注 tag**，冲突即重读再取（最多 5 次）。`git push` 拒绝移动已有 ref，所以并发两个发布里输的那个会看到别人的号已占用，重取下一个——**永不覆盖已有 tag**。构建失败允许留下空号。

之后 `setup` 用本仓库的 `release-tag` 命令把 tag 解析成版本（tag 与版本是两个身份），门禁、构建、上传为 **draft**、Docker 依次跑；证据齐全后把 `prerelease` 置为 **true** → **testing**。draft 不进用户目录。

一次派发只发一个候选：**不移动 tag、不重建、不替换附件。**

> **分配器在本仓库里，改规则就是改代码。** 这条规则**曾经**来自 pin 住的 Node 模块，于是一个规则修复要先合并上游、再升 pin，发布路径才用得上新规则；现在它在 `internal/version` 里，合并到 `main` 即生效。
>
> **但"同一规则"仍要靠向量保证**，不是靠两边各写一遍：`internal/version` 与前端 `web-react/src/utils/productVersion.vectors.json` 由同一份向量驱动。**跨仓那一半由 pinned-source 契约 job 做**——它本来就把 Node 仓库按记录的 revision 签出来，现在这份 checkout 也用来比对向量；本仓库不再要求 Node 模块，`go.mod` 里已经没有它。

**渠道来自 `prerelease` 元数据，永远不来自 tag 文本。** 纯数字产品版本没有连字符，按连字符判渠道会把所有正式版误判。

## 3. 转 stable

1. 选定一个**已验收**的 release，核对 commit 与制品 digest 没有变。
2. 确认 required 证据完整（`check-case-set.mjs` 的汇总）。
3. 只改 GitHub 的 `prerelease` 元数据为 **false**。
4. **不移动 tag、不重建、不替换附件、不要求已安装的实例重装。**
5. 更新 `latest`（仅正式版）与 Docker `latest` 到**已经验证过的那个 digest**。

> 同一个版本从 testing 转到 stable 是**改元数据**，不是发新版本。若修复代码或改变构建输入导致制品不同，**分配新号**（同线增量修复即下一个第 4 段），不要在原 tag 下重新上传。

## 4. 修一个坏候选

代码变更必须新号：**同一小版本线上的增量修复走第 4 段**（`X.Y.0.N`），第三段留给「指定一条新线」这个决定。旧候选保留为历史。

> **不要用「撤销推荐」冒充回退。** 面板提供什么由**已发布的发行**决定，这里没有一份政策可以把某个版本从列表里拿掉——那份签名政策已经删除。所以撤销推荐是**操作决定**：在公告里说明、不去安装它。已经装上的实例按第 6 节的恢复路径处理。

## 5. 推广中途失败

GitHub 元数据、Docker 标签和政策更新**不是跨服务原子事务**。任何一步失败：

- 保留已知有效状态，不猜测；
- 列出 `promotion_pending` 的**准确步骤**；
- 未完成的推广不引发节点自动重装；
- 重复事件按 `release_id + 目标渠道 + digest` **幂等**——事件会重复，也可能由不同 token 触发。

## 6. 回退

`stable → prerelease` **不是**常规回退手段。坏版本的「撤销推荐」是公告与不安装，不是改元数据——面板不再有一份政策可以据此收紧准入（见第 4 节）。已安装实例走已验证的恢复路径。不得通过把旧版本改成很大的数字来欺骗升级器。

## 8. 每次发布后

- 支持政策是否仍然不超过证据（`docs/compat/verification-v1.json` 的 required 集合非空且都通过）
- 固定 SHA 是否仍可获取
- 旧的解析路径是否仍然能读历史清单
- 过期的 observation 是否有人处理
