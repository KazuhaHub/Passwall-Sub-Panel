# PSP v4.0.0-beta.1：升级与回退

这是 V4 首个预发布版本：原有 3X-UI、S-UI 服务器继续使用；新增自有 Passwall-Node（PN）服务器、私有安装脚本/手动安装与管理员远程升级。先选择服务器，再单独添加/配置节点。新安装基线为 PN `v0.0.1-beta3`。

## V3 数据迁移

V4 首次启动自动执行 `EnsureSchema`，不是换版本号而已：

- `nodes.port/protocol` 复制到相同的 desired/observed 两组端口/协议，然后删除旧列，保留升级时的连接行为。
- `psp_client_inbounds.provisioned=true` 转为 `applied` 并保存当时的客户端凭据；false 转为 `pending` 并开始等待计时，不伪造已下发成功。
- 客户端仍保留原 ID、凭据和流量基线；旧唯一 `(panel_id,email)` 索引改成非唯一查询索引，行身份不再随 email 改变。

历史迁移测试的源结构取自真实 `v3.9.2-beta.20` 的源码 commit `081b209d67873f8ab78f69aba5d6a24cf294404e`，冻结完整 nodes/psp_clients/psp_client_inbounds 三表模型，再运行当前迁移。覆盖共有列、禁用状态、密文/证书绑定/中转配置、ID/计数基线、首次唯一约束及重复启动幂等；不是生产数据库副本或完整面板升级 E2E。[验收测试](../../internal/adapters/sqlstore/v3_v4_upgrade_test.go)

SQLite 原生删列保留无关的自建索引/触发器；若自建对象依赖退休列，迁移拒绝启动，需人工审查该对象。不要为启动成功盲删管理员自建对象。迁移并非整体事务；启动失败也可能已完成部分结构变化。

## 升级前备份

停下所有 PSP 实例，保存一个限制访问的成套备份，并先在隔离环境验证可恢复：

- 原版本二进制或精确 Docker 镜像版本、启动参数、服务/Compose 配置、环境文件。
- 实际 `--config` / `PSP_CONFIG` 指向的配置，以及实际 `config_dir`、`data_dir`。包括外置 rulesets、templates、locales 和自管证书/密钥；目录不在默认位置或容器挂载外时也要单独备份。
- 完整 PSP 数据库的结构和数据，不只用户表。默认 SQLite 为 `<data_dir>/panel.db`；显式 SQLite DSN 可指向别处。Docker 示例的 `/app/data` 是命名卷，不能只备份宿主的 `./config`。
- 保留有效 `encryption_key` / `PSP_ENCRYPTION_KEY`（兼容别名 `PSP_SECRET_KEY_MATERIAL`）和 `jwt_secret` / `PSP_JWT_SECRET`。旧配置未设置独立加密密钥时，JWT secret 也是数据库解密材料；此次升级不要轮换它。不要将备份、安装脚本或凭据放入公开日志/Issue。

SQLite 必须确认进程退出后再一致复制；仍存在的 WAL/journal 与数据库配套保存，不能把运行中的 `panel.db` 单文件直接复制当完整备份。恢复时不能混入另一时点的日志文件。[SQLite 官方备份说明](https://www.sqlite.org/howtocorrupt.html#backup_or_restore_while_a_transaction_is_active)

MySQL 使用数据库工具的一致性 dump，包含结构/数据/索引；`mysqldump --single-transaction --quick` 的一致性只覆盖 InnoDB 等事务表，导出期间禁止 DDL。非事务表按数据库工具的锁定方案处理。PostgreSQL 可使用 `pg_dump -Fc`，同时保留恢复所需的数据库账号/授权与连接配置。为配套文件与数据库处于同一维护边界，本次升级仍建议停 PSP 写入后导出。[MySQL](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html#option_mysqldump_single-transaction)、[PostgreSQL](https://www.postgresql.org/docs/current/app-pgdump.html)

## 升级与验收

1. 完成备份后替换为对应平台的官方 V4 二进制，或将 Docker 镜像固定到 `v4.0.0-beta.1` 并保留原挂载；不要删除数据卷，不要同时运行 V3/V4 连接同一数据库。
2. 使用原配置和原密钥启动一个 PSP 实例，检查迁移完成、登录、服务器连接、节点端口/协议及订阅渲染。
3. 抽查旧用户/客户端 UUID、客户端和节点流量基线、禁用/到期/配额状态，以及已有模板/规则/语言包。测试成功不替代对实际部署的这次验收。

## 回退边界

如果新程序尚未打开数据库、执行迁移或写入不兼容数据，保留原配置/数据，换回原二进制或精确镜像通常足够；有明确同 schema 兼容证据的后续版本也可这样处理。

**V4 启动过迁移后回退 V3：停服务，保留当前失败现场，恢复升级前同一套数据库、配置/外置文件/密钥，再启动原 V3 版本。仅换旧二进制不够。** 旧版自动建表可能重建已删除的 port/protocol/provisioned 列为默认值，不能还原原有连接和下发状态。不要直接把旧 dump 合并到现用 V4 数据库；使用隔离、正确权限的恢复目标并确认配套日志。恢复备份会丢失备份之后的更改与计数，需要明确接受这一时间边界。

这不是自动降级或 VM/数据库快照恢复功能；普通一致备份与人工恢复即可。数据库恢复也不会撤销已推到外部 3X-UI/S-UI/PN 的更改，恢复后要检查并重新收敛，不宣称双端自动回到某一时点。

## 已有 PN 节点

PN `v0.0.1-beta2` 尚未具备远程升级执行器，先手动更新到 `v0.0.1-beta3`，不必在 PSP 重新添加服务器：停止节点服务，核对官方发布校验和/平台，替换 `/opt/passwall-node/bin/passwall-node` 与 LICENSE/NOTICE，更新 `config/version` 为精确版本，原样保留 `config/credential`、`config/environment` 和整个 `data`（身份、数据库、流量、core 缓存）。不要重跑新版本首次安装脚本当升级脚本：已有版本不匹配时它会拒绝覆盖。

固定 Linux/systemd 安装可由 root 执行下面的显式维护命令，然后启动非 root 节点服务，确认 PSP 显示正确版本及健康/升级能力：

```sh
sudo /opt/passwall-node/bin/passwall-node --enable-remote-upgrade
sudo systemctl start passwall-node.service
```

远程升级只适用于受管 Linux/systemd amd64/arm64 节点，下载固定官方精确版本，需要当前版本 CAS、同状态 schema（本版为 `9`）及重启后的真实进程健康确认。失败时回退节点程序/版本/许可证文件，不恢复或改动节点数据库、固定凭据和环境。Docker、其他操作系统/手动目录安装与跨 schema 更新仍走人工维护；不会让节点 daemon 以 root 运行，也不要求特权 Docker。
