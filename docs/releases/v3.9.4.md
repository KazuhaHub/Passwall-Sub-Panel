
## V3 maintenance patch

Panels now read the compatibility manifest `docs/compat/v3.json` from the
`release/v3` branch instead of from `main`, so the file a V3 panel fetches is
the file this branch ships and its drift guard checks. `main` is the V4 line
and shares no history with V3; the V3 manifest existed there only as a
hand-copied duplicate, and a missed copy would have stopped compat refreshes on
every deployed V3 panel with no visible failure — the fetch would keep serving
a stale range, the refresh would report success, and the first symptom would be
an operator refused a panel upgrade whose tested ceiling was raised weeks
earlier. Nothing else about the refresh changes: same reactive trigger, same
60-second throttle, same fallback to the on-disk cache when a fetch fails.

The copy on `main` stays in place as a frozen mirror. v3.9.3 and earlier have
that URL compiled in and keep reading it, so raising a tested ceiling for those
deployments still means editing both files until they upgrade.

The in-app update check is now scoped to this release line. It previously read
GitHub's "Latest release" marker and compared whatever tag it found against this
build. That marker is a single repository-wide pointer with no notion of a
release line, so once V4 publishes a stable it owns the marker, and a V3 panel
would have read `3.9.x < 4.y.z` and offered an upgrade across a major boundary —
to a release with a different database model and a node backend V3 cannot run.
Nothing prevented this except that V4's current tag shapes happen not to parse as
versions. The check now ignores releases from another major, and falls back to
scanning the release list for the newest V3 stable when the repository-wide
marker no longer points at this line. Panels running v3.9.3 or earlier read the
marker directly and are unaffected by this change until they upgrade.

Follow `:v3` rather than `:latest` to stay on V3. Both tags point at this image
today, but only because every V4 release so far is a pre-release and `:latest`
means "newest stable in the repository", not "newest V3". `:v3` only ever follows
V3 stable maintenance releases. Both READMEs now say so, and the release workflow
records what has to change on the day V4 ships a stable.

Back up the database and configuration, including encryption/signing keys and
custom rule sets/templates/locales, before upgrading. For SQLite, stop PSP before
copying its database; for MySQL/PostgreSQL use a consistent backup. Do not replace
your existing configuration or data directories with files from the archive.

`ghcr.io/kazuhahub/passwall-sub-panel:v3.9.4` identifies this release. The
rolling `:latest` and `:v3` tags follow stable V3 maintenance releases. The
`:beta` tag remains on the V4 testing line.
