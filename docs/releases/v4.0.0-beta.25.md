# PSP v4.0.0-beta.25

## 兼容体系整改（R01–R11）

本版发布的是整条兼容体系的整改结果。它改变的是**面板如何判断自己支持什么**，而不是支持范围本身——没有任何组合被加入或移出。

- **证据分类**（R01）：支持声明必须落在六类证据之一（wire-contract、adapter-live、dataplane、upgrade-mechanism、historical-upgrade、artifact-runtime），写进 `docs/compat-policy.md`。
- **"没测到"不再绿灯**（R02）：`go test` 退出 0 也可能一个用例都没选中。逐 case 校验器按 profile 判断，skip、零匹配、截断的日志流、非零退出、后报成功都会被拒。
- **汇总门**（R03）：每个 case 上传结构化结果，汇总 job 按规划器推导出的期望集合检查报告集合，缺一个 artifact 即未通过；所有发布动作都只经由这道门。
- **规划器**（R04）：支持集合由 `docs/compat/node-v4.json` 的 `min_supported` **按位置**切片得出，且每个 tag 固定到当初解析出的**提交**，tag 移动会被发现而不是静默测了另一份源码。
- **反方向 profile**（R05）：候选 Node agent 对**已发布的旧 PSP**跑 B01–B08。
- **真实历史升级**（R06）：用真实历史发布物验证升级/回退路径,包含平台专用 acceptance。
- **第三方隔离**（R07）：隔离启动真实 3X-UI 与 S-UI 容器,对真实面板跑适配器。
- **真实代理链路**（R08）：面板建真实状态 → 渲染订阅 → **真实 sing-box 加载** → 流量经节点通行；再验证到期与额度耗尽后确实被拒、恢复后重新可用。
- **运行时判断**（R09）：协议代、能力、观察新鲜度与操作资格由**同一个纯函数**决定，列表、任务创建与下发不再各算一遍。能力缺失现在 fail-closed。
- **发布物**（R10）：发布摘要与被验收摘要的一致性由四处独立守护强制（tag 必须解析到 CI 自身的提交、下游 job 一律 checkout 该提交、`target_commitish` 指向它、构建期间 tag 变动即拒绝发布）。
- **维护 SOP 与交接包**（R11）：`docs/compat-maintenance.md`、`docs/compat-handover.md`。

附带一处**语义澄清**（不影响行为）：`min_supported` 的意义被写明为"选择**测什么**，不决定**谁能连**"——没有生产代码读它，抬高它只停止测试下面那些版本，不会因此拒绝任何节点。拒绝节点是 wire 世代的事（`wire.min_protocol_version`），需要自己的变更与迁移验收。此前该字段的说明容易被读成相反的意思。

## 行为变化：远程升级要求"已验证的边"

**这是本版唯一可能影响你日常使用的变化。**

节点的远程升级现在要求 `(当前版本 → 目标版本)` 是一条**已验证的边**，而不只是"目标版本在支持清单里"。判断依据是清单里的 `upgrade_edges`，而**该清单目前是空的**——至今没有人通过历史升级套件验证过任何一条边。

后果：**面板不再推荐或受理任何节点远程升级**，直到有人验证并发布一条边；列表里的 `node_compatibility_reason` 会显示 `upgrade-edge-missing`。显式请求同样会被拒，理由具名。

这是有意的：先前"目标是本面板列出的某个发布"就足以推荐升级，等于沿一条没人走过的路径升级。要开放某条路径，在 `upgrade_edges` 里加一条 `{id, from, to}` 并发布到运行时清单即可，`docs/compat-maintenance.md` §3 写明步骤。**基础同步、配置下发与订阅渲染不受影响。**

## 升级与兼容性

本版为 Pre-release，仅发布 PSP，不自动升级线上面板、节点或代理内核。升级前请备份数据库和配置。

本次整改不改变任何已支持组合的**支持范围**：没有版本被加入或移出，第三方面板的测试上限与 floor 均未移动。受影响的只有"升级推荐"这一项，见上。

Docker 精确标签为 `ghcr.io/kazuhahub/passwall-sub-panel:v4.0.0-beta.25`；滚动标签 `beta` 会跟随最新发布，`latest` 仍仅指正式版。
