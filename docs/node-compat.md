# PSP × Passwall-Node 兼容性

PSP 通过 `/v1/node/sync` 接收 Passwall-Node 的汇报。本文档确定三件事：

1. **哪个方向被保证**（升级前先看这里）
2. **判据是什么**（协议版本与能力，不是 tag 号）
3. **测试矩阵怎么设、什么时候可以缩小**

> 与 `3xui-compat.md` 同一体例。那份管的是"PSP 对接多旧的 3X-UI"，
> 这份管的是"PSP 对接多旧的 Node"——**方向相反**：3X-UI 是别人做的东西，
> Node 是我们自己发的，所以这份还能反过来约束 Node 怎么改。

## 一句话

**先升 Panel，再升 Node。只保证「旧 Node 对新 Panel」这一个方向。**

## 方向：为什么只有一个

把 Panel 想成经理、Node 想成打电话汇报的员工：

- **老员工 + 新经理**：新经理上任时读过老员工的汇报格式，听得懂。**保证。**
- **新员工 + 老经理**：新员工说了老经理没听过的东西。老经理可能当没听见，
  也可能理解错。**不保证。**

原因是升级顺序是定的——先换经理、再换员工，所以员工总是落后一截。
"员工比经理新"只会在有人把顺序搞反时出现，那时**正确的做法是让经理明确拒绝**，
而不是让经理含混地凑合。

**这不是我们的发明，是行业惯例。** Kubernetes 规定 kubelet / kube-proxy /
controller-manager **不得比 apiserver 新**；Elastic 规定 agent 不得比它注册的
Fleet Server 新一个 minor，必须**先升 Fleet Server**；Go 干脆把不对称写进承诺——
Go 1.2 的代码不保证能在 Go 1.1 下编译。各家窗口不同（Kubernetes 3 个 minor、
Consul 1 个、Nomad 2 个），但**方向是一致的**。

### 「碰巧能容忍」不等于「受支持」

2026-09-19 实测过反向：`v0.0.1-beta11` 的 agent 对着 `v4.0.0-beta.19` 的面板
跑通了，旧面板零报错、把不认识的 `host` 子树静默丢掉。这是**加成式扩展**的功劳。

但那是**碰巧**。没人承诺过这个组合；将来某个改动破坏它，也不会有任何测试报警，
因为我们从没承诺过——**不承诺的东西坏了不算 bug，这才是危险的地方。**
本文档的作用就是把"碰巧"和"承诺"分开。

## 判据：协议版本与能力，不是 tag 号

各家用的窗口单位是"落后 N 个版本"。**这个单位对 PSP 不适用**：
一次会话里就发过 beta10 和 beta11，"落后 3 个版本"在这里等于落后几个小时。

PSP 与 Node 之间真正稳定的量只有两个：

- **`protocol_version`**：wire 形状的世代，目前恒为 `1`，**从未变过**。
  面板在 `/v1/node/sync` 校验它，超出自己认识的区间即拒绝。
- **能力声明**：Node 在报告里主动声明自己会什么（`host.telemetry.v1`、
  `task.diagnostics.collect.v1` …）。面板按能力**逐项**决定给不给对应功能，
  而不是整体接受或拒绝。

所以：**保证范围由协议版本决定，不由 tag 数量决定。** tag 只用来跑矩阵，
不参与运行时判断。

## 运行时怎么拦（已经实现，不是待办）

| 情形 | 现行为 |
|---|---|
| 报告的 `protocol_version` 超出面板认识区间 | **拒绝**，`protocol/validate.go` 校验 |
| Node 缺少某项能力 | 该功能对它不可用，**不整体拒绝**——能力是逐项的 |
| Node 版本老于面板 | 保证可工作 |

第一条就是"拒绝过新的客户端"，**它已经在了**。本文档要做的是把它写成承诺，
并让测试矩阵与之一致，而不是新造一道闸。

## 兼容矩阵

| Panel 版本 | 最低 Node | 已实测通过 | 备注 |
|---|---|---|---|
| **v4.0.0-beta.20+** | **未确立**（见下） | `v0.0.1-beta11` | WP4–WP10（主机遥测与远程诊断）落地；诊断走 `task.diagnostics.collect.v1` |
| v4.0.0-beta.19 及更早 | 未确立 | `v0.0.1-beta11`（**反向实测通过但不保证**） | 面板侧没有主机遥测；Node 的新字段被静默丢弃 |

**「最低 Node」为什么是未确立**：所有已发布的 Node 都还在 `protocol_version = 1`，
没有任何一个版本真的与当前面板不兼容。**最低支持版本只在某个协议版本被退休时才成立**
——在那之前，确立一个 floor 是在凭空丢弃还完全能用的版本。

这与 `3xui-compat.md` 里 S-UI 那条的处境相同，但原因不同：S-UI 是"从没有人确立过"，
Node 是"还没有需要确立的时机"。

## 规则

1. **升级顺序：先 Panel，后 Node。** Node 不得超前于 Panel。
2. **保证范围 = 面板 `[min_protocol_version, max_protocol_version]` 之内的全部已发布 Node。**
3. **超出范围必须被明确拒绝**，不得静默容忍——静默会把"不支持"变成
   "看起来能用但行为未定义"。
4. **beta / pre-release 不进保证范围**：Envoy 明确不保证 alpha 内的兼容，
   Go 也说"发布前不承诺"。稳定版才承诺。
5. **测试矩阵覆盖"仍在协议支持范围内的全部已发布 Node"**，另加一条
   **被拒路径**的测试（构造一个声称未来协议版本的报告，断言被拒）。
6. **缩小矩阵的唯一正当理由是协议版本退休**：退休协议 v1 就同时退休所有只会讲 v1 的
   Node，floor 随之移动到"仍支持的最老协议版本"。要改 floor 就改这里，并记进下节。

> ⚠️ 规则 5 与现状的差距：CI 目前把已发布 tag **硬编码在四个地方**
> （`test.yml` 的循环、`release.yml` 的矩阵、`docs/compat/node-v4.json`、
> `node_compat_matrix_test.go` 的 `wantReleases`）。每发一版要改四处，
> 而清单没有 floor 可以停。收敛成一处数据源是后续的机械改动，规范先定，改动随其后。

## 历史兼容性事件

- **2026-09-19 · 反向实测**：`v0.0.1-beta11` agent × `v4.0.0-beta.19` 面板跑通。
  结论记为"碰巧容忍"，**未**因此把反向列入保证范围。前置核对过
  beta.19 的代码树确实没有 `nodehost.go`/`nodemetrics`，否则测试没有意义。
- **2026-09-19 · §6 的 128 KiB 上限**：加成式扩展意味着**旧面板会收到不认识的字段**。
  面板在**原始字节层**量 `host` 子树长度（`node_sync.go` 用 `RawMessage` 先量后解），
  超限丢样本并计数——这是"陌生字段"唯一能在解码前拦住的地方。
